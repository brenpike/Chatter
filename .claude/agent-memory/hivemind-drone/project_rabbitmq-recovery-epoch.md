RabbitMqConnectionSource receive-channel epoch lifecycle. The bump-only recovery fix (R-STEP-003/004/005) was SUPERSEDED on 2026-06-13 by a closed-by-construction redesign (E-STEP-001..005) after a two-iteration break-fix oscillation.

**Why the bump-only fix was insufficient (EDGE 2):** The original fix kept `TopologyRecoveryEnabled` default-on and just bumped the epoch on `RecoverySucceededAsync`. But with topology recovery ON, RabbitMQ.Client re-binds the SAME consumer WITHOUT re-running `BasicConsumeAsync`, so the consumer's `ReceivedAsync` delegate keeps CLOSING OVER the registration-time epoch. After the bump, every POST-recovery delivery carries the STALE pre-bump epoch → every post-recovery ack/nack/deadletter no-ops → sustained redelivery/duplicate loop. EDGE 1 (pre-recovery in-flight false-ack) and EDGE 2 are the same class: the epoch is sampled at desyncing points (registration-closure, recovery-bump, settle-read).

**The closed-by-construction redesign (CHOSEN, user-authorized):** Disable TOPOLOGY/consumer auto-recovery (`ConnectionFactory.TopologyRecoveryEnabled = false`), KEEP `AutomaticRecoveryEnabled = true` (transport recovers). The source now OWNS the receive-channel + consumer lifecycle. A new seam `IRabbitMqConnectionSource.StartReceivingAsync(Func<IChannel,long,CancellationToken,Task> registerConsumer, ct)` lets the receiver hand the source a consume-registration delegate. On EVERY (re)creation — cold start, lazy recreate, recovery — the source, UNDER `_receiveChannelGate` as ONE atomic event, disposes the old channel, creates a fresh one, `Interlocked.Increment`s the epoch, and re-runs the stored delegate with the FRESHLY-BUMPED epoch. Because the registration (only code that stamps an epoch onto deliveries) and the bump are the same gated event, a delivery's stamped epoch ALWAYS equals its delivering session by construction, race-free. Pre-recovery in-flight delivery keeps old epoch (no-ops at settle); post-recovery delivery stamped with new epoch (settles).

**Implementation shape:** `EnsureReceiveChannelAsync` early-returns when `_receiveChannel is {IsOpen:true}`, else delegates to new private `RecreateReceiveChannelAsync` (dispose→create→QoS→bump→re-run `_registerConsumer` if non-null). `OnRecoverySucceededAsync` calls `RecreateReceiveChannelAsync` DIRECTLY (not `EnsureReceiveChannelAsync`) because the transport-recovered channel may report IsOpen but carries NO consumer — early-return would leave it consumer-less. Double `_disposed` re-check inside the gate (after WaitAsync) so DisposeAsync racing the recovery callback can't resurrect resources. Receiver: `InitializeAsync` creates the bounded `_buffer` ONCE then calls `StartReceivingAsync(RegisterConsumerAsync, ct)`; `RegisterConsumerAsync(channel, epoch, ct)` does BasicQos + new consumer + `ReceivedAsync += BufferDeliveryAsync(delivery, epoch)` + BasicConsumeAsync, capturing latest `_consumerTag` (changes across recovery). `_buffer` is NOT recreated on re-registration so in-flight buffered deliveries survive the swap.

**API (RabbitMQ.Client 7.2.1, verified by grepping `~/.nuget/packages/rabbitmq.client/7.2.1/lib/net8.0/RabbitMQ.Client.xml`):** `ConnectionFactory.TopologyRecoveryEnabled` (bool prop), `IConnection.RecoverySucceededAsync` (`AsyncEventHandler<AsyncEventArgs>`), `IChannel.ChannelShutdownAsync` (`AsyncEventHandler<ShutdownEventArgs>`). The recovery trigger used is `RecoverySucceededAsync` ONLY — fires once after connection+channel transport recovery completes; ChannelShutdownAsync was NOT used (fires mid-recovery, would race). `AsyncEventArgs` ctor is `(CancellationToken)` — raise with `new AsyncEventArgs(CancellationToken.None)`.

**Test redesign (E-STEP-004/005):** `InMemoryRabbitMqConnectionSource` now implements `StartReceivingAsync` (store delegate + invoke once with current epoch) and adds `SimulateRecoveryAsync()` (dispose old recording channel → new `RecordingChannel` → bump epoch → re-invoke stored delegate with new epoch). `ReceiveChannel` became a `private set` property returning the CURRENT channel; `ReceiveChannels` list tracks all created channels. CRITICAL COMPATIBILITY: `AdvanceEpoch()` stays BUMP-ONLY (no channel swap, no re-register) so the existing `WhenSettlingMessage` stale-epoch tests (call AdvanceEpoch then settle an already-buffered delivery, expect no-op) keep passing. `RecordingChannel` needed NO change — each `new RecordingChannel()` is already a fresh per-session recorder. `ReceiverHarness` needed NO change (InitializeAsync internally calls StartReceivingAsync). Old `WhenAdvancingEpochOnRecovery.cs` (bump-only, masked EDGE 2) REPLACED by `WhenRecreatingReceiveChannelOnRecovery.cs`: proves (a) post-recovery delivery stamps new epoch, (b) pre-recovery delivery no-ops at settle, (c) post-recovery delivery settles, buffer-survives-recovery, (d) N recoveries = N bumps + N+1 channels each with a consumer, (e) recovery-after-disposal no-op (kept on the REAL source via the `OnRecoverySucceededAsync` reflection seam — handler short-circuits on `_disposed` before touching the gate).

**Counts:** RabbitMQ test suite 118→120 per TFM (net8.0+net10.0) after the swap (dropped 4 bump-only tests, added 6 invariant tests). Full `dotnet test Chatter.sln --filter Category!=Integration` green both TFMs.

**Publish-pool / topology-off dependency check (flagged clean):** Publish channels declare no topology (publish to default exchange by name), and `AcquirePublishChannelAsync`'s `!channel.IsOpen` lazy-recreate already covers a post-recovery closed publish channel — so `TopologyRecoveryEnabled=false` has NO impact on the publish path. No production path depends on client topology recovery for queue existence (topology is provisioned externally/in-test).
