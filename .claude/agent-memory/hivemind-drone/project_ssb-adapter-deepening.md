**Hard reachability ceiling for sender Dispatch unit tests (empirically verified against System.Data.SqlClient 4.8.6):** an unopened `SqlConnection` (what InMemorySqlConnectionSource hands back) — `CreateCommand()` WORKS, but `BeginTransactionAsync()` THROWS InvalidOperationException ("connection is closed"). In `Dispatch`'s new-connection branch this fires AFTER the source is consulted but BEFORE the Begin/Send/End loop. So through Dispatch the ONLY unit-reachable surface is: (a) ctor null guards, (b) new-connection branch consults ISqlConnectionSource once with CancellationToken.None, (c) policy origin decision (no context tx => NewConnection for all 3 modes), (d) fail-fast + propagate. DEFERRED to end-to-end: Begin/Send/End sequencing, EndConversationAfterDispatch firing, ChatterBrokeredMessageType body-conversion (private SendMessageOnConversation, post-live-Begin), commit-on-success, ReuseContext branch.

**Two traps that look assertable but are NOT:** (1) `SqlTransaction` has no public ctor and can't be begun without an open connection, so the ReuseContext branch (FullAtomicityViaInfrastructure + present context tx) is NOT constructible at unit scope — its decision is pinned on the pure OutboundTransactionPolicy instead. (2) `connection.Dispose()` in the finally on the !useContextTransaction path leaves NO observable trace when the connection was NEVER opened (post-dispose State stays Closed AND ConnectionString remains settable without throwing — verified). So you CANNOT prove Dispose ran on the fail-fast path; the dispose contract is only reachable once the connection is actually opened (live SQL). I wrote a dispose-assertion test, found it false via probe, and deleted it — do not re-add it.

**HARD BLOCKER forcing the ServiceDescriptor FALLBACK (not full resolution like the ASB twin):** full Chatter bootstrap is UNREACHABLE in the SSB test AppDomain. Both `AddChatterCqrs` AND `AddMessageBrokers` call `AssemblySourceFilter.Apply()` (CqrsExtensions line 35 / ChatterMessageBrokerExtensions line 89), which is `ExplictAssemblies.Union(GetAssembliesThatMatchNamespaceSelector())` — and the latter UNCONDITIONALLY enumerates `AppDomain.CurrentDomain.GetAssemblies()` and calls `assembly.GetTypes()` on EVERY loaded assembly (AssemblySourceFilter.cs line 54), BEFORE any namespace-selector filtering. In the SSB AppDomain, System.Data.SqlClient 4.6.1.6 is loaded (transitive ref) and its `GetTypes()` throws `ReflectionTypeLoadException: Could not load type 'SqlGuidCaster' ... incorrectly aligned or overlapped`. No AddChatterCqrs/AddMessageBrokers overload avoids this — namespace-selector & marker-type & explicit-assembly overloads all still run the full AppDomain GetTypes scan. The throw is in product CQRS code; cannot be suppressed from a test without product edits (out of scope).

**Why ASB doesn't hit it:** ASB module does NOT reference System.Data.SqlClient, so its AppDomain GetTypes scan is clean — that's the ONLY reason the ASB twin (commit 5bbd601) could full-resolve.

**The fallback that works:** build a BARE `ChatterBuilder.Create(services, config, AssemblySourceFilterBuilder.New().Build())` and call ONLY `AddSqlServiceBroker` on it — AddSqlServiceBroker itself runs NO Apply() scan, so the real production registration executes cleanly. Then assert ServiceDescriptor shape on the IServiceCollection: IMessagingInfrastructure = Singleton w/ ImplementationFactory!=null; ISqlConnectionSource/receiver/sender = Scoped (internal types fetched by FullName via `typeof(SSBMessageContext).Assembly.GetType(..., throwOnError:true)`); SqlServiceBrokerOptions = Singleton instance carrying the connection string; NO IBrokeredMessagePathBuilder registered (pins the 3-arg-ctor default-path-builder divergence from ASB). Survives the STEP-006 factory rewire because it asserts service-type/lifetime/factory-presence, NOT the concrete factory type name.

**Config gotcha:** `SqlServiceBrokerOptionsBuilder.WithConnectionString` alone NPEs in Build() — it sets `.ConnectionString` on a still-null `_sqlServiceBrokerOptions`. Must call an `AddSqlServiceBrokerOptions(connectionString[, ...])` overload first (the string overload constructs the options object). Canonical usage (SqlChangeFeedExtensions line 73) uses `AddSqlServiceBrokerOptions(options)`.
