Follow one message

01 · The noise

Every call knows too much.

Controllers swell with orchestration. Logging, transactions and retries are copy-pasted into every path.

Broker SDK calls leak into domain code, so changing brokers means rewriting the business logic that never cared which broker it was.

02 · Chatter.CQRS

Three shapes. One dispatcher.

Send a message to IMessageDispatcher; its shape decides where it goes.

  1. Command — handled by exactly one handler.
  2. Event — zero or many handlers react.
  3. Query — the Query Dispatcher returns a Read Model.
public class PlaceOrderHandler
  : IMessageHandler<PlaceOrder>
{
  public Task Handle(PlaceOrder message,
    IMessageHandlerContext context) …
}

03 · Command Pipeline

Cross-cutting, written once.

Ordered behaviors wrap every Command handler — logging, unit of work, an inbox check — so the handler keeps only the business decision. A Message Context travels with each dispatch.

Assembly scanning finds and registers your handlers:

builder.Services.AddChatterCqrs(
  builder.Configuration,
  typeof(Program).Assembly);

04 · Chatter.MessageBrokers

Leave the process. Keep the handler.

A handler publishes; in another service a Brokered Message Receiver hands the message to an existing handler. Same interface on both sides.

[BrokeredMessage("order-placed",
  "shipping-order-placed")]
public class OrderPlaced : IEvent { … }

await context.Publish(new OrderPlaced { … });

The attribute names the send and receive paths, so handlers never name a queue or topic. Until AddMessageBrokers() replaces it, the External Dispatcher is a no-op.

05 · Transports

Swap the medium. The handler stays.

Azure Service Bus — queues, topic subscriptions, sessions and cross-entity transactions.

.Auth: Entra ID tokens, including managed identity — no connection-string secret.

$ dotnet add package Chatter.MessageBrokers.AzureServiceBus

RabbitMQ — publish and receive over the exchanges and queues you provision.

$ dotnet add package Chatter.MessageBrokers.RabbitMQ

SQL Server Service Broker — conversations and queues inside the database you already run.

$ dotnet add package Chatter.MessageBrokers.SqlServiceBroker

Transports create no infrastructure; you provision queues, topics, exchanges and Service Broker objects.

06 · Reliability

Store first. Publish after commit.

  1. Outbox — state change, Inbox record and Outbox record are saved in one database transaction in your DbContext; the message publishes after commit (optional polling Outbox Processor). the Document Tier writes the aggregate, an Outbox document and an Inbox marker in one TransactionalBatch; a change-feed Outbox Relay publishes pending outbox documents.
  2. Inbox — deduplicates redelivered commands: a message it has already recorded skips the handler.

07 · Recovery

Bend, set aside, then break.

  1. Retry — transient failures get another attempt.
  2. Error Queue — a message that exceeds its max receive attempts is moved aside for inspection.
  3. Circuit Breaker — after repeated failures it stops processing, then admits trial calls once it has cooled.

08 · Chatter.SqlChangeFeed

public class OrderRowChanged

09 · Diagnostics

Visible when you ask.

Opt-in tracing and metrics through ActivitySource and Meter from the .NET base class library. Nothing is emitted until you subscribe.
