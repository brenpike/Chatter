The SDK buries the domain.

  • Your domain starts simple: orders, payments, the rules of the business.
  • Then broker SDK code moves in: retries, queues, connection strings, serializers, dedupe. Controllers swell with orchestration and the domain gets buried.
  • Chatter moves those concerns behind stable abstractions in separate packages, so your handlers keep speaking the domain.

  • A Command asks for one thing to happen. The Message Dispatcher (IMessageDispatcher) sends it to exactly one handler.
  • An Event says something happened. Zero or many handlers react to it.
  • A Query asks a question. The Query Dispatcher returns a Read Model.
  • The Command Pipeline wraps every Command handler in ordered behaviors such as logging, unit of work and an inbox check. AddChatterCqrs scans your assembly and registers the handlers.

  • In the Orders service a handler publishes an Event with context.Publish(new OrderPlaced { … }).
  • [BrokeredMessage] on the message names its send and receive paths, so handlers never name queues or topics.
  • In the Billing service a Brokered Message Receiver, a hosted service per message type, hands it to the handler you already wrote.
  • The External Dispatcher is a no-op until AddMessageBrokers() replaces it. Until then, everything stays in-process.

  • Retry runs a failing receive again, immediately or with constant or exponential delay, for the exception types you choose.
  • The Circuit Breaker stops processing after repeated failures, then admits a trial once it has cooled.
  • A message that reaches its receive limit is deadlettered and sent to its Error Queue, out of the way of healthy traffic.

  • Chatter.SqlChangeFeed watches a SQL Server table. A new row arrives as a strongly typed RowInsertedEvent.
  • A changed row arrives as a RowUpdatedEvent, handled by an ordinary Chatter handler.
  • A removed row arrives as a RowDeletedEvent.
  • It is built on SQL Server Service Broker, so the change feed rides the database you already run.
