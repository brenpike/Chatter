Line 01 · The trouble

Direct dialing gets tangled.

Every service dials every other service directly. Orders calls Billing, Billing calls Mail, Mail calls Audit, and each one hand-wires the line.

Broker SDK calls, retry loops, duplicate checks and queue names end up soldered into domain code. Controllers fill with orchestration. Change the broker and you rewire the building.

Chatter puts an exchange in the middle. Handlers stay plain C#, cross-cutting concerns live in one pipeline, and the broker becomes a line you plug in.

Line 02 · Chatter.CQRS

Private lines, party lines, and calls that answer back.

Chatter.CQRS is the in-process exchange. Hand a message to the Message Dispatcher and it finds the handler by type. Assembly scanning registers your handlers, so a new handler is just a new class.

Program.csbuilder.Services.AddChatterCqrs( builder.Configuration, typeof(Program).Assembly);

A Message Context travels with each dispatch, so headers and cancellation ride along with the call.

Command · a private line. Patched to exactly one handler. On the way it passes the Command Pipeline: ordered behaviors such as logging, a unit of work or an inbox check wrap every Command handler.

Event · a party line. Rings every handler that subscribes to it: one, many, or none at all. The caller never needs to know who picks up.

Query · a call that answers back. Goes through the Query Dispatcher to its handler and returns a Read Model, without changing a thing.

Line 03 · Chatter.MessageBrokers

Long distance. Same handler.

Chatter.MessageBrokers adds the trunk line between services, without tying you to a carrier. A Brokered Message Receiver is an operator on duty: a hosted service, one per message type, that takes calls off the broker and hands them to the handlers you already wrote.

A [BrokeredMessage] routing card supplies the send and receive paths, so handlers never dial a queue or topic name. Until AddMessageBrokers() is called, the External Dispatcher is a no-op and nothing leaves the building.

Route by card, not by dialing[BrokeredMessage("orders.placed")] public class OrderPlaced : IEvent { /* … */ } // inside PlaceOrderHandler.Handle await context.Publish(new OrderPlaced { OrderId = message.Id });

It also brings sending and routing (Brokered Message Router, Forwarder), Recovery, and the Inbox and Outbox ports. It ships no transport of its own: that is the next line.

External Dispatcher: no-op. The call stays in the building.

Line 04 · Transports

Swap the trunk. Keep the handler.

Three carriers, one socket shape. Each transport plugs into Chatter.MessageBrokers; your handlers and messages do not change when the trunk does.

  • Azure Service BusQueues, topic subscriptions, sessions and cross-entity transactions.
  • RabbitMQSends and receives over the exchanges and queues you provision.
  • SQL Server Service BrokerConversations and queues inside the SQL Server you already run.

Transports provision nothing. You create the queues, topics, exchanges or Service Broker objects; Chatter connects the calls.

Line 05 · Reliability

Keep a call log. Keep a ledger.

Brokers redeliver, and processes stop between a save and a send. Chatter's reliability modules keep the books in the database you already use.

Inbox · the call log. Each handled call is written down. A redelivered call already in the log is recognised and the handler is not rung again: the Inbox deduplicates redelivered commands.

Outbox · the ledger. The state change and the outgoing message are saved in one transaction, and the message publishes from the store after commit.

Reliability.EntityFramework. Inbox, Outbox and Unit of Work stored in your DbContext. State change, Inbox record and Outbox record are saved in one database transaction; the Outbox publishes after commit, with an optional polling Outbox Processor.

Reliability.Cosmos. The Document Tier writes the aggregate, an Outbox document and an Inbox marker in one TransactionalBatch; a change-feed Outbox Relay publishes pending outbox documents. A standalone Inbox Gate is there too.

Line 06 · Recovery

Busy signals, blown breakers, the dead-letter board.

Lines fail. Chatter.MessageBrokers ships Recovery for the moment a handler cannot take the call.

  • RetryA busy signal is not the end: a failed receive is tried again.
  • Circuit BreakerWhen a line keeps failing, the breaker trips open and stops taking calls. After a pause it lets a test call through (half-open), then closes once it connects.
  • Error QueueA message that exceeds its max receive attempts is parked on the Error Queue, where you can inspect it.
Line 07 · Chatter.SqlChangeFeed

Line 08 · Diagnostics

The supervisor's panel stays dark until you look.

Tracing and metrics are opt-in and built on the .NET base class library, ActivitySource and Meter. Nothing is emitted until you subscribe, with OpenTelemetry or any listener.

Subscribe with OpenTelemetrytracing.AddSource("Chatter.CQRS", "Chatter.MessageBrokers"); metrics.AddMeter("Chatter.CQRS", "Chatter.MessageBrokers");
