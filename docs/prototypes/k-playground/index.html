00 Chatter for .NET

Write the handler once. Let it travel.

Modular .NET libraries for domain-driven Web APIs and microservices: an in-process CQRS core with technology-agnostic brokered messaging.

  • Controllers bloat with orchestration and copy-pasted cross-cutting code.
  • Broker SDK calls leak into domain code and lock you to one vendor.

The simulator is two services built with Chatter, already running. Scroll and each level hands you a new control.

dotnet add package Chatter.CQRS

01 Dispatch · Chatter.CQRS

Every message knows where it goes.

Commands change state and reach exactly one handler. Events announce what happened to zero or many handlers. Queries return a Read Model through the Query Dispatcher. Your controller hands the message to the Message Dispatcher, and assembly scanning has already registered every handler.

03 Go distributed · Chatter.MessageBrokers

      
Same handler. Now it crosses services.

      
The handler publishes with context.Publish. On its own, the External Dispatcher does nothing. AddMessageBrokers() replaces it, so the event leaves for a broker and a Brokered Message Receiver in Billing hands it to Billing's own handler. [BrokeredMessage] names the paths, so handlers never name a queue or topic.

04 Transports

      
Pick a broker. Keep the code.

      
Chatter.MessageBrokers ships no transport. Add Azure Service Bus, RabbitMQ or SQL Server Service Broker and only the registration changes. Transports create no infrastructure: you provision the queues, topics, exchanges or Service Broker objects. The Auth package signs in to Azure Service Bus with Microsoft Entra ID, including managed identity, instead of a connection-string secret.

05 Chaos · Reliability

      
Make the network misbehave.

      
Brokers can deliver the same message twice, and a process can stop between saving state and publishing. The Inbox deduplicates redelivered commands. The Outbox saves outgoing messages with your state in one transaction and publishes them from the store after commit. Choose EF Core, stored in your own DbContext, or Azure Cosmos DB, written in one TransactionalBatch and relayed from the change feed.

06 Recovery · Chatter.MessageBrokers

      
When a dependency has a bad day.

      
A failed receive is retried. Repeated failures trip a Circuit Breaker that pauses receiving, then lets one message test the water half-open. A message that exceeds max receive attempts moves to the Error Queue, and the Receiver moves on.

07 Change Feed · Chatter.SqlChangeFeed

      
Your table becomes an event stream.

      
Watch a SQL Server table. A trigger sends each row change onto a Service Broker queue, and a Receiver hands it to your handlers as a typed RowInsertedEvent<T>, RowUpdatedEvent<T> or RowDeletedEvent<T>. Nothing polls the table.
