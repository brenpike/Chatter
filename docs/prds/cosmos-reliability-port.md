# PRD: Cosmos DB reliability provider (two-tier reliability port)

## Problem Statement

Chatter.MessageBrokers' reliability port (outbox/inbox/unit-of-work) is shaped entirely around a relational ambient-transaction model: the unit of work wraps the whole message handler in an open transaction. Teams building on Azure Cosmos DB (NoSQL) cannot use it — Cosmos has no ambient transaction; its atomic primitive is a stage-then-commit batch confined to one logical partition. Today such teams must hand-write transactional-outbox plumbing per app, risking non-atomic "publish after a separate write" bugs and accidentally deriving integration events from domain-document change feeds. They need a first-class Cosmos reliability provider that realizes the transactional-outbox atomic-writes pattern with the same reliability guarantees the EntityFramework provider gives relational users.

## Solution

Evolve the reliability port to Two-Tier Reliability: a Relational Tier (the existing ambient-transaction, polling-dispatch model, behavior-unchanged) and a new Document Tier (NoSQL stage-then-commit). The two tiers share only the abstract message / enqueue / inbox **contracts** — not the EF-shaped mechanics. The document tier owns its **own provider-shaped document-tier reliability surface** that carries the document-store primitives: resolved partition key, bound container, the `TransactionalBatch` handle, batch lifecycle, inbox-marker enlistment, and ETag concurrency token. The enqueue contract (`SendToOutbox`) is abstracted over an **Atomic-Write Handle** (the relational `IPersistanceTransaction` OR the document-tier handle both satisfy it — exact shape deferred to implementation); the inbox contract and intent are shared while the seam that implements them forks per tier. A new Cosmos reliability provider lets an application atomically persist its aggregate and its outbound messages in a single partition-scoped batch; the framework owns the batch lifecycle (open + execute) while the application owns aggregate serialization and partition selection, and the handler contributes aggregate ops to the framework-owned batch (framework-owns-batch-lifecycle). The partition key is sourced via an app-registered **partition-key resolver** — an application-supplied delegate `(InboundBrokeredMessage) -> partition-key` — invoked by the Document-Tier Batch-Lifecycle Behavior to open the batch on the correct partition. A change-feed Outbox Relay drains persisted outbox records — identified by an outbox discriminator — and publishes them through the broker, never deriving events from domain-document changes. Inbox idempotency uses a co-resident inbox marker contributed by the Document-Tier Batch-Lifecycle Behavior (via the document-tier reliability surface, not via `ReceiveViaInbox` / `InboxBehavior` which are relational-only mechanics) to the framework-owned batch before the handler runs; a create-conflict detected at the single framework-owned batch-execute fails the whole batch atomically, making dedup atomic with the aggregate write. The existing EntityFramework users are unaffected at runtime.

## User Stories

- As an app developer on Cosmos DB, I want atomic aggregate and outbound-message persistence in one partition batch, so that I never publish an event whose state write rolled back.
- As an app developer, I want Chatter to own the outbox-record shape and the relay, so that I write no hand-written outbox plumbing and face no risk of deriving events from domain changes.
- As a message consumer, I want idempotent inbox dedup on the Document Tier, so that a redelivered message is handled once.
- As an existing EntityFramework reliability user, I want the Relational Tier to behave identically after the port change, so that upgrading does not change runtime behavior.
- As a library maintainer, I want the breaking core-port change to be scoped and versioned, so that implementers, not ordinary consumers, absorb the break knowingly.
- As a maintainer and CI, I want an emulator-backed integration suite that asserts Chatter's contracts, so that atomicity, relay, and dedup regressions are caught.

## Acceptance Criteria

- The core reliability port exposes a common enqueue contract (abstracted over an Atomic-Write Handle — exact shape deferred to implementation) and a common inbox dedup **contract** (a tier-neutral once-only-handling abstraction — parallel to the Atomic-Write Handle, exact C# shape deferred to implementation), each realized by both tiers, plus a relational-only Pollable Outbox Store capability the Document Tier does not implement; the unit-of-work (ambient-transaction) capability is relational-only. The common inbox contract is the tier-neutral dedup abstraction, NOT the relational-shaped `IBrokeredMessageInbox.ReceiveViaInbox(..., Func<Task>)` wrap seam: `ReceiveViaInbox` / `InboxBehavior` are relational-only mechanics that REALIZE the shared contract on the relational tier, while the document tier realizes the same contract via inbox-marker enlistment on its own reliability surface. The contract and intent are shared; the implementing seam is provider-specific.
- The Relational Tier (EntityFramework provider) exhibits identical observable behavior before and after the change (ambient transaction; polling dispatch).
- On the Document Tier, an application's aggregate write and its outbound message(s) either both persist or neither does, within a single logical partition.
- A Document-Tier outbound message persisted via the enqueue contract becomes a Chatter-owned outbox record Co-Resident with the aggregate (same container, same logical partition), carrying the agreed identity and discriminator, with an expiry applied after delivery.
- The Outbox Relay publishes only outbox records (selected by discriminator) and never publishes from domain-document changes.
- Each outbox record is published through the broker at-least-once; the relay suppresses the delivered-document duplicate (a record already marked delivered / past its delivery stamp is not re-published by the change-feed update that stamped it), and downstream consumers deduplicate (the document-tier inbox marker is the in-framework mechanism). Exactly-once broker publication is not promised, since publishing and persisting the delivered-status/TTL marker are two separate systems.
- A redelivered message with the same identity is handled once: inbox dedup is atomic with the aggregate and outbox write via a co-resident inbox marker contributed by the framework to the framework-owned batch before the handler runs; a 409 create-conflict detected at the single framework-owned batch-execute fails the whole batch (no aggregate write, no outbox record). This constraint applies when the message deterministically maps to a single aggregate partition; handlers outside that scope are not covered by document-tier inbox dedup.
- The change-feed Outbox Relay is at-least-once; downstream consumers must implement idempotency (the document-tier inbox marker is the in-framework mechanism).
- Post-delivery TTL purge of outbox records requires the application's container to have TTL enabled (container `defaultTtl` set, e.g. to `-1`); this is an application prerequisite and is not automatic.
- Aggregate concurrency conflicts surface as an optimistic-concurrency failure the application can retry; inbox/outbox identity collisions surface as create-conflicts.
- The Cosmos provider package targets net8.0 and net10.0 and depends on the Cosmos SDK major line that provides the batch and change-feed-processor capabilities.
- Versioning: the core MessageBrokers package takes a breaking-change version step; the EntityFramework provider takes a corresponding version step; the new Cosmos provider ships at its initial version. CHANGELOG entries exist for all three, including a breaking-change note on the core.

## Implementation Decisions

- The **surface-ownership boundary** governs how the two tiers relate: the document tier owns its own provider-shaped document-tier reliability surface (carrying the resolved partition key, bound container, `TransactionalBatch` handle, batch lifecycle, inbox-marker enlistment, and ETag concurrency token); it shares with the relational tier **only** the abstract message / enqueue / inbox contracts. Because document-store primitives live on a surface designed to hold them, the class of finding "the EF-shaped seam carries no primitive X" is eliminated by construction.
- Two coexisting reliability tiers share the abstract enqueue contract and the abstract inbox dedup contract. The enqueue contract (`SendToOutbox`) is abstracted over an **Atomic-Write Handle** (the relational `IPersistanceTransaction` OR the document-tier handle both satisfy it — exact shape deferred to implementation). Symmetrically, the inbox contract is a tier-neutral **inbox dedup contract abstraction** (the once-only-handling intent — exact C# shape deferred to implementation), parallel to the Atomic-Write Handle. This shared contract is NOT the relational-shaped `IBrokeredMessageInbox.ReceiveViaInbox(..., Func<Task>)` wrap seam: the relational tier REALIZES the shared contract via its `ReceiveViaInbox` / `InboxBehavior` seam (relational-only mechanics), and the document tier REALIZES the same contract by enlisting the inbox marker via the document-tier reliability surface. The contract and intent (once-only dedup) are shared; the mechanics implementing them fork per tier.
- The outbox contract is split: a common enqueue responsibility versus a relational-only polling-dispatch responsibility. The Document Tier implements only enqueue and its own relay; it never implements polling dispatch or the unit-of-work.
- The Document Tier uses framework-owns-batch-lifecycle: the Document-Tier Batch-Lifecycle Behavior (outermost document-tier pipeline behavior, sibling of `UnitOfWorkBehavior`) owns batch open and batch-execute; the application owns aggregate serialization and partition selection; the handler contributes aggregate ops to the framework-owned batch via the doc-tier atomic-write handle (the doc-tier sibling of `IPersistanceTransaction`, NOT a value stuffed into `TransactionContext.Container`); the framework contributes the inbox marker and the outbox record. This keeps the messaging library ignorant of application domain types and container ownership, and makes aggregate-plus-outbox co-location structurally enforced. The handler must NOT execute the batch — batch-lifecycle ownership belongs to the framework; executing the batch inside the handler re-admits the commit-point failure that framework-owns-batch-lifecycle eliminates.
- The **partition-key resolver** is an app-registered delegate `(InboundBrokeredMessage) -> partition-key` invoked by the Document-Tier Batch-Lifecycle Behavior to open the batch on the correct partition. There is no core primitive carrying the partition key (the core has zero references to partition concepts); the partition is the aggregate's partition, which only the application knows. The resolver lives on the document-tier reliability surface, never as a core property.
- The outbox record is Co-Resident with its aggregate in one logical partition (cross-partition and cross-container atomic writes are physically impossible on the platform and are a non-goal).
- Dispatch on the Document Tier is a change-feed Outbox Relay filtered by an outbox discriminator — not a polling query — and is forbidden from deriving integration events from domain-document changes. The relay is at-least-once; downstream consumers must deduplicate via the inbox mechanism.
- Idempotency and concurrency model on the Document Tier: ETag optimistic concurrency for aggregate writes (lives on the document-tier surface, not on `TransactionContext`); conflict-on-create dedup for outbox identity; inbox dedup via a co-resident inbox marker contributed by the Document-Tier Batch-Lifecycle Behavior to the framework-owned batch before the handler runs — a create-conflict detected at the single framework-owned batch-execute fails the whole batch atomically (no aggregate write, no outbox record), making dedup atomic with the handler's write rather than a sequential guard. Applicable only when the message deterministically maps to one aggregate partition. Post-delivery TTL purge requires the application's container to have TTL enabled (container `defaultTtl` set).
- This is a breaking change to the core reliability port; the breaking surface is confined to code that implements the port or constructs outbox records directly, not to ordinary consumers of broker adapters. The surface-ownership boundary narrows this blast radius: the document tier touches core only for the outbox-interface split (`IPollableOutboxStore` peel) and the Atomic-Write Handle abstraction on the enqueue contract; no `TransactionContext` generalization, no `InboxBehavior` generalization, no typed multi-tier `ContextContainer`.

## Testing Decisions

- An emulator-backed integration suite verifies Chatter's contracts, not the database SDK. Asserting a hand-built batch merely exists is banned as the system-under-test; every test drives Chatter's public contracts and observes results through them.
- Required contract coverage (intent, not test code): the enqueue contract produces the correct Co-Resident outbox record in the framework-owned batch; atomicity (a forced aggregate concurrency failure leaves no outbox record; success yields both aggregate and outbox record); inbox idempotency atomicity (for a redelivered message whose inbox marker already exists, the marker `CreateItem` conflict is detected at the single framework-owned batch-execute — after `next()` returns — so no aggregate write and no outbox record commit; the criterion asserts the absence of committed writes on conflict, since the duplicate is detected at framework-owned batch-execute, not via a pre-handler marker read); Outbox Relay discriminator filtering (a domain-document change is not published, an outbox record is published); relay publish-once plus post-delivery expiry (requires container TTL enabled); at-least-once relay redelivery (a publish-succeeds-then-status-update-fails scenario causes redelivery on the next change-feed pass, and the inbox marker deduplicates the redelivery); and an end-to-end path from handler through relay to a broker sink exercised through Chatter's public API.
- The suite is docker-gated and runs in the existing CI integration lane alongside the other adapters' integration suites; it auto-skips when the container runtime is unavailable.
- The Relational Tier retains its existing unit-test coverage, extended to prove the interface split is behavior-preserving.

## Success Metrics

- A Cosmos DB application can adopt the provider and achieve atomic aggregate-plus-event persistence without writing its own outbox plumbing.
- Zero observed "event published but state write rolled back" outcomes under the atomicity tests.
- Existing EntityFramework consumers upgrade across the breaking core version with no runtime-behavior change.
- The integration suite reliably passes in the CI integration lane (flake rate low enough not to gate unrelated PRs).

## Out of Scope

- Cross-partition and multi-aggregate atomic writes (saga and process-manager territory).
- Document-tier inbox once-only dedup for handlers whose incoming message does not deterministically map to a single aggregate partition.
- Deriving integration events by tailing the domain change feed.
- The older Cosmos SDK major line and the separate non-SDK client packages.
- Migrating existing EntityFramework consumers off the Relational Tier (it remains, unchanged).
- A new strongly-typed core partition-key property — the partition key is application-domain knowledge; it is sourced via the app-registered partition-key resolver on the document-tier reliability surface and never becomes a core property. This is consistent with the surface-ownership boundary: no partition concept reaches into core.
- Any specific downstream application's own integration with this provider.

## Further Notes

- Primary delivery risk: change-feed Outbox Relay correctness (publish-once and lease management) is the most novel surface and warrants the heaviest contract coverage.
- The Cosmos emulator for the container runtime is heavy and historically flaky in CI; mitigation is the lighter preview emulator plus a generous startup budget and strict docker-gating so it never causes timeout-only failures on unrelated PRs.
- Exact version numbers and per-package CHANGELOG wording are resolved at implementation time under the project's versioning governance; the breaking-change classification on the core is fixed.
- **Desirable simplification — #216 blast radius narrows (net).** The surface-ownership boundary is a net simplification of the core breaking change. The document tier no longer needs `TransactionContext` to carry a partition key, does not need `InboxBehavior` GENERALIZED to cover Cosmos (the relational-shaped wrap seam is not forked onto the document tier), and does not need `ContextContainer` to become a typed multi-tier handle. Core is touched for the outbox-interface split (`IPollableOutboxStore` peel), the Atomic-Write Handle abstraction on the enqueue contract, and the symmetric tier-neutral inbox dedup contract abstraction (the once-only-handling intent — so both tiers have a common inbox contract to realize). The document-tier reliability surface (partition-key resolver registration, Document-Tier Batch-Lifecycle Behavior, doc-tier atomic-write handle, inbox-marker enlistment) lives entirely in the new Cosmos module. Pre-1.0 blast radius is assessed as low.
- **Root-cause scope and linked review threads.** The surface-ownership boundary resolves root-cluster r3409943227 by construction (eliminated class: the doc tier no longer reaches into the relational-shaped `TransactionContext` for primitives it does not carry); the approach-level recurrence across r3409870435 / r3409914969 / r3409943227 is closed by the same boundary. Full root-cause scope and bounded-impact rationale (pre-1.0, low) are recorded here as the deferral target for those threads. Impact is bounded: only implementers of the reliability port are affected; ordinary broker-adapter consumers are unaffected.
