# Document-tier participation model and multi-container via a per-command container registry

The document-tier reliability provider (ADR-0006 / ADR-0007) shipped as a single global, single-container behavior. The outermost `DocumentTierBatchLifecycleBehavior<TMessage>` is an open-generic pipeline behavior, and the CQRS pipeline cannot register behaviors conditionally — `WithBehavior(Type)` registers one open generic, and `CommandBehaviorPipeline` resolves and runs `ICommandBehavior<TMessage>` for EVERY command. Two defects followed from that shape:

1. **No participation model — and a null-inbound NRE.** The behavior resolved the partition key for every command via `PartitionKeyResolver.Resolve(messageHandlerContext.GetInboundBrokeredMessage())` BEFORE `next()`. But `GetInboundBrokeredMessage()` returns `null` for any in-process command not received from a broker, and the resolver received that null with no guard. The only opt-out was the empty-batch guard at the write layer — which fires AFTER the resolver has already run. A realistic resolver that reads the inbound message NREs on the first non-brokered command; the suite only passed because the test resolver ignored its argument.

2. **One container app-wide.** Registration bound exactly one document container, one lease container, and one resolver for the whole application. An application with aggregates spread across multiple Cosmos containers (different partition keys, throughput, or TTL) could not model that. ADR-0007 constrains each atomic write to a single partition but says nothing about multiple containers — a genuine gap, not a documented non-goal.

The constraint that shapes any fix: opt-in CANNOT be expressed via selective DI registration (the pipeline forbids conditional/typed behavior registration). It must be implemented INSIDE the behavior's `Handle` as a fast pass-through for non-participants.

## Considered Options

- **Option 1 — global behavior + null-safe pass-through, single container.** Keep the behavior global; make the resolver null-safe so a null inbound message no longer NREs; leave the single container in place. Rejected: participation stays "everyone runs, opt-out is data" — complete-the-known-set, not class elimination — and the single-container gap is untouched. The next "this handler should not participate" or "this aggregate lives in another container" finding is the same shape with a different byte.
- **Option 2 — marker interface (`IWriteCosmosAggregate`) + single container.** A command implementing the marker participates. A genuine participation model, but it still binds one container app-wide, and it introduces a second source of truth (the marker AND the DI binding) for a fact the registry can carry alone. Rejected: single-container unaddressed; the participation idea is kept but realized via the registry, not a marker.
- **Option 3 — per-command container registry/factory (ACCEPTED).** A singleton registry keyed by command `Type` to a registration `{database, containerName, leaseName, resolver, partitionKeyPath}`. Participation IS having a registration; the registry is the positive allowlist. Container handles are derived and cached from the app-registered `CosmosClient` via `client.GetContainer(db, name)`. The behavior consults `registry.TryGet(typeof(TMessage))`; a miss is a bare pass-through.
- **Option 4 — handler-imperative enlistment / lazy batch open.** The handler decides at runtime whether to enlist and opens its own batch lazily. Rejected: regresses ADR-0006's framework-owns-batch-lifecycle re-decision (re-admits handler-owns-batch) and destroys the inbox-marker-before-`next()` ordering #220 depends on.

## Decision

Adopt Option 3.

**Participation = has a registration (registry-only).** A new singleton `DocumentReliabilityRegistry` maps command `Type` → `DocumentReliabilityRegistration`. The registry is a positive allowlist: a command type with a registration participates; a command type without one bypasses the document tier entirely. There is NO `IWriteCosmosAggregate` marker interface — the registry is the single source of truth. `DocumentTierBatchLifecycleBehavior<TMessage>.Handle` consults `registry.TryGet(typeof(TMessage), out var reg)`: a miss is a cheap dictionary lookup followed by a bare `await next()` — no resolver call, no container derivation, no batch.

**Multi-container via the registry.** Each registration carries `{database, containerName, leaseName, resolver, partitionKeyPath}`. Many command types MAY map to one container, but exactly ONE registration exists per command type; a duplicate registration for the same command type throws with a message naming the type. The selection axis is command `Type` → registration — the only axis that preserves ADR-0007's "the framework never sees domain types" (the command declares its registration; the framework maps type → container). It is NOT routing-key (which would read domain content) and NOT handler-imperative enlistment (Option 4).

**Container handles are derived and cached, never provisioned.** A new singleton `CosmosContainerFactory` resolves the app-registered `CosmosClient` singleton from DI (`GetRequiredService<CosmosClient>`, so a missing client fails loudly) and derives each `Container` via `client.GetContainer(database, containerName)`. Handles are cached in a thread-safe `ConcurrentDictionary` keyed by `(database, containerName)` — concurrent distinct in-flight command types resolve their containers without duplicate derivation or torn reads. The factory derives handles; it does NOT provision Cosmos resources — the application owns the `CosmosClient` lifecycle and the existence of the database/container/lease, a documented prerequisite. The provider registers no `CosmosClient`. The eager two-`Container`-instance overload is REMOVED; a per-registration `Func<IServiceProvider, Container>` factory overload is KEPT for applications that resolve their containers from the service provider themselves.

**Try/nullable resolver eliminates the null-inbound NRE.** The `ResolvePartitionKey` delegate becomes `PartitionKey? ResolvePartitionKey(InboundBrokeredMessage)` — a `null` return means "no resolvable partition for this message". The resolver is only ever invoked for registered participants, so a non-participant (including any in-process command) never reaches it. A participant whose resolver returns `null` is a bare `next()` (no batch opened). The null-inbound NRE for non-participants is therefore unrepresentable.

**Relationship to ADR-0006 and ADR-0007 (refined, not overturned).** ADR-0006's two-tier model, framework-owns-batch-lifecycle, and surface-ownership boundary are unchanged: the handle still lives on the document-tier reliability surface, not `TransactionContext.Container`. ADR-0007's single-aggregate / single-partition hard constraint is UNAFFECTED — each write is still single-partition. ADR-0007 gains a sibling note: MULTIPLE single-partition containers are now supported via the registry. The behavior preserves the empty-batch guard, the single `ExecuteAsync`, and the `InspectBatchResponse` / `CosmosBatchExecutionException` seam (#219) verbatim.

## Consequences

- **Participation is closed-by-construction.** A non-registered command CANNOT reach the resolver or open a batch — the positive allowlist makes the spurious-resolver-call and the no-opt-in classes unrepresentable, not merely unobserved. The discriminating question — what future finding does this make impossible? — is answered by an eliminated class: "command X should not participate" cannot recur because absence-of-registration IS non-participation.
- **The null-inbound NRE class is eliminated.** Resolvers run only for participants, and the Try/nullable contract gives a participant-without-a-partition a first-class no-op. There is no path on which a null inbound message reaches an unguarded resolver.
- **Multi-container is structural.** Container selection is by command type; the factory derives and caches per `(database, containerName)`. Cross-container leakage cannot occur because each command opens its batch on its own registration's container.
- **The application owns the client.** Deriving from the DI `CosmosClient` gives correct lifecycle ownership and removes the prior anti-pattern of passing `Container` instances into the builder. The provider provisions nothing.
- **Downstream consequences (NOT implemented here).** #220 (inbox dedup) becomes registry-gated — only participants stamp an inbox marker, read from the same registry as the outbox. #222 (relay) becomes a per-registration fan-out — one change-feed processor per registered document container, each with its own lease container from the registration's `leaseName`. #223 (emulator integration) adds multi-container atomicity, non-participant bypass, and the deferred #238 DI/registry-resolution tests. These are noted, not built, by this decision.
