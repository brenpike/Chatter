# Cosmos outbox co-resident in the aggregate container, drained by a discriminator-filtered change-feed relay

The NoSQL reliability tier (ADR 0006) must realize the transactional-outbox / atomic-writes pattern on Cosmos DB. Cosmos `TransactionalBatch` imposes hard physical constraints: all items in a batch must share one partition-key value; a batch is bounded at 100 operations, 2 MB, and 5 seconds. Cross-partition and cross-container batches are physically impossible.

## Considered Options

- **Outbox in its own container/table** — mirrors the EF provider's own `DbSet`. Rejected: a cross-container batch is impossible, so the aggregate write and the outbox write cannot be atomic.
- **(C1) Framework-owns-batch (original framing)** — the handler hands domain objects and a partition key to Chatter; Chatter serializes them, builds the batch, and executes it. Rejected: forces Chatter — a messaging library — to know how to serialize the application's domain aggregates and own the container. Wrong layer.
- **(C2) Handler-owns-batch, framework-contributes-outbox + co-resident outbox + change-feed relay** — originally accepted; superseded by the framework-owns-batch-lifecycle re-decision (see ADR-0006 Superseded sub-decision). Preserved here as an audit trail.
- **(C3) Framework-owns-batch-lifecycle, handler contributes aggregate ops + co-resident outbox + change-feed relay (ACCEPTED).**

## Decision

**Co-residency.** The Cosmos outbox document lives **inside** the application's aggregate container, in the **same logical partition** as the aggregate it accompanies. Chatter's Cosmos provider does not own a container; the application injects the container (and the change-feed lease container). Co-location of aggregate and outbox in one partition is structurally enforced because the outbox document is added to the framework-owned partition-scoped batch.

**Batch lifecycle (framework-owns-batch-lifecycle).** The outermost document-tier pipeline behavior — the Document-Tier Batch-Lifecycle Behavior, the document-tier sibling of `UnitOfWorkBehavior` — owns the batch lifecycle. It opens an empty `TransactionalBatch` on the message's resolved partition, stamps the inbox-marker create-op into the batch (framework-owned shape; no domain knowledge), then calls `next()`. The partition key is sourced via the app-registered partition-key resolver — an application-supplied delegate `(InboundBrokeredMessage) -> partition-key` — invoked by the behavior to open the batch on the correct partition; there is no core primitive carrying the partition key. The handler resolves the batch from the doc-tier atomic-write handle (the doc-tier sibling of `IPersistanceTransaction`, NOT a value stuffed into `TransactionContext.Container`) and contributes its own aggregate ops; the application owns aggregate serialization and partition selection, and the framework never sees domain types. `SendToOutbox` contributes the outbox-doc op to the same batch via the shared enqueue contract (abstracted over an Atomic-Write Handle — exact shape deferred to implementation). After `next()` returns, the behavior executes the batch once — this is the single commit point. The per-op `TransactionalBatchResponse` is inspected after execution: a 409 on the marker op is a *candidate* duplicate that is then CONFIRMED by point-reading the conflicting document (it is treated as a duplicate only when that doc is a genuine Chatter inbox marker for this message id — see the inbox-dedup bullet under Concurrency); because batch execution is all-or-nothing, no aggregate or outbox write commits on conflict. The 409 is detected at batch-execute time (after `next()`) — not via a pre-handler marker read — so there is no TOCTOU window and no sequencing gap in which a redelivery could escape dedup.

**Hard constraint.** Every atomic write in scope is single-aggregate / single-partition. A workflow needing to atomically mutate two aggregates in different partitions AND emit an event is physically impossible on Cosmos and is **out of scope** — that is a saga / process-manager concern (multiple single-partition steps), not the outbox.

**Outbox-doc shape.** Chatter owns this — it is the library value-add over hand-writing `.CreateItem(outboxMessage)`:

- A **Chatter-reserved discriminator field**, `_chatterType = "outbox"`. The discriminator lives under a namespaced, Chatter-reserved field name (not a generic top-level `type`) so it cannot collide with an application's own `type` field that may already carry an `outbox` value on a domain document. This is what lets the relay's filter (see Dispatch) select Chatter outbox documents by construction without ever matching a domain document.
- Document id `outbox:{encoded(MessageId)}`, where `encoded(...)` is a deterministic, Cosmos-id-safe encoding/hash of `OutboundBrokeredMessage.MessageId` (the raw `MessageId` may be caller-supplied and can contain characters Cosmos rejects in item ids — e.g. `/`, `?`, `#`). The original `OutboundBrokeredMessage.MessageId` is stored verbatim in a separate field as the event id; the encoded form is used only as the physical Cosmos item id.
- A `status` (or equivalent delivery-state) field, initialized to `pending` and advanced to `delivered` by the relay (see Dispatch).
- Carries the serialized `MessageContext`, message body, `Destination`, and content-type.
- A positive `ttl` is stamped when the relay marks the document `delivered`, so delivered documents self-expire. **Prerequisite**: post-delivery TTL purge requires the application's container to have TTL enabled (`defaultTtl` set on the container, e.g. `defaultTtl = -1`). This is a documented application prerequisite, not automatic — documents in a container without TTL enabled will not self-expire regardless of the `ttl` field value.

**Concurrency and idempotency.**

- Aggregate upsert carries `IfMatchEtag` — the ETag concurrency token lives on the document-tier reliability surface, not on the relational `TransactionContext`; a 412 on conflict is an application-level retry signal.
- The outbox `CreateItem` is a fresh document with no ETag.
- Inbox deduplication uses a **co-resident inbox marker** contributed by the Document-Tier Batch-Lifecycle Behavior to the framework-owned `TransactionalBatch` before `next()` is called. The marker enlistment happens via the document-tier reliability surface — not through `ReceiveViaInbox` / `InboxBehavior`, which are relational-only mechanics. The inbox contract (once-only dedup intent) is shared; the seam that implements it is provider-specific. The marker is co-resident: `partitionKey` equals the aggregate's partition value; `id` is `inbox:{encoded(MessageId)}` using the same Cosmos-id-safe encoding as the outbox id; the raw `MessageId` is stored verbatim in a separate field. A 409 create-conflict on the marker is detected by inspecting the per-op `TransactionalBatchResponse` after the framework-owned batch-execute (which runs after `next()` returns); the 409 is a *candidate* duplicate that the behavior then CONFIRMS by point-reading the conflicting document — it acks as a duplicate only when that doc is a genuine Chatter inbox marker (its `_chatterType` equals `inbox` AND its `MessageId` equals the inbound message id). Because batch execution is all-or-nothing, no aggregate write occurs and no outbox doc is written on the conflict; a confirmed duplicate is acked, while a 409 whose conflicting doc is NOT a confirmed marker (or cannot be read) is redelivered instead of swallowed. Dedup is closed-by-construction: the marker is a member of the framework-owned batch, and the Document-Tier Batch-Lifecycle Behavior adds the marker before `next()`, so the "marker cannot join a handler-internal batch" class of failure is eliminated. There is no window between marker persistence and aggregate/outbox persistence in which a redelivery could escape.
- **Handler-side-effect timing (consequence of the no-pre-read design).** The Document-Tier Batch-Lifecycle Behavior stamps the marker, calls `next()`, and only THEN executes the single batch, so the confirmed-duplicate marker-409 is detected AFTER `next()` has run. The once-only guarantee therefore splits: writes staged on the framework-owned batch (the aggregate write + co-resident outbox doc) roll back atomically on the marker-409 and never re-commit — **exactly-once** for batched writes; but handler side effects performed OUTSIDE the batch (external HTTP, non-Cosmos writes) have already executed by the time the duplicate is detected and re-execute on every redelivery — **at-least-once** for non-batched side effects. Handlers with non-batched side effects must therefore be idempotent. This is the deliberate cost of the no-pre-read / TOCTOU-free design and is the one place the two tiers' contracts differ: the relational tier (`BrokeredMessageInbox.ReceiveViaInbox`) reads `HasBeenReceived` first and skips the handler entirely on a known duplicate, so its non-batched side effects do not re-run; the document tier intentionally has no such pre-read (it would be the TOCTOU read this ADR eliminates) and so cannot offer that skip. This records the already-accepted design's consequence — it changes no decision.
- **Participant requires a non-empty `MessageId` (fail-loud).** The inbox marker is keyed on the message identity (`inbox:{encoded(MessageId)}`), so a participant that resolves a partition but arrives with a null/whitespace `MessageId` cannot be deduped — the once-only guarantee cannot be honored for it. Rather than silently proceed (stamp no marker, run the handler, commit aggregate + outbox, ack — which would leave a redelivery of the same identity-less message undetectable, a silent once-only loss), the Document-Tier Batch-Lifecycle Behavior FAILS LOUD: it throws `InvalidOperationException` BEFORE opening the batch, so nothing is staged, the handler never runs, and the message is not acked. A participant without a `MessageId` is a protocol/config error, matching the in-memory tier which throws. This records/strengthens the once-only contract and reverses no fixed architecture — co-residency, framework-owns-batch-lifecycle, and single-partition (ADR-0006/0007/0008) remain accepted and unchanged in substance.
- The inbox marker carries the same Chatter-reserved discriminator field with the value `_chatterType = "inbox"`. The change-feed relay's `_chatterType = "outbox"` filter predicate excludes inbox markers by construction — no relay-side inbox suppression logic is required.
- **Marker-409 soundness: CONFIRM the conflicting doc, do not INFER from the bare 409.** A bare marker-op 409 is NOT treated as a duplicate by inference. The application OWNS the container (it registers the `CosmosClient` the `CosmosContainerFactory` derives the container from, and the document-tier atomic-write handle exposes the raw `Container`), so an app can author a document with an `inbox:{encoded(MessageId)}` id through a non-staging path no staging guard can close — its create would 409 the framework's marker create. Inferring "duplicate" from that bare 409 would silently lose the colliding message's first delivery. To close that class by construction, the Document-Tier Batch-Lifecycle Behavior point-reads the conflicting marker on the 409 branch and treats it as a duplicate ONLY when the conflicting doc is a genuine Chatter inbox marker (its `_chatterType` discriminator equals `inbox` AND its `MessageId` equals the inbound message id); an app-authored reserved-prefix collision — or a doc that cannot be confirmed, including a NOT-FOUND read from a TTL/delete race or any other non-success read — is detected and redelivered, never swallowed. The point-read is cold-path-only (it runs solely on the 409 branch, never the hot path) and is NOT a TOCTOU: the atomic create already failed, so the read only disambiguates WHY and gates no subsequent write. The `inbox:`/`outbox:` reserved-namespace guard on the public atomic-write surface (`CosmosItemId.GuardNotReserved`) REMAINS as useful DEFENSE-IN-DEPTH (parity with the trusted `_chatterType` field), but it is NO LONGER the soundness basis — confirmation is. The framework's own reserved-id writes (the outbox doc and the inbox marker) still flow through an internal guard-bypassing reserved-write facet that is the sole sanctioned reserved-id writer. This changes ONLY the 409-interpretation; the co-residency, framework-owns-batch-lifecycle, and single-partition decisions (ADR-0006/0007/0008) remain fixed and UNCHANGED.
- Inbox markers are not given a post-delivery TTL. They persist for the dedup window. An app-configurable dedup-window TTL is a deferred design point.
- No datetime concurrency token (relational-only).

**Single-partition constraint for inbox dedup.** Atomic document-tier inbox dedup requires the incoming message to deterministically map to the single aggregate partition the handler writes — the same single-partition scope this ADR already accepts for aggregate-plus-outbox atomicity. Handlers whose message does not map to exactly one aggregate partition, or that write no aggregate, are outside the scope of document-tier once-only inbox dedup.

**Dispatch via change-feed relay.** A change-feed processor attached to the application's container drains outbox documents **filtered by the Chatter-reserved `_chatterType="outbox"` discriminator** and publishes them through the broker. The relay **must not** derive integration events from domain-document changes — only explicitly authored outbox documents are published. The relay (not a polling query) is the Cosmos dispatch mechanism; the Cosmos provider does **not** implement `IPollableOutboxStore`.

The Cosmos change feed emits **both inserts and updates** for an item, so the relay's own post-delivery write (advancing `status` to `delivered` and stamping `ttl`) re-surfaces the document on the feed. To preserve publish-once, the `_chatterType="outbox"` discriminator alone is **not** a sufficient relay predicate: the relay **must additionally skip any document already marked `delivered`** (equivalently, any document whose `ttl`/delivery marker is set). Only `pending` outbox documents are published; the delivered-state check guards against republishing a document on the change-feed event generated by its own delivery stamp.

**At-least-once relay semantics.** The change-feed relay is **at-least-once**: a publish can succeed and then the post-delivery `status`/`ttl` update can fail, causing the outbox document to be redelivered on the next change-feed pass. Downstream consumers **must** deduplicate; the document-tier inbox marker is the in-framework mechanism for this. Callers must not assume exactly-once delivery from the relay.

**Platform.** New module `Chatter.MessageBrokers.Reliability.Cosmos`, targeting `net8.0;net10.0`, depending on the Microsoft.Azure.Cosmos SDK v3 (`TransactionalBatch` + change-feed-processor API). Initial version `0.1.0`.

**Relay realized (#222).** The change-feed relay decided above is now implemented and changes no decision here. A hosted `ChangeFeedProcessor` runs one processor per distinct `(Database, ContainerName, LeaseName)` triple from the per-command registry (NOT one per command type — many command types may share one container, ADR-0008), with a stable per-triple `processorName` so all app instances sharing a lease cooperate and a unique per-host `instanceName`. The in-code filter selects exactly `_chatterType="outbox" && status="pending"`, skipping domain documents, inbox markers, already-`delivered` outbox documents (including the relay's own delivery-stamp event — publish-once by construction), and malformed outbox documents with a missing/empty status. A selected document is reconstructed into an `OutboundBrokeredMessage` (mirroring the relational `OutboxProcessor`) and published via `IMessagingInfrastructureProvider.GetDispatcher(infra).Dispatch(message, null)` — the no-reliability-re-entry path (NOT `IBrokeredMessageDispatcher`, which could route back through the outbox and recurse). On publish success the relay advances the document to `delivered` and stamps a positive `ttl` in a single `PatchItemAsync` (two set-ops) keyed on the document id and partition key; on publish failure it issues no patch and propagates the exception out of the change-feed handler so the SDK does not checkpoint the batch and the document re-surfaces next pass — realizing the at-least-once semantics already decided above (downstream consumers dedup via the #220 inbox marker). The container-`defaultTtl`-enabled prerequisite stands.

**Monitored container verified at host start.** The Outbox Relay no longer merely documents the monitored container's configuration — it reconciles the DECLARED configuration against the container's GROUND TRUTH once at host start, on BOTH hosts (the co-resident pipeline-integrated relay and the standalone relay), from a single `ReadContainerAsync` per monitored container. Three facts are rejected: a declared partition-key path that does not match the container's actual `PartitionKeyPaths`; a `defaultTtl` that is neither unset nor `-1`, because a *pending* Outbox Document carries no `ttl` field of its own and any purging value would delete it before the relay ever published it; and a partition key on a path the relay itself patches when it stamps a document `delivered` (`/status`, `/ttl`), which Cosmos refuses to patch, so no document on such a container could ever leave `pending`. Every check runs against that one read and a single throw names EVERY violation, and a violation FAILS HOST START rather than being merely documented — which supersedes the "documented application prerequisite, not automatic" framing above for exactly the facts the check covers. It supersedes no more than that: the check deliberately PERMITS an UNSET `defaultTtl`, so it rejects only a value that would purge a still-pending document and does NOT guarantee post-delivery self-purge — leaving TTL off remains a legitimate application choice whose no-purge consequence stays an application concern. **New authorization requirement.** Verification reads container metadata, which the relay never previously needed. An identity permitted to read the change feed and patch items but NOT to read container properties started the relay successfully before and now FAILS AT HOST START; such deployments must be granted metadata read on the monitored container. This changes no architectural decision — co-residency, framework-owns-batch-lifecycle, single-partition, and at-least-once relay semantics (ADR-0006/0007/0008) remain accepted and unchanged.

**The relay stops safely on a proven-undeliverable document and on a failing confirmation path (#361, #416).** Two mechanisms QUALIFY decisions made above; neither withdraws one, and they share no state and no control flow. The **Outbox Document Contract** is a TOTAL and PURE verification of one outbox document against the fields the reconstruction AND the publish read, evaluated over the document's OWN persisted bytes — and only on the verbatim no-resolver path, because a supplied `IOutboxBodyResolver` OWNS the message it publishes and the document's persisted fields need not be publishable at all. A document that violates it is stamped an **Undeliverable Outbox Document** instead of being published, which AMENDS the Outbox-doc shape decision above: `status` now carries a THIRD terminal value, `undeliverable`, alongside `pending` and `delivered`. The stamp is a single-op patch on `/status` with deliberately NO `/ttl` op — an Undeliverable Outbox Document is never TTL'd and never deleted, because it IS the evidence of the defect that produced it and has to outlive the drain for an operator to find. That is consistent under BOTH `defaultTtl` modes the monitored-container check above accepts: under `-1` and under unset alike, a document carrying no `ttl` field of its own never expires. The order is STAMP → EMIT → LOG, so a stamp blocked by an unavailable container throws before anything is counted or reported — the document stays `pending` and self-heals on the next pass instead of the relay reporting a give-up that did not happen.

**At-least-once relay semantics: QUALIFIED, not withdrawn.** A publish that succeeds and a delivered stamp that then fails STILL redelivers. Nothing is lost, nothing is checkpointed, and downstream dedup via the #220 document-tier inbox marker is unchanged. What changes is the RATE: redelivery is now rate-limited by Drain Suspension rather than occurring on every change-feed pass. Separately, a document the relay has PROVEN unpublishable is no longer redelivered at all — and that is NOT a weakening of at-least-once. At-least-once bounds deliveries of a message that CAN be published; for a document whose own persisted bytes prove it can never be reconstructed into an `OutboundBrokeredMessage`, no publish was ever possible, so there is no delivery the guarantee ever promised and none is withdrawn.

**#361 closed by construction — not "we now also handle it".** The class of finding ELIMINATED is: *an exception, from some source, elects a give-up*. No exception from any source can elect one. The give-up decision is a TOTAL function of the document's own persisted bytes, evaluated before any I/O and before any code this module does not own — the body converter, the broker publish call, `IMessagingInfrastructureProvider.GetDispatcher`, and an application-supplied `IOutboxBodyResolver` are all deliberately outside it — and a violation is derived only from what the document PROVES, never inferred from the absence of a disqualifier. That is the #414 defect eliminated, not handled. Because the function is total and pure over immutable input, a second evaluation is provably identical to the first: there is NO threshold, therefore no counter, therefore no key, no entry lifetime and no capacity. The four properties three prior review passes fixed in turn are not fixed here — they are UNREPRESENTABLE. A second class closes with it: *a reconstruction failure the relay did not classify*. It closes by SCOPE, not by counting the fields the verification checks: after `Verify` returns, the verbatim reconstruct-and-publish path holds NO `JsonElement` at all. `Reconstruct` takes only the `OutboxDocumentVerification` descriptor, and the dispatch takes the messaging system as an explicit parameter carried on that same descriptor. There is no sixth field to find because there is no document in scope to read one from. (An earlier framing of this class here asserted that reconstruction's single path *was* the classification. That was FALSE as shipped: the dispatch went on to read a fifth document-derived field — the messaging infrastructure the message context names — and hard-cast it, which is exactly the unclassified branch the framing claimed could not exist. The descriptor-only path above is the construction that makes the claim true.)

**The BOUNDARY of that classification is the positive rule, not the field list.** For the messaging infrastructure a message context names, only a NON-STRING persisted KIND is a violation — the document's own bytes prove that value can never be read as the string the publish resolves a dispatcher with. ABSENT, JSON-null and BLANK are deliberately NOT violations: each resolves to null, and what the infrastructure provider then answers for null is a HOST concern the positive rule excludes, because a redeploy or a registration fix repairs it on the very next pass. One non-casting reader backs both the read and the classification, so the two can never disagree about what the context carries. Separately, the STAMPING and ADDRESSING reads — the document's `id` and its partition key — sit OUTSIDE this class and are total: they feed the patch, never the message. The missing-`id` `InvalidOperationException` is unreachable for a Cosmos-sourced document, because Cosmos requires an `id` on every item; were it ever to occur it would be BOUNDED by Drain Suspension rather than classified, since a document the relay cannot address cannot be stamped undeliverable either.

**#416 closed by construction — not "we now also handle it".** The class of finding ELIMINATED is: *a fault on the confirmation half of the drain produces unbounded republishing*. **Drain Suspension** counts consecutive **Confirmation Failures** — a document that PUBLISHED and whose delivered stamp then failed — per **(Change-Feed Source Identity, Lease Token)**, and the host consults it BEFORE it drains a batch. The relay therefore stops publishing before it publishes, and the stop requires NO successful write to anything, which is precisely why the answer is not to mark the document: a give-up mark is a write to the very store whose writes are failing. The bound is arithmetic: at most `Threshold` (5) republishes per **(Change-Feed Source Identity, Lease Token)** to open a suspension, then at most ONE probe republish per Suspension Window (60 s) per that same pair, indefinitely. Every reset path — host restart, lease rebalance, entry eviction on a successful confirmation — costs at most another `Threshold` republishes and then re-opens; there is no state whose LOSS restores the unbounded storm. That eviction is GATED on a **Confirmation Receipt**: the gate lifts a suspension only on evidence that a status write LANDED, never on the drain having merely reached its end, because absence of a Confirmation Failure is not presence of a confirmation — an EMPTY batch and a batch every document's pending-outbox pre-gate rejected both reach loop-end having written nothing, and on a CO-RESIDENT monitored container the second is the ORDINARY batch. So *consecutive* is measured over confirmation OUTCOMES rather than batch ARRIVALS, and a batch that confirmed nothing is not an event the count sees. A receipt is derivable only from an object a status write returned, so a lift inferred from control-flow arrival is not expressible at any call site; and it is accumulated per BATCH and presented once, never per document, because a per-document lift would let a healthy document ordered before the wedging one evict the entry on every pass and void the arithmetic bound above rather than tighten it. Both stamps mint one ALIKE — the delivered stamp and the undeliverable give-up stamp are the same write on the same `/status` path — because what the suspension measures is whether that write path is up, not whether a publish happened. The two constants are non-configurable by construction: they are a safety bound, not a tuning parameter, and a bound that cannot be configured cannot be misconfigured into uselessness. No decision here is withdrawn by any of this: the arithmetic bound, the object scoping below, and the closed-by-construction claim all stand.

**Why that pair is OBJECT SCOPE and not a composite key.** ONE gate is built PER PROCESSOR, inside each host's `BuildChangeFeedHandler(descriptor)`, and reaches its change-feed handler only as a parameter of the closure that handler is; NEITHER host holds a gate field, so a host-shared gate is not expressible on either. That scoping is what makes the Lease Token a SUFFICIENT internal key: a gate never sees a token belonging to another Change-Feed Source Identity. A composite `(source, lease)` dictionary key was the alternative and is weaker — it would be *keyed correctly today*, not unrepresentable, because a later call site could still compute the wrong key and the key space would still span sources. Under object scoping there is no key space spanning sources at all, because no gate is reachable from more than one processor. The gate nonetheless takes its source identity as a REQUIRED construction argument — the identity-less overload is gone — because a measurement LEAVING the process carries no such scoping and must state it.

Worth recording as the mechanical finding behind this: a `LeaseToken` is a partition-key-range id of the processor's OWN monitored container, so two Change-Feed Source Identities co-resident on one host both emit lease `"0"`. Under the host-shared gate that shipped first, a healthy source's confirmation success EVICTED a failing source's consecutive count, so the failing source never reached the threshold and its republishing stayed unbounded — the exact defect #416 exists to close — and a suspension raised by one source cross-REFUSED the other, healthy, source's batches.

**Telemetry disambiguation, from the same fact.** The lease-token collision reaches this module's measurements too, so every LEASE-TAGGED instrument — `chatter.messaging.outbox.drain.batches`, `.drain.batch.size`, `.drain.failures` and `.drain.suspensions` — now also carries the **Change-Feed Source Identity** as `chatter.messaging.outbox.source_identity`, valued at the relay's processor name, and each emit takes it as a REQUIRED parameter with no lease-token-only overload. `chatter.messaging.outbox.drain.undeliverable` is deliberately EXCLUDED, by positive rule rather than by omission: it carries NO attribute at all, because one document can violate several contract facts at once and a single-valued tag may not claim one value for a heterogeneous set (ADR-0010 D7).

**Why CONSECUTIVE failures on one lease of one source, and not distinct document identities.** Because the relay is fail-closed it NEVER advances past the first failing document in a batch: batch [A, B, C] publishes A, fails to stamp A, throws, is not checkpointed, and re-surfaces as [A, B, C] forever — only A is ever seen. A distinctness requirement (which #416's own text suggested) would therefore never be satisfied in exactly the single-document case the mechanism exists for, and the suspension would never be raised. Consecutive failures on one Lease Token of one Change-Feed Source Identity is the only signal actually observable, and that pair is already the grain this module dimensions its lease-tagged drain instruments on.

**Nothing is stopped.** No `ChangeFeedProcessor` is stopped and no hosted service is stopped. A suspended lease simply DECLINES to publish and the host takes the module's EXISTING fail-closed exit — throw out of the change-feed handler, the SDK does not checkpoint, the batch re-surfaces. The question of whether a co-resident host may stop itself therefore dissolves rather than being answered.

**Where the two mechanisms meet — exactly two places.** A failed give-up stamp is a PRE-publish write and never feeds the Confirmation Failure count, which counts only a fault that follows a publish; its LANDING is a separate fact and does mint a Confirmation Receipt, so the two do not mirror each other — the count measures a fault after a publish, the receipt measures whether the write path is up. And Drain Suspension takes PRECEDENCE: the suspension check precedes the document loop, so a suspended lease evaluates no contracts and stamps nothing — which is correct, because under the broad write fault that opened the suspension the give-up stamp would fail anyway.

**Accepted residuals, both PRE-EXISTING; neither is introduced here.** A document whose APPLICATION-SUPPLIED `IOutboxBodyResolver` always throws still wedges its Lease Token — the module cannot prove an application delegate's fault permanent, and a resolver fault is a publish-side failure that raises no Confirmation Failure, so neither mechanism reaches it. And a document deleted between the change-feed read and the delivered stamp still replays until its change record ages out. Both are named consequences carried forward, not regressions of these mechanisms. This changes no architectural decision — co-residency, framework-owns-batch-lifecycle, single-partition, and the change-feed relay as the sole Cosmos dispatch mechanism (ADR-0006/0007/0008) remain accepted and unchanged.

## Consequences

- Atomic aggregate-plus-event write is achieved with a single `TransactionalBatch`.
- Chatter remains ignorant of application domain types and container ownership.
- Co-location of aggregate and outbox in one partition is enforced by construction, not by convention.
- The relay's discriminator filter encodes the "never derive events from the domain change feed" rule inside Chatter — it cannot be accidentally bypassed by a caller.
- Cross-partition atomic writes are an explicit non-goal (saga territory).
- The Cosmos Linux emulator is heavy and flaky in CI; this is a known integration-test risk, mitigated by the lighter vnext-preview emulator and docker-gating.
