# Chatter.MessageBrokers.AzureServiceBus.Auth — Characterization Findings

These are observations recorded while writing characterization (behavior-pinning) tests for `Chatter.MessageBrokers.AzureServiceBus.Auth`. The intent is a pure observation log: every row documents the **current** behavior of the code *as it exists today*, captured by a passing test. No production source was modified. Tests live under the module's `tests/` tree.

Each item below is flagged for human review only — no fix is prescribed or implied. Where current behavior looks suspicious, it is pinned exactly as-is so that any future change is caught by a failing test.

> **Reflection note.** `TokenProvider.Authority` has no public (or protected) property accessor in the shipped `Microsoft.Azure.ServiceBus` 5.2.0 assembly; the value is stored in a private field named `authority` declared directly on `AzureActiveDirectoryTokenProvider`. All authority assertions in the tests read this field via `System.Reflection`, walking the type hierarchy until the field is found. This technique is documented here so reviewers understand why the tests use reflection rather than a direct property access.

## Observations not directly assertable

- **`WithInteractive` naming vs. actual MSAL flow.** The callback body constructs a `ConfidentialClientApplicationBuilder` with `.WithRedirectUri(redirectUri)` and calls `AcquireTokenForClient` (the OAuth client-credentials grant), which is non-interactive. The method name `WithInteractive` is therefore misleading. This is **not directly assertable** in a characterization test because the callback is never awaited (awaiting would hit AAD/network). Documented as observation only; flagged for human review. Suggested follow-up: reconcile the method name with the actual MSAL flow, or switch to a genuine interactive (`AcquireTokenInteractive`) public-client flow.

## Deferred items (with rationale)

- **`GetCertificate` / cert-store path (`WithCert`).** Exercising the cert lookup requires a real `X509Store` and an installed certificate matching the thumbprint; on CI this would throw (or behave non-deterministically depending on the host cert store). Not pinned, to keep CI deterministic. `WithCert` is still characterized at the *construction* boundary (non-null provider, authority coercion, no callback invocation) — only the inner cert-store/AAD path is deferred.

- **Awaiting any of the three token callbacks (`GetTokenAsync` → `_tokenCallback`).** Awaiting would invoke MSAL and reach AAD/network (and, for `WithCert`, the cert store). Per the test constraints these callbacks are never awaited, so token-acquisition behavior (audience scope formatting `"{audience}/.default"`, token expiry computation in `AzureActiveDirectoryTokenProvider.GetTokenAsync`) is not pinned.

- **`ServiceBusOptionsBuilderExtensions` (`UseAadTokenProviderWithSecret` / `UseAadTokenProviderWithCert` / `UseAadTokenProviderInteractively`).** Characterizing these in isolation requires constructing a real `ServiceBusOptionsBuilder`. Its only constructor is `private` and its only factory, `ServiceBusOptionsBuilder.Create(IServiceCollection, IConfiguration)`, is `internal` to `Chatter.MessageBrokers.AzureServiceBus`, with no `InternalsVisibleTo` granting access to this test assembly. The only public construction path is `ServiceCollectionExtensions.AddServiceBus(...)`, which immediately calls `optionsBuilder.Build()` and performs full Service Bus registration — characterizing the extension methods through it would pin `AddServiceBus` behavior rather than the extension methods themselves, and couple this module's tests to the AzureServiceBus registration pipeline. Pinning these extension methods is therefore **deferred**: the task constraints forbid `InternalsVisibleTo` and any production-source change that would expose a construction seam. The following observations remain **un-pinned, documented for human review**:
  - All three extension methods return the same builder instance fluently (`return builder;`) — *not pinned* (no constructable builder).
  - `AddTokenProvider(Func<ITokenProvider>)` is invoked **eagerly** (`TokenProvider = tokenProviderFactory();` in `ServiceBusOptionsBuilder`), so the `Func<>` overload does not actually defer provider construction despite the deferring shape — *not pinned via the extension path* (observed by reading source only).
  - All three extension methods accept an `Action<DefaultAzureCredentialOptions> optBuilder` parameter that is **never forwarded or used** — `DefaultAzureCredential` customization supplied via this parameter is silently ignored — *not pinned* (no constructable builder).
