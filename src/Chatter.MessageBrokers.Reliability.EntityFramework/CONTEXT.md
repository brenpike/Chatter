# Chatter.MessageBrokers.Reliability.EntityFramework

EF Core persistence implementing the inbox/outbox reliability ports and unit-of-work for Chatter.MessageBrokers.

## Language

**Brokered Message Outbox**: EF-backed store of outgoing messages. `SendToOutbox` and both `UpdateProcessedDate` overloads only stage `OutboxMessage` rows into the EF context — neither saves. An enqueue is committed by the unit of work wrapping the handler, the same single commit that makes the Brokered Message Inbox claim durable. A drain's processed stamp is committed by the outbox's own `IUnitOfWork.ExecuteAsync` (`UnitOfWork<TContext>.CompleteAsync`), which commits its own transaction only when this unit of work began it — the ownership captured under Unit of Work — rather than merely because it runs after the handler's transaction has already committed. An enqueue outside any surrounding unit of work is staged, never persisted; the inbox diverges there, refusing to claim at all.

**Brokered Message Inbox**: EF-backed store of received message ids, which claims a message id before the handler runs. A marker the Inbox Deduplication Window has not aged out still skips the handler outright. Otherwise the claim — an insert for a fresh id, an in-place `ReceivedByInboxAtUtc` refresh for an expired one — is staged and flushed with `SaveChangesAsync` into `TContext`'s ambient transaction, and only then is the handler invoked, so two deliveries of one id are ordered by the store's own row lock rather than by a read both can pass. The flush is not a commit: the Unit of Work's single commit remains the only one, so claim and handler commit together or roll back together. Claiming when the context holds no transaction is refused with `InvalidOperationException`, since a flush with none autocommits and a failure between that autocommit and the handler's work would leave a marker suppressing a message nothing handled. A flush that fails detaches the entry and re-reads the marker by key as ground truth — a committed marker within the window means another delivery owns the id and the handler is skipped; anything else is rethrown. Decision: [ADR-0033](https://github.com/brenpike/Chatter/blob/master/docs/adr/0033-the-relational-inbox-claims-the-message-id-before-the-handler-inside-the-ambient-transaction.md).
_Avoid_: "stages only" / "never saves" / "closed by construction" / "commit capability denied" for `BrokeredMessageInbox<TContext>` — none holds: the type keeps a `TContext` field and calls `SaveChangesAsync` on it, so it does save. What it does not do is commit, and that is the distinction the oracles draw: `MustFlushTheClaimWithoutCommittingForAFreshMessageId` and `MustFlushTheRefreshedClaimWithoutCommittingForAnExpiredMessageId` count `TransactionCommitting` through `InboxCommitCountingTransactionInterceptor` at zero across a whole receive, then at one after an explicit commit, so the zero is not the vacuous zero of an interceptor nobody wired up. Nor is the in-transaction requirement structural — it is a runtime read of `_context.Database.CurrentTransaction`, pinned by `MustRefuseToClaimOutsideATransaction`, the only fact that reddens when that guard is removed.

**Unit of Work**: Coordinates a single atomic commit spanning domain state and inbox/outbox writes. Commit, rollback and dispose act only on a transaction this unit of work itself began; a transaction it adopted from a caller is participated in — `SaveChangesAsync` still flushes into it — but never committed, rolled back or disposed here, leaving it for its owner to complete. Boundary: a unit of work runs only under a non-retrying execution strategy, and it is the unit of work itself that says so — `ExecuteAsync` reads `RetriesOnFailure` and throws `InvalidOperationException` before the strategy runs and before any transaction is begun, so a `DbContext` configured with `EnableRetryOnFailure` is refused whether this unit of work would have begun its own transaction or adopted a caller's. Terminal cleanup — the rollback and the dispose on the failure path, the dispose on the success path — is guarded on both paths: each failure is logged at Warning and swallowed. On failure that keeps the exception which caused it the one reported; on success it keeps a faulting disposal from reporting failure for a commit that stood. The guard preserves the causal exception; it does not guarantee the transaction is closed, since a provider whose own disposal aborts still leaves it attached.
_Avoid_: "unrepresentable" / "capability denial" / "no commit-capable handle" / "closed by construction" for this ownership rule — none holds: `IUnitOfWork.CurrentTransaction` is still public and still hands out a commit-capable `IPersistanceTransaction`, and `BrokeredMessageOutbox<TContext>` re-exposes it, so a consumer can still commit on its own behalf through that surface. What changed is narrower: only the unit of work's own commit/rollback/dispose paths are now confined to a transaction they began, not the reachability of a commit-capable handle in general.

**Unit of Work Transaction**: The private handle `UnitOfWork<TContext>.BeginAsync` returns, pairing an `IPersistanceTransaction` with a `BegunHere` flag captured once at begin. Commit, rollback and dispose consult only that flag; they never re-derive ownership from the context's ambient transaction.

**Persistance Transaction**: The transaction abstraction wrapping the Unit of Work commit (note: spelled `Persistance` in code). Creation refuses a null transaction, and commit and rollback answer `ObjectDisposedException` once the handle has been disposed.

**No Active Transaction**: What `IUnitOfWork.CurrentTransaction` hands back when the context holds no transaction, so the absence of one is reported rather than dereferenced. Its `TransactionId` is `Guid.Empty`, disposing it is a no-op, and `CommitAsync` and `RollbackAsync` throw `InvalidOperationException`. It is never published into the `TransactionContext` container — only a live transaction is — so an application holding a transaction it took out of that container still holds a real one.

**Inbox Deduplication Window**: How long a relational inbox marker suppresses a redelivery of its message id, configured as `EntityFrameworkReliabilityOptions.InboxDeduplicationWindow`. DISABLED by default (`null`): with no window, every existing marker suppresses its id however old that marker is. Expiry is decided at receive — a marker older than the window is spent, so it is refreshed in place and flushed, and only then does the handler run, all within the same transaction — which is what makes the suppression period the window itself rather than the window plus the Retention Purge's cadence. A marker carrying no `ReceivedByInboxAtUtc` has no age to compare and never expires. The refresh does not race the Retention Purge, which is what the deferral tracked by [#507](https://github.com/brenpike/Chatter/issues/507) was about: the refresh is flushed ahead of the handler, so it holds the row's exclusive lock for the handler's whole duration. A purge pass firing during the handler blocks on that lock, re-evaluates its cutoff predicate once the handler's transaction has committed, finds the row freshly received, and skips it. The purge can therefore only decline to delete a row it would otherwise have deleted; it cannot invalidate a write the handler has already depended on. The disabled default is a deliberate divergence from the Message Brokers context's Deduplication Window, which is mandatory and at least one minute: that window is the in-memory store's only reclamation rule, whereas a persistent row is reclaimable by the Retention Purge as well, so a marker nothing has purged costs a row rather than leaves an entry nothing can remove.
_Avoid_: "purge-timed dedup" — the Retention Purge does not decide when an id stops being suppressed. `ReceiveViaInbox` decides that, at receive time; the purge only reclaims the row afterwards.

**Retention Purge**: The background pass that deletes inbox markers and processed outbox rows which have outlived their retention, configured through the single `WithReliabilityRetention<TContext>` door over both tables and run by `ReliabilityRetentionPurgeService<TContext>`. It is hygiene bounding table growth, not the deduplication rule. It takes its own scope each cycle, issues exactly one bounded `DELETE` per configured table per pass — at most a thousand rows, oldest first, the remainder left for the next pass — and waits `PurgeInterval`, five minutes by default, between passes; the service's only loop is `ExecuteAsync`'s, owned by the stopping token. A pass that throws is logged at Error and retried on the next one rather than faulting the host, since a `TContext` mapping neither entity must not take the host down. Every configured span is refused non-positive at registration. An inbox marker is eligible only once it carries a received timestamp, and an outbox row only once it carries a processed stamp, so a row still awaiting its drain is never deleted. Ceiling, disclosed not eliminated: a pass reclaims at most a thousand rows per table per `PurgeInterval` — 288,000 per table per day at the five-minute default — so a table accruing eligible rows faster than that is never drained, and `PurgeInterval` is the operator's dial on that rate. Pinned by `WhenPurgingRetentionOverSqlite.MustPurgeAnOutboxBacklogOneBoundedStatementPerPass` and `.MustPurgeAnInboxBacklogOneBoundedStatementPerPass`; the reasoning is in the `INVARIANT:` on `PurgeOnceAsync`. Residual: each outbox chunk can be served by the opt-in Outbox Poll Index, but `InboxMessageConfiguration` declares no index over `ReceivedByInboxAtUtc` and keys the table on `MessageId`, so the eligible markers are scattered and every inbox chunk scans. An opt-in inbox index is the companion to the Outbox Poll Index and does not exist yet.

**Outbox Attempt State**: The durable `OutboxMessage.DispatchAttempts` / `OutboxMessage.NextAttemptAtUtc` pair `OutboxMessageConfiguration` maps — the count required with a store default of `0`, the instant nullable — which makes relational outbox selection *unprocessed AND due* rather than merely unprocessed. `GetUnprocessedMessagesFromOutbox` filters `ProcessedFromOutboxAtUtc == null && (NextAttemptAtUtc == null || NextAttemptAtUtc <= now)`, adds `DispatchAttempts < OutboxMaxDispatchAttempts` only when that option carries a value, and applies both clauses ahead of the ordering and the take. Null is the due-now value, so a row staged before these columns existed is taken by a poll rather than held back. `RecordDispatchAttempt` spends one attempt and advances the instant through a single `ExecuteUpdateAsync` keyed on the message's own `Id`, outside the change tracker; `ProcessedFromOutboxAtUtc` stays the sole concurrency token. `GetUnprocessedBatch` carries neither clause. The schema change is additive and needs no backfill — see the README's Migration section. Decision: [ADR-0031](https://github.com/brenpike/Chatter/blob/master/docs/adr/0031-outbox-selection-is-derived-from-durable-attempt-state-not-from-the-absence-of-success.md). Pinned by `WhenGettingUnprocessedMessages.MustSpendNoBatchSlotOnAMessageThatIsNotDue`, `.MustSpendNoBatchSlotOnAMessageThatHasSpentTheAttemptCeiling`, `.MustTranslateTheDueGateAndTheCeilingToSqlOverARelationalProvider`, `.MustDueGateWithoutReliabilityOptions`, `.MustNeitherDueGateNorCeilingTheUnprocessedBatch`, `WhenUpdatingProcessed.MustCountOneMoreDispatchAttemptOnTheStoredRow`, `.MustRecordTheAttemptAfterAFailedClaimLeftTheMessageStagedAsProcessed`, `.MustRecordTheAttemptOnlyOnTheMessageItWasHanded`, `WhenConfiguring.MustGiveDispatchAttemptsAStoreDefaultOfZero`, `.MustAllowNextAttemptToBeNullable` and `.MustTreatProcessedDateAsTheOnlyConcurrencyToken`; the reasoning is in the `INVARIANT:` comments on `GetUnprocessedMessagesFromOutbox`, `RecordDispatchAttempt` and `OutboxMessageConfiguration.Configure`.

**Outbox Poll Index**: The opt-in index over `ProcessedFromOutboxAtUtc` then `SentToOutboxAtUtc`, shipped as `OutboxMessagePollIndexConfiguration` separately from `OutboxMessageConfiguration` so that applying it — and owning the migration it generates — is the application's decision rather than a model change made on its behalf. The leading column is the one both unprocessed polls filter on; the second follows it because a drain works the oldest staged message first. It is neither filtered nor unique, so it stays provider-neutral. It indexes neither column of the Outbox Attempt State: extending it to lead with `NextAttemptAtUtc` would force a second migration on an application that has already applied it, so that shape is carried by [#381](https://github.com/brenpike/Chatter/issues/381) instead.

## Relationships

- Implements the Outbox and Inbox persistence ports defined in the Message Brokers context, replacing their in-memory defaults.
- All types are generic over the consumer's own `DbContext` (`TContext : DbContext`) — no separate Chatter context; entity configs are applied in the consumer's `OnModelCreating`.
- Wired through the Command Pipeline as behaviors (`WithInboxBehavior<TContext>()`, `WithOutboxProcessingBehavior<TContext>()`, `WithUnitOfWorkBehavior<TContext>()`), not a standalone DI registration; `WithReliabilityRetention<TContext>(...)` is a fourth entry point on the same builder that adds no behavior. All four must name one `TContext`: the first call to arrive binds it, a later call naming the same one is a no-op, and a later call naming a different one throws `InvalidOperationException` at registration naming both contexts. A refused call leaves the service collection exactly as it found it, slot for slot, wherever within the entry point the refusal is raised: each entry point stages every registration it makes onto a scratch `IServiceCollection` and reaches the caller's own only through a commit phase containing no fallible operation. Pinned by `WhenBindingReliabilityContext.MustLeaveTheServiceCollectionExactlyAsItWasWhenAnyRefusalIsRaised`, a sweep over every public `TContext`-parameterized entry point crossed with every refusal that entry point can raise; the reasoning is in the `INVARIANT:` on `StageReliabilityRegistrations` and the decision in [ADR-0032](https://github.com/brenpike/Chatter/blob/master/docs/adr/0032-the-reliability-registration-door-stages-its-mutations-so-a-refusal-cannot-be-observed.md). Residual: a collection the host has made read-only refuses the commit's write, as it refused the registration before staging existed, and no test pins that.
- The Unit of Work commits domain changes together with Outbox/Inbox writes via a Persistance Transaction (`IPersistanceTransaction`).
- Outbox processing wraps the Unit of Work, which wraps the Inbox — this order is package-guaranteed, not derived from the order the pipeline extension methods are called in. The guarantee covers only descriptors registered through `WithUnitOfWorkBehavior<TContext>()`, `WithInboxBehavior<TContext>()`, and `WithOutboxProcessingBehavior<TContext>()`; later direct `WithBehavior` calls, and closed-generic, factory, keyed, or decorated registrations of these behavior types, are outside normalization.

## Example dialogue

> **Dev:** "How do I guarantee the message publishes only if my DB write succeeds?"
> **Domain expert:** "Write to the Brokered Message Outbox inside the same Unit of Work as your aggregate; the Persistance Transaction commits both or neither."
