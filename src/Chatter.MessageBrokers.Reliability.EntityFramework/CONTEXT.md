# Chatter.MessageBrokers.Reliability.EntityFramework

EF Core persistence implementing the inbox/outbox reliability ports and unit-of-work for Chatter.MessageBrokers.

## Language

**Brokered Message Outbox**: EF-backed store of outgoing messages. `SendToOutbox` and both `UpdateProcessedDate` overloads only stage `OutboxMessage` rows into the EF context — neither saves. An enqueue is committed by the unit of work wrapping the handler, the same single `SaveChangesAsync` that commits the Brokered Message Inbox marker. A drain's processed stamp is committed by the outbox's own `IUnitOfWork.ExecuteAsync` (`UnitOfWork<TContext>.CompleteAsync`), which commits its own transaction only when this unit of work began it — the ownership captured under Unit of Work — rather than merely because it runs after the handler's transaction has already committed. An enqueue outside any surrounding unit of work is staged, never persisted — symmetric with the inbox.

**Brokered Message Inbox**: EF-backed store of received message ids enforcing once-only, idempotent handling.
_Avoid_: "closed by construction" / "commit capability denied" for `BrokeredMessageInbox<TContext>`'s `DbSet<InboxMessage>` field — it does not: the reflection guard (`MustNotDeclareADbContextField`) denies a declared `DbContext` field, not the commit capability itself; EF's `DbSet<T>` declares `IInfrastructure<IServiceProvider>`, the runtime `InternalDbSet<T>` implements `IInfrastructure<DbContext>` and holds a private `DbContext` field, and `SaveChangesAsync` is reachable through that handle with no reflection and no internal-type cast.

**Unit of Work**: Coordinates a single atomic commit spanning domain state and inbox/outbox writes. Commit, rollback and dispose act only on a transaction this unit of work itself began; a transaction it adopted from a caller is participated in — `SaveChangesAsync` still flushes into it — but never committed, rolled back or disposed here, leaving it for its owner to complete. Boundary: a unit of work runs only under a non-retrying execution strategy, and it is the unit of work itself that says so — `ExecuteAsync` reads `RetriesOnFailure` and throws `InvalidOperationException` before the strategy runs and before any transaction is begun, so a `DbContext` configured with `EnableRetryOnFailure` is refused whether this unit of work would have begun its own transaction or adopted a caller's. Terminal cleanup — the rollback and the dispose on the failure path, the dispose on the success path — is guarded on both paths: each failure is logged at Warning and swallowed. On failure that keeps the exception which caused it the one reported; on success it keeps a faulting disposal from reporting failure for a commit that stood. The guard preserves the causal exception; it does not guarantee the transaction is closed, since a provider whose own disposal aborts still leaves it attached.
_Avoid_: "unrepresentable" / "capability denial" / "no commit-capable handle" / "closed by construction" for this ownership rule — none holds: `IUnitOfWork.CurrentTransaction` is still public and still hands out a commit-capable `IPersistanceTransaction`, and `BrokeredMessageOutbox<TContext>` re-exposes it, so a consumer can still commit on its own behalf through that surface. What changed is narrower: only the unit of work's own commit/rollback/dispose paths are now confined to a transaction they began, not the reachability of a commit-capable handle in general.

**Unit of Work Transaction**: The private handle `UnitOfWork<TContext>.BeginAsync` returns, pairing an `IPersistanceTransaction` with a `BegunHere` flag captured once at begin. Commit, rollback and dispose consult only that flag; they never re-derive ownership from the context's ambient transaction.

**Persistance Transaction**: The transaction abstraction wrapping the Unit of Work commit (note: spelled `Persistance` in code). Creation refuses a null transaction, and commit and rollback answer `ObjectDisposedException` once the handle has been disposed.

**No Active Transaction**: What `IUnitOfWork.CurrentTransaction` hands back when the context holds no transaction, so the absence of one is reported rather than dereferenced. Its `TransactionId` is `Guid.Empty`, disposing it is a no-op, and `CommitAsync` and `RollbackAsync` throw `InvalidOperationException`. It is never published into the `TransactionContext` container — only a live transaction is — so an application holding a transaction it took out of that container still holds a real one.

**Inbox Deduplication Window**: How long a relational inbox marker suppresses a redelivery of its message id, configured as `EntityFrameworkReliabilityOptions.InboxDeduplicationWindow`. DISABLED by default (`null`): with no window, every existing marker suppresses its id however old that marker is. Expiry is decided at receive — a marker older than the window is spent, so the handler runs and the marker is refreshed in place within the same transaction — which is what makes the suppression period the window itself rather than the window plus the Retention Purge's cadence. A marker carrying no `ReceivedByInboxAtUtc` has no age to compare and never expires. The disabled default is a deliberate divergence from the Message Brokers context's Deduplication Window, which is mandatory and at least one minute: that window is the in-memory store's only reclamation rule, whereas a persistent row is reclaimable by the Retention Purge as well, so a marker nothing has purged costs a row rather than leaves an entry nothing can remove. Deduplication covers redelivery, not concurrency: two deliveries racing on the same expired id can both run the handler.
_Avoid_: "purge-timed dedup" — the Retention Purge does not decide when an id stops being suppressed. `ReceiveViaInbox` decides that, at receive time; the purge only reclaims the row afterwards.

**Retention Purge**: The background pass that deletes inbox markers and processed outbox rows which have outlived their retention, configured through the single `WithReliabilityRetention<TContext>` door over both tables and run by `ReliabilityRetentionPurgeService<TContext>`. It is hygiene bounding table growth, not the deduplication rule. It takes its own scope each cycle, deletes in chunks — at most a thousand rows per `DELETE`, oldest first, until a chunk comes back short — so a first pass over a table that has accumulated for months issues many bounded statements rather than one unbounded one that would escalate to a lock on the table the durability path writes through, and waits `PurgeInterval` — five minutes by default — between passes; a pass that throws is logged at Error and retried on the next one rather than faulting the host, since a `TContext` mapping neither entity must not take the host down. Every configured span is refused non-positive at registration. An inbox marker is eligible only once it carries a received timestamp, and an outbox row only once it carries a processed stamp, so a row still awaiting its drain is never deleted. Residual: each outbox chunk can be served by the opt-in Outbox Poll Index, but `InboxMessageConfiguration` declares no index over `ReceivedByInboxAtUtc` and keys the table on `MessageId`, so the eligible markers are scattered and every inbox chunk scans. An opt-in inbox index is the companion to the Outbox Poll Index and does not exist yet.

**Outbox Poll Index**: The opt-in index over `ProcessedFromOutboxAtUtc` then `SentToOutboxAtUtc`, shipped as `OutboxMessagePollIndexConfiguration` separately from `OutboxMessageConfiguration` so that applying it — and owning the migration it generates — is the application's decision rather than a model change made on its behalf. The leading column is the one both unprocessed polls filter on; the second follows it because a drain works the oldest staged message first. It is neither filtered nor unique, so it stays provider-neutral.

## Relationships

- Implements the Outbox and Inbox persistence ports defined in the Message Brokers context, replacing their in-memory defaults.
- All types are generic over the consumer's own `DbContext` (`TContext : DbContext`) — no separate Chatter context; entity configs are applied in the consumer's `OnModelCreating`.
- Wired through the Command Pipeline as behaviors (`WithInboxBehavior<TContext>()`, `WithOutboxProcessingBehavior<TContext>()`, `WithUnitOfWorkBehavior<TContext>()`), not a standalone DI registration; `WithReliabilityRetention<TContext>(...)` is a fourth entry point on the same builder that adds no behavior. All four must name one `TContext`: the first call to arrive binds it, a later call naming the same one is a no-op, and a later call naming a different one throws `InvalidOperationException` at registration naming both contexts. Because each entry point binds before it registers anything, a refused call leaves the service collection exactly as it found it.
- The Unit of Work commits domain changes together with Outbox/Inbox writes via a Persistance Transaction (`IPersistanceTransaction`).
- Outbox processing wraps the Unit of Work, which wraps the Inbox — this order is package-guaranteed, not derived from the order the pipeline extension methods are called in. The guarantee covers only descriptors registered through `WithUnitOfWorkBehavior<TContext>()`, `WithInboxBehavior<TContext>()`, and `WithOutboxProcessingBehavior<TContext>()`; later direct `WithBehavior` calls, and closed-generic, factory, keyed, or decorated registrations of these behavior types, are outside normalization.

## Example dialogue

> **Dev:** "How do I guarantee the message publishes only if my DB write succeeds?"
> **Domain expert:** "Write to the Brokered Message Outbox inside the same Unit of Work as your aggregate; the Persistance Transaction commits both or neither."

- **Persistance** is misspelled in the codebase; keep the spelling when referencing the type, use _persistence_ in prose.
