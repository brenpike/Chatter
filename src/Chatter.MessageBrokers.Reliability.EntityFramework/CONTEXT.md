# Chatter.MessageBrokers.Reliability.EntityFramework

EF Core persistence implementing the inbox/outbox reliability ports and unit-of-work for Chatter.MessageBrokers.

## Language

**Brokered Message Outbox**: EF-backed store of outgoing messages. `SendToOutbox` and both `UpdateProcessedDate` overloads only stage `OutboxMessage` rows into the EF context — neither saves. An enqueue is committed by the unit of work wrapping the handler, the same single `SaveChangesAsync` that commits the Brokered Message Inbox marker. A drain's processed stamp is committed by the outbox's own `IUnitOfWork.ExecuteAsync` (`UnitOfWork<TContext>.CompleteAsync`), which commits its own transaction only when this unit of work began it — the ownership captured under Unit of Work — rather than merely because it runs after the handler's transaction has already committed. An enqueue outside any surrounding unit of work is staged, never persisted — symmetric with the inbox.

**Brokered Message Inbox**: EF-backed store of received message ids enforcing once-only, idempotent handling. The row states which of two states its message id is in: `ReceivedByInboxAtUtc` null records a CLAIM whose handler has not completed, a timestamp records a handler that completed at that instant, and no row records a fresh id. `ReceiveViaInbox` flushes the claim into `TContext`'s ambient transaction before invoking the handler — inserting a fresh row or re-claiming an existing one in place, since `MessageId` is the primary key — and flushes the handled stamp after the handler returns. The claim's flush takes the row's lock, which is what orders a concurrent delivery of the same id behind it. It FLUSHES but never COMMITS, leaving the unit of work's single commit as the only one, and it refuses with `InvalidOperationException` when the context holds no transaction, because that flush would otherwise commit on its own and leave a claim standing outside the unit of work meant to carry it. A caller who swallows the handler's failure commits a claim carrying no stamp, which the next delivery reads as unhandled. `HasBeenReceived` answers for the HANDLER rather than for the row, so a claim carrying no stamp reports not-received under either setting of the Inbox Deduplication Window. `InboxMessageConfiguration` maps `ReceivedByInboxAtUtc` `IsConcurrencyToken()` — an annotation on the model, not a column. Decision: [ADR-0033](https://github.com/brenpike/Chatter/blob/master/docs/adr/0033-the-relational-inbox-claims-before-the-handler-and-stamps-handled-after-it-in-the-same-row.md). Pinned by `WhenReceivingViaInbox.MustFlushAClaimCarryingNoTimestampBeforeInvokingTheHandler`, `.MustFlushTheStampWhenTheHandlerReturnsAndCommitIt`, `.MustCommitAnUnstampedClaimWhenACallerSwallowsTheHandlersFailure` and `.MustRefuseToClaimOutsideATransaction`, and over a real database by `Integration/WhenDeduplicatingInboxOnSqlServer.MustMakeASecondDeliverysClaimWaitOnTheFirstsRowLock`; the reasoning is in the `INVARIANT:` comments on `ReceiveViaInbox` and `ClaimMessageIdAsync`.
_Avoid_: "closed by construction" / "commit capability denied" for `BrokeredMessageInbox<TContext>`'s flush-never-commit rule — nothing denies the capability: the type declares a `TContext` field and calls `SaveChangesAsync` on it twice, so a commit is one further call on a handle it already holds. What holds the rule is a fact that counts commits rather than a shape that forbids a field — `WhenReceivingViaInbox.MustFlushTheClaimWithoutCommittingIt`, which counts through an `IDbTransactionInterceptor` and goes red when this type commits the ambient transaction itself.

**Unit of Work**: Coordinates a single atomic commit spanning domain state and inbox/outbox writes. Commit, rollback and dispose act only on a transaction this unit of work itself began; a transaction it adopted from a caller is participated in — `SaveChangesAsync` still flushes into it — but never committed, rolled back or disposed here, leaving it for its owner to complete. Rolling back a transaction it began also clears `TContext`'s change tracker, because EF accepts changes when it saves rather than when it commits, so the entities a failed attempt flushed would otherwise stay tracked as though the write had landed and be resolved out of the identity map ahead of the store. The same ownership rule scopes that: where the transaction was adopted, the tracker is left as it was found, since the caller owns the state staged into it. The success path is untouched. Decision: [ADR-0034](https://github.com/brenpike/Chatter/blob/master/docs/adr/0034-a-rolled-back-unit-of-work-reconciles-its-contexts-change-tracker.md). Pinned by `WhenExecutingUnitOfWorkOverSqlite.MustLeaveNoTrackedChangesWhenAUnitOfWorkItBeganRollsBack` and `.MustLeaveTheCallersTrackedChangesAloneWhenTheCallerBeganTheTransaction`. Boundary: a unit of work runs only under a non-retrying execution strategy, and it is the unit of work itself that says so — `ExecuteAsync` reads `RetriesOnFailure` and throws `InvalidOperationException` before the strategy runs and before any transaction is begun, so a `DbContext` configured with `EnableRetryOnFailure` is refused whether this unit of work would have begun its own transaction or adopted a caller's. Terminal cleanup — the rollback and the dispose on the failure path, the dispose on the success path — is guarded on both paths: each failure is logged at Warning and swallowed. On failure that keeps the exception which caused it the one reported; on success it keeps a faulting disposal from reporting failure for a commit that stood. The guard preserves the causal exception; it does not guarantee the transaction is closed, since a provider whose own disposal aborts still leaves it attached.
_Avoid_: "unrepresentable" / "capability denial" / "no commit-capable handle" / "closed by construction" for this ownership rule — none holds: `IUnitOfWork.CurrentTransaction` is still public and still hands out a commit-capable `IPersistanceTransaction`, and `BrokeredMessageOutbox<TContext>` re-exposes it, so a consumer can still commit on its own behalf through that surface. What changed is narrower: only the unit of work's own commit/rollback/dispose paths are now confined to a transaction they began, not the reachability of a commit-capable handle in general.

**Unit of Work Transaction**: The private handle `UnitOfWork<TContext>.BeginAsync` returns, pairing an `IPersistanceTransaction` with a `BegunHere` flag captured once at begin. Commit, rollback and dispose consult only that flag; they never re-derive ownership from the context's ambient transaction.

**Persistance Transaction**: The transaction abstraction wrapping the Unit of Work commit (note: spelled `Persistance` in code). Creation refuses a null transaction, and commit and rollback answer `ObjectDisposedException` once the handle has been disposed.

**No Active Transaction**: What `IUnitOfWork.CurrentTransaction` hands back when the context holds no transaction, so the absence of one is reported rather than dereferenced. Its `TransactionId` is `Guid.Empty`, disposing it is a no-op, and `CommitAsync` and `RollbackAsync` throw `InvalidOperationException`. It is never published into the `TransactionContext` container — only a live transaction is — so an application holding a transaction it took out of that container still holds a real one.

**Inbox Deduplication Window**: How long a relational inbox marker suppresses a redelivery of its message id, configured as `EntityFrameworkReliabilityOptions.InboxDeduplicationWindow`. DISABLED by default (`null`): with no window, every existing marker suppresses its id however old that marker is. Expiry is decided at receive — a marker older than the window is spent, so the marker is re-claimed in place, the handler runs, and the stamp is rewritten, all within the same transaction — which is what makes the suppression period the window itself rather than the window plus the Retention Purge's cadence. A marker carrying no `ReceivedByInboxAtUtc` records a claim rather than a handled message, so it never suppresses and the window has no age to compare it against. The disabled default is a deliberate divergence from the Message Brokers context's Deduplication Window, which is mandatory and at least one minute: that window is the in-memory store's only reclamation rule, whereas a persistent row is reclaimable by the Retention Purge as well, so a marker nothing has purged costs a row rather than leaves an entry nothing can remove. Two deliveries racing on the same expired id are ordered by the re-claim's row lock rather than by the window: one of them re-claims the row and the other waits on that lock, pinned over a real database by `Integration/WhenDeduplicatingInboxOnSqlServer.MustInvokeTheHandlerOnceWhenTwoRedeliveriesRaceAnExpiredMarker`.
_Avoid_: "purge-timed dedup" — the Retention Purge does not decide when an id stops being suppressed. `ReceiveViaInbox` decides that, at receive time; the purge only reclaims the row afterwards.

**Retention Purge**: The background pass that deletes inbox markers and processed outbox rows which have outlived their retention, configured through the single `WithReliabilityRetention<TContext>` door over both tables and run by `ReliabilityRetentionPurgeService<TContext>`. It is hygiene bounding table growth, not the deduplication rule. It takes its own scope each cycle, issues exactly one bounded `DELETE` per configured table per pass — at most a thousand rows, oldest first, the remainder left for the next pass — and waits `PurgeInterval`, five minutes by default, between passes; the service's only loop is `ExecuteAsync`'s, owned by the stopping token. A pass that throws is logged at Error and retried on the next one rather than faulting the host, since a `TContext` mapping neither entity must not take the host down. Every configured span is refused non-positive at registration. An outbox row is eligible only once it carries a processed stamp, so a row still awaiting its drain is never deleted. An inbox marker reads the other way: one carrying no received timestamp records a claim no handler completed, and since no cutoff on a null column would ever age it out, the purge takes it alongside the markers past their cutoff. Pinned by `WhenPurgingRetentionOverSqlite.MustPurgeAnInboxMarkerClaimedButNeverHandledWhileSparingAFreshOne` and `Integration/WhenPurgingRetentionOnSqlServer.MustPurgeAnInboxMarkerClaimedButNeverHandled`. Ceiling, disclosed not eliminated: a pass reclaims at most a thousand rows per table per `PurgeInterval` — 288,000 per table per day at the five-minute default — so a table accruing eligible rows faster than that is never drained, and `PurgeInterval` is the operator's dial on that rate. Pinned by `WhenPurgingRetentionOverSqlite.MustPurgeAnOutboxBacklogOneBoundedStatementPerPass` and `.MustPurgeAnInboxBacklogOneBoundedStatementPerPass`; the reasoning is in the `INVARIANT:` on `PurgeOnceAsync`. Residual: each outbox chunk can be served by the opt-in Outbox Poll Index, but `InboxMessageConfiguration` declares no index over `ReceivedByInboxAtUtc` and keys the table on `MessageId`, so the eligible markers are scattered and every inbox chunk scans.

**Outbox Attempt State**: The durable `OutboxMessage.DispatchAttempts` / `OutboxMessage.NextAttemptAtUtc` pair `OutboxMessageConfiguration` maps — the count required with a store default of `0`, the instant nullable — which makes relational outbox selection *unprocessed AND due* rather than merely unprocessed. `GetUnprocessedMessagesFromOutbox` filters `ProcessedFromOutboxAtUtc == null && (NextAttemptAtUtc == null || NextAttemptAtUtc <= now)`, adds `DispatchAttempts < OutboxMaxDispatchAttempts` only when that option carries a value, and applies both clauses ahead of the ordering and the take. Null is the due-now value, so a row staged before these columns existed is taken by a poll rather than held back. `RecordDispatchAttempt` spends one attempt and advances the instant through a single `ExecuteUpdateAsync` keyed on the message's own `Id`, outside the change tracker; `ProcessedFromOutboxAtUtc` stays the sole concurrency token. `GetUnprocessedBatch` carries neither clause. The schema change is additive and needs no backfill — see the README's Migration section. Decision: [ADR-0031](https://github.com/brenpike/Chatter/blob/master/docs/adr/0031-outbox-selection-is-derived-from-durable-attempt-state-not-from-the-absence-of-success.md). Pinned by `WhenGettingUnprocessedMessages.MustSpendNoBatchSlotOnAMessageThatIsNotDue`, `.MustSpendNoBatchSlotOnAMessageThatHasSpentTheAttemptCeiling`, `.MustTranslateTheDueGateAndTheCeilingToSqlOverARelationalProvider`, `.MustDueGateWithoutReliabilityOptions`, `.MustNeitherDueGateNorCeilingTheUnprocessedBatch`, `WhenUpdatingProcessed.MustCountOneMoreDispatchAttemptOnTheStoredRow`, `.MustRecordTheAttemptAfterAFailedClaimLeftTheMessageStagedAsProcessed`, `.MustRecordTheAttemptOnlyOnTheMessageItWasHanded`, `WhenConfiguring.MustGiveDispatchAttemptsAStoreDefaultOfZero`, `.MustAllowNextAttemptToBeNullable` and `.MustTreatProcessedDateAsTheOnlyConcurrencyToken`; the reasoning is in the `INVARIANT:` comments on `GetUnprocessedMessagesFromOutbox`, `RecordDispatchAttempt` and `OutboxMessageConfiguration.Configure`.

**Relational Drain Claim**: How `BrokeredMessageOutbox<TContext>` realizes the Message Brokers context's Drain Claim. That context defines the term and states how it differs from the claim the processed stamp carries; neither is restated here. `TryClaimForDispatch` is ONE `ExecuteUpdateAsync` compare-and-set — `Id == the message's own && ProcessedFromOutboxAtUtc == null && NextAttemptAtUtc == the instant the poll observed`, setting `NextAttemptAtUtc` one backoff ahead — which also writes the granted instant back onto the supplied message, because the statement bypasses the change tracker. It neither opens a transaction nor saves: it enlists in whatever transaction the caller has open, and `OutboxProcessor` takes it as the first statement inside the drain's unit of work, so the claim is TRANSACTION-SCOPED — invisible to every other connection until that unit of work commits, discarded by its rollback. That is what makes the arbitration real here rather than advisory: a second host's drain blocks on the row's lock for the winner's whole publish and then matches zero rows, so the relational transaction genuinely ENFORCES which drain publishes — the one place in this package where that word is honest. What it replaced: the poll ran, and still runs, outside any transaction, and both drain queries are plain lock-free reads at ReadCommitted, which left `ProcessedFromOutboxAtUtc`'s concurrency token as the only arbiter — and that predicate is emitted at `SaveChanges`, AFTER the publish, so it prevented a double CLAIM and never a double DISPATCH. NO schema change: the claim rides the `NextAttemptAtUtc` column Outbox Attempt State already maps, so no property, mapping or annotation moves, and this package ships no migrations for an application to regenerate. Decision: [ADR-0035](https://github.com/brenpike/Chatter/blob/master/docs/adr/0035-the-outbox-drain-claims-the-row-it-is-about-to-publish-inside-the-transaction-that-publishes-it.md). Pinned by `WhenClaimingForDispatch.MustGrantTheDrainClaimToOnlyOneOfTwoDrainsThatObservedTheSameNextAttempt`, `.MustRefuseTheDrainClaimAgainstAStaleObservedNextAttempt`, `.MustRefuseTheDrainClaimOnAMessageAlreadyProcessed`, `.MustClaimOnlyTheMessageItWasHanded`, `.MustCompareANullObservedNextAttemptAsIsNull`, `.MustCompareANonNullObservedNextAttemptAsAParameter`, `.MustWriteTheGrantedClaimOntoTheSuppliedMessage` and `.MustEnlistTheClaimInTheAmbientTransaction`, and over a real SQL Server — every fact run under `READ_COMMITTED_SNAPSHOT` ON and OFF, evidenced from `sys.dm_exec_requests` through `SqlServerBlockedRequestProbe` rather than from elapsed time — by `Integration/WhenArbitratingOutboxDrainsOnSqlServer.MustMakeASecondDrainsClaimWaitOnTheWinningDrainsRowLock`, `.MustDenyTheWaitingDrainsClaimOnceTheWinningDrainCommits`, `.MustGrantTheWaitingDrainsClaimOnceTheWinningDrainRollsBack` and `.MustLeaveADifferentRowClaimableWhileADrainIsBlockedOnTheRacedRow`; the reasoning is in the `INVARIANT:` comments on `TryClaimForDispatch`. The first of those four asserts the waiting request's wait type STARTS WITH `LCK`: it pins that the wait is on a lock, not which lock mode, and no fact here names a mode. Limitation, disclosed not eliminated: every lock measurement covers a SINGLE-ROW clustered-PK seek, which is what keeps one wedged publish from stalling the outbox for other rows (`.MustLeaveADifferentRowClaimableWhileADrainIsBlockedOnTheRacedRow`); a range or scan claim predicate takes locks beyond the one row and is unmeasured. Consequence: a publish slower than the `DbContext` command timeout — 30 seconds by the provider's default, a figure no oracle pins — makes the waiting drain's claim statement throw, and that drain then spends a dispatch attempt it never used. It is bounded, because `OutboxMaxDispatchAttempts` is absent by default, so the outcome is a deferred row the winner is already publishing. It is a consequence rather than a knob: no option was added anywhere for it.
_Avoid_: reading `ProcessedFromOutboxAtUtc`'s concurrency token as what keeps two hosts from publishing one row twice — it arbitrates the STAMP, at commit, once both have published; the Relational Drain Claim is what arbitrates the publish.

**Outbox Poll Index**: The opt-in index over `ProcessedFromOutboxAtUtc` then `SentToOutboxAtUtc`, shipped as `OutboxMessagePollIndexConfiguration` separately from `OutboxMessageConfiguration` so that applying it — and owning the migration it generates — is the application's decision rather than a model change made on its behalf. The leading column is the one both unprocessed polls filter on; the second follows it because a drain works the oldest staged message first. It is neither filtered nor unique, so it stays provider-neutral. It indexes neither column of the Outbox Attempt State: extending it to lead with `NextAttemptAtUtc` would force a second migration on an application that has already applied it, so that shape is carried by [#381](https://github.com/brenpike/Chatter/issues/381) instead.

## Relationships

- Implements the Outbox and Inbox persistence ports defined in the Message Brokers context, replacing their in-memory defaults.
- All types are generic over the consumer's own `DbContext` (`TContext : DbContext`) — no separate Chatter context; entity configs are applied in the consumer's `OnModelCreating`.
- Wired through the Command Pipeline as behaviors (`WithInboxBehavior<TContext>()`, `WithOutboxProcessingBehavior<TContext>()`, `WithUnitOfWorkBehavior<TContext>()`), not a standalone DI registration; `WithReliabilityRetention<TContext>(...)` is a fourth entry point on the same builder that adds no behavior. All four must name one `TContext`: the first call to arrive binds it, a later call naming the same one is a no-op, and a later call naming a different one throws `InvalidOperationException` at registration naming both contexts. A refused call leaves the service collection exactly as it found it, slot for slot, wherever within the entry point the refusal is raised: each entry point stages every registration it makes onto a scratch `IServiceCollection` and reaches the caller's own only through a commit phase containing no fallible operation. Pinned by `WhenBindingReliabilityContext.MustLeaveTheServiceCollectionExactlyAsItWasWhenAnyRefusalIsRaised`, a sweep over every public `TContext`-parameterized entry point crossed with every refusal that entry point can raise; the reasoning is in the `INVARIANT:` on `StageReliabilityRegistrations` and the decision in [ADR-0032](https://github.com/brenpike/Chatter/blob/master/docs/adr/0032-the-reliability-registration-door-stages-its-mutations-so-a-refusal-cannot-be-observed.md). Residual: a collection the host has made read-only refuses the commit's write, as it refused the registration before staging existed, and no test pins that.
- The Unit of Work commits domain changes together with Outbox/Inbox writes via a Persistance Transaction (`IPersistanceTransaction`).
- Outbox processing wraps the Unit of Work, which wraps the Inbox — this order is package-guaranteed, not derived from the order the pipeline extension methods are called in. The guarantee covers only descriptors registered through `WithUnitOfWorkBehavior<TContext>()`, `WithInboxBehavior<TContext>()`, and `WithOutboxProcessingBehavior<TContext>()`; later direct `WithBehavior` calls, and closed-generic, factory, keyed, or decorated registrations of these behavior types, are outside normalization.

## Example dialogue

> **Dev:** "How do I guarantee the message publishes only if my DB write succeeds?"
> **Domain expert:** "Write to the Brokered Message Outbox inside the same Unit of Work as your aggregate; the Persistance Transaction commits both or neither."
