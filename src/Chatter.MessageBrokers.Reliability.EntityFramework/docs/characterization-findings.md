# Chatter.MessageBrokers.Reliability.EntityFramework — Characterization Findings

This document is a pure observation log produced during behavior-pinning (characterization) testing of `Chatter.MessageBrokers.Reliability.EntityFramework`. Every row records **current behavior as-is** — not desired or corrected behavior. No production source was modified. Tests that pin these behaviors live under `src/Chatter.MessageBrokers.Reliability.EntityFramework/tests/`. Each finding is flagged here for human review and prioritization; no code fix is prescribed.

| # | Unit | Pinned behavior | Why suspicious | Pinning test | Suggested follow-up |
|---|------|-----------------|----------------|--------------|---------------------|
| 1 | `UnitOfWork<TContext>.ExecuteAsync` (via `BrokeredMessageOutbox<TContext>`) | Under EF Core InMemory, `BeginTransactionAsync` surfaces `TransactionIgnoredWarning` as an `InvalidOperationException` before the supplied operation runs; the UoW body and commit never execute. Superseded in part: `ExecuteAsync` now throws earlier still when the context's execution strategy reports `RetriesOnFailure`, refusing before the strategy runs and before any transaction is begun. The InMemory provider's strategy does not retry, so this row's begin-before-operation ordering is unchanged for it; a `DbContext` configured with `EnableRetryOnFailure` never reaches the begin at all | This is provider-specific test-harness behavior: production relational providers (SQL Server) support transactions normally; any test that calls `ExecuteAsync` under InMemory cannot exercise the operation, commit, or rollback paths | `UsingBrokeredMessageOutbox/WhenExecutingUnitOfWork.cs::MustThrowWhenBeginningTransactionUnderInMemory`, `MustThrowWithNullTransactionContextUnderInMemory` | Integration-test the full UoW flow against a real relational provider (e.g. SQL Server LocalDB or SQLite with `EnableSensitiveDataLogging`) to cover the commit and rollback branches |
| 2 | `UnitOfWork<TContext>.ExecuteAsync` (via `BrokeredMessageOutbox<TContext>`) | When both `BeginTransactionAsync` and the supplied operation would throw, only the transaction-begin `InvalidOperationException` is surfaced; the operation exception is never observed | The transaction-begin failure preempts the operation entirely, so the caller cannot distinguish a misconfigured provider from a failing operation when both would have thrown | `UsingBrokeredMessageOutbox/WhenExecutingUnitOfWork.cs::MustThrowFromTransactionBeginBeforeRunningOperationThatThrows` | Document this ordering contract in XML-doc on `ExecuteAsync`; consider wrapping both exceptions in an aggregate if operation-level diagnosis is needed |
| 3 | `BrokeredMessageInbox<TContext>.ReceiveViaInbox` | After a successful handler invocation the new `InboxMessage` is added to the change tracker (`EntityState.Added`) but `SaveChangesAsync` is never called; the row is not persisted until the surrounding `DbContext` is saved externally; a fresh store query returns empty | The outbox now matches the inbox: `SendToOutbox` on the sibling `BrokeredMessageOutbox<TContext>` also only stages (`outbox.AddAsync`, no `SaveChangesAsync`); neither store saves itself, and both are committed by the unit of work wrapping the handler — idempotency (`AnyAsync`) only sees previously-saved rows, so a process restart before that commit would re-handle a message | `UsingBrokeredMessageInbox/WhenReceivingViaInbox.cs::MustInvokeHandlerAndTrackButNotPersistInboxMessageForFreshMessageId` | Decided: the marker is deliberately left pending (`EntityState.Added`, not saved) and is committed by the unit of work's single `SaveChangesAsync`, not by an inbox-owned save — see [ADR-0006](../../../docs/adr/0006-two-tier-reliability-relational-ambient-tx-vs-nosql-stage-then-commit.md). Durability is guaranteed by the canonical reliability behavior order (inbox nested inside the unit of work), not by the inbox saving on its own. The single-`TContext` condition that guarantee rests on is now enforced rather than assumed: `WithUnitOfWorkBehavior<TContext>()`, `WithInboxBehavior<TContext>()`, `WithOutboxProcessingBehavior<TContext>()`, and `WithReliabilityRetention<TContext>(...)` each bind the context as their first statement, so the first call records it, a later call naming the same one is a no-op, and a later call naming a different one throws `InvalidOperationException` at registration naming both contexts and leaving the service collection exactly as it found it. A lone `WithInboxBehavior<TContext>()` call remains sufficient, since it registers the matching unit of work itself. The previously-documented void case — a later `WithUnitOfWorkBehavior` or `WithOutboxProcessingBehavior` naming a different `TContext`, leaving the unit of work committing a different `DbContext` than the one holding the marker — is no longer reachable through these entry points. |
| 4 | `BrokeredMessageOutbox<TContext>` explicit `IUnitOfWork.ExecuteAsync` (formerly inside `SaveOutboxAsync`, now removed) | The `catch (DbUpdateConcurrencyException)` branch, wrapping the drain's `_unitOfWork.ExecuteAsync` call, is never reachable under the EF Core InMemory provider because InMemory does not enforce concurrency tokens; the compensating-read and `entry.OriginalValues.SetValues` logic is dead in the test harness | The branch exists for a real relational scenario (row already processed, concurrency-token mismatch) but cannot be exercised in unit tests without a relational provider or manual EF state manipulation. The catch's scope also widened on relocation: it now wraps the whole `_unitOfWork.ExecuteAsync(operation)` call, including the broker dispatch inside `operation`, where it previously wrapped only `_context.SaveChangesAsync`. It is also now re-keyed off an exception predicate rather than try-block position — `catch (DbUpdateConcurrencyException ce) when (ce.Entries.Any(e => e.Entity is OutboxMessage))` — though the inner `if (entry.Entity is OutboxMessage)` guard is retained, so this re-key changes only whether the catch frame is entered, not observable resync behavior; that inner guard already no-ops the loop body for a non-outbox conflict, so the re-key is not independently observable. The body also gained a null guard: `entry.GetDatabaseValuesAsync` returns null when the conflicted row was concurrently deleted, and the code now logs and continues so the original `DbUpdateConcurrencyException` propagates, where previously a `NullReferenceException` replaced it. The whole per-entry compensation body was then wrapped in `try / catch (Exception)`, deliberately broad, so that any failure the best-effort resync raises — not only the null case — is logged instead of replacing the concurrency exception | verified live against a real SQL Server container: `Integration/WhenClaimingOutboxConcurrentlyOnSqlServer.cs::MustSurfaceConcurrencyExceptionWhenConflictedRowWasDeleted` (new) pins the null-guard and `::MustSurfaceConcurrencyExceptionWhenCompensatingReadThrows` (new) pins the broad guard, driving a real failure through `tests/Support/FailingCompensationReadInterceptor.cs` and asserting the injection actually fired — those two are the independently observable reds from this row's changes; the two existing `[RequiresDockerFact]` race facts in the same file (`MustAllowExactlyOneClaimWhenTwoStoresRaceForTheSameRow`, `MustClaimRowExactlyOnceWhenTwoStoresRaceForTheSameRow`) still pass through the new catch site and serve as the predicate re-key's regression net | Cover the concurrency-exception path with an integration test against a relational provider with a rowversion/timestamp concurrency token, or use EF interceptors to force the exception in a unit test |
