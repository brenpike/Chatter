# Changelog

All notable changes to this project will be documented in this file.

This project follows [Keep a Changelog](https://keepachangelog.com/en/1.0.0/) and [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Documentation

- Documented the cross-tier inbox handler-side-effect contract (#220/#241, ADR-0007). Because the Document-Tier Batch-Lifecycle Behavior stamps the `inbox:` marker, runs `next()`, and only THEN executes the single `TransactionalBatch`, a confirmed-duplicate marker-409 surfaces AFTER the handler has run. Consequence on a redelivered duplicate: writes staged on the framework-owned batch (the aggregate write + co-resident outbox doc) roll back atomically and never re-commit (EXACTLY-ONCE), but handler side effects performed OUTSIDE the batch (external HTTP, non-Cosmos writes) have already executed and re-execute on every redelivery (AT-LEAST-ONCE) — so handlers with non-batched side effects MUST be idempotent. This contrasts with the relational tier (`BrokeredMessageInbox.ReceiveViaInbox`), which reads `HasBeenReceived` first and SKIPS the handler entirely on a known duplicate, so its non-batched side effects do not re-run. This is the deliberate cost of the no-pre-read / TOCTOU-free design (a pre-read would reintroduce the eliminated TOCTOU); it records existing intent and is a documentation-only clarification (README, XML-doc, ADR-0007) with NO behavior or wire-shape change.

### Added

- Enforced reserved id-namespace for the `inbox:`/`outbox:` item-id prefix (#220 hardening, ADR-0007): the prefix is now a Chatter-reserved id-namespace ENFORCED at stage time (parity with the trusted `_chatterType` reserved field), not a naming convention. The public document-tier atomic-write surface rejects an app-authored reserved-prefix id by construction — the only public create/upsert path is the peek-guarded `StageCreateItemStream`, whose guard keys on the PERSISTED `item.id` peeked from the payload bytes the SDK reads, so a reserved-prefix persisted id cannot be staged by any public create/upsert by construction; `StageReplaceItem<T>`/`StagePatchItem` guard their explicit op-key `id` (which IS the persisted key). Each calls `CosmosItemId.GuardNotReserved` BEFORE staging, so a rejected stage leaves the batch and `StagedOperationCount` unperturbed. The framework's own reserved-id writes (the outbox doc, the inbox marker) flow through an internal guard-bypassing `ICosmosReservedWriteHandle` facet that is the sole sanctioned reserved-id writer. This closes a soundness gap in the inbox marker-409 → confirmed-duplicate inference: an app aggregate doc authored with an `inbox:{encoded(MessageId)}` id could previously 409 the framework's marker create and be swallowed as a "duplicate," silently losing the first delivery; with the public surface unable to stage a reserved-prefix id, a marker-create 409 can ONLY mean a prior Chatter marker, so the inference is collision-proof.
- Document-tier inbox idempotent dedup (#220, ADR-0006/0007): a redelivered message with the same identity is handled exactly once. The `DocumentTierBatchLifecycleBehavior` now stamps a co-resident `CosmosInboxMarker` (`_chatterType="inbox"`, id `inbox:{encoded(MessageId)}` via the shared `CosmosItemId` encoder, the raw `MessageId` verbatim, a `ReceivedAtUtc` ISO-8601 instant; NO status field and NO TTL) into the framework-owned `TransactionalBatch` as op index 0 — BEFORE the handler runs — for a participant command whose inbound message carries a usable identity, in the aggregate's partition so it rides the SAME batch as the aggregate + outbox writes and commits atomically with the business write (no TOCTOU; dedup is closed-by-construction via the create-conflict, NOT a read-then-add). At batch-execute time the response inspection is a three-way branch: a 409 Conflict on the MARKER op (index 0) is a CONFIRMED DUPLICATE — the all-or-nothing batch failed so nothing committed, and the message is acked without re-handling (no throw, no redeliver); an aggregate ETag/412, a 409 on a NON-marker op, a marker 424 failed-dependency, no per-op results, or any other non-success still throws `CosmosBatchExecutionException` so the transport redelivers/retries (conflating the marker 409 with an aggregate 412 would be silent message loss, so only the marker op's own 409 is swallowed). A participant command MUST carry a non-empty `MessageId`: a participant that resolves a partition but has a null/whitespace `MessageId` cannot be deduped by identity, so the once-only guarantee cannot be honored — the behavior rejects it loudly with `InvalidOperationException` BEFORE the batch is opened (nothing staged, the handler never runs, nothing acked), matching the in-memory tier which throws. The marker's `type="inbox"` discriminator keeps markers out of the #222 change-feed relay (which drains `type="outbox"`) by construction. The fresh-node partition-key stamping primitive is extracted into a shared `CosmosPartitionKeyStamping` helper used by both the outbox document and the inbox marker (each passing its own reserved-root-field collision-guard set; no duplication); the outbox wire shape and stamping behavior are unchanged. `CosmosInboxDeduplicator` realizes the tier-neutral `IInboxDeduplicator` contract TYPE for parity/discoverability but is intentionally NOT DI-registered — the document tier never resolves `IBrokeredMessageInbox`/`IInboxDeduplicator` (a cast-facet of the single resolved store the document tier does not register), so registering it would violate core's resolves-to-null cast-at-consumption invariant; its `HasBeenReceived` throws `NotSupportedException` because a read-then-add would reintroduce the TOCTOU this design eliminates. An app-configurable dedup-window TTL on markers is a deferred design point.
- Per-command document-tier participation registry and multi-container model (#238, ADR-0008): document-tier reliability is now opt-in PER COMMAND TYPE via a positive allowlist. `WithCosmosDocumentReliability<TCommand>(database, container, lease, resolver, partitionKeyPath...)` adds one registration per participating command type to a singleton `DocumentReliabilityRegistry`; participation IS having a registration, so a command type without one bypasses the document tier entirely (no resolver call, no batch). Multiple single-partition containers are supported — many command types may map to one container, but exactly one registration exists per command type (a duplicate registration for the same command type throws). Container handles are DERIVED (never provisioned) from the app-registered `CosmosClient` singleton via `client.GetContainer(database, container)` by the new singleton `CosmosContainerFactory`, cached thread-safely per `(database, container)`; the application owns the `CosmosClient` lifecycle and the existence of the database/container/lease (a documented prerequisite — the provider registers no client). ADR-0007's single-aggregate/single-partition hard constraint is unaffected; the registry adds container selection, not cross-partition atomicity.
- Document-tier outbox enqueue (#219): `CosmosBrokeredMessageOutbox` realizes `IBrokeredMessageOutbox.SendToOutbox` by resolving the active doc-tier atomic-write handle from the reliability surface and contributing the Chatter-owned outbox document's `CreateItemStream` op to the framework-owned `TransactionalBatch` (it never executes the batch — the Document-Tier Batch-Lifecycle Behavior owns the single commit point). The outbox is container-agnostic — it stages onto whatever container the behavior opened the batch on, so it supports the multi-container registry above with no change. The outbox document (`CosmosOutboxDocument`) carries the `_chatterType="outbox"` discriminator, an `outbox:{encoded(MessageId)}` id via the shared Cosmos-id-safe encoder (`CosmosItemId`, reused by #220 for inbox markers), the raw `MessageId` verbatim, the `MessageContext` serialized with `ChatterJson.Options` (EF parity), the message body/destination/content-type, and `status="pending"`; the resolved partition-key value is stamped at the container's actual partition-key path (supporting a hierarchical path), not a fixed field. Registered as `IBrokeredMessageOutbox` with the outbox router in DI.
- Closed-by-construction staging contract on `ICosmosAtomicWriteHandle`: the framework-owned `TransactionalBatch` is no longer publicly reachable for op-adds. All staging goes through intent-revealing methods (`StageCreateItemStream`, `StageReplaceItem<T>`, `StagePatchItem`), each of which calls the corresponding SDK batch op AND increments `StagedOperationCount` in one indivisible action. The ack-on-uncommitted class — stage an op via the raw batch without calling a count method → empty-batch guard reads 0 → skips `ExecuteAsync` → acks with nothing committed — is impossible by construction. `StagedOperationCount` is read-only for the behavior's empty-batch guard only; callers may not manipulate it independently. `StageCreateItemStream` is the Chatter-owned wire-shape path (outbox, #220 inbox marker) and the only public create/upsert path. The `CosmosBatchExecutionException.StatusCode` response-inspection seam is unchanged — #220 can still distinguish a confirmed-duplicate inbox-marker 409. Closes the first of the two deferred P1 skeleton findings.
- Removed the typed `StageCreateItem<T>`/`StageUpsertItem<T>` from the public document-tier atomic-write surface pre-release: their reserved-namespace guard keyed on an explicit `id` parameter the Cosmos SDK ignores — the SDK derives the persisted physical id by serializing `item` and reading `item.id`, so the guarded parameter could diverge from what Cosmos persists and a reserved-prefix doc could be staged unguarded. The sole surviving public create/upsert path is the peek-guarded `StageCreateItemStream`, whose guard keys on the persisted `item.id`.
- Batch-response inspection in the Document-Tier Batch-Lifecycle Behavior: after the single `ExecuteAsync`, a non-success `TransactionalBatchResponse` throws `CosmosBatchExecutionException` so the message is not acked when the writes did not commit (a forced aggregate ETag/412 surfaces here). The inspection is structured as a clean seam so #220 can later distinguish a confirmed-duplicate inbox-marker 409. The empty-batch guard (skip `ExecuteAsync` when no op was staged) is preserved. Closes the second deferred P1 skeleton finding.

### Changed

- A document-tier participant with a resolved partition but a null/whitespace `MessageId` now FAILS LOUD (#220/#241, ADR-0007). Previously such a message stamped no inbox marker and proceeded — running the handler and committing the aggregate + outbox before acking — so a redelivery of the same identity-less message was undetectable (a silent once-only loss). The behavior now throws `InvalidOperationException` BEFORE opening the batch, so nothing is staged, the handler never runs, and nothing is acked. A participant without a `MessageId` is a protocol/config error, matching the in-memory tier which throws.
- The `ResolvePartitionKey` delegate is now Try/nullable (`PartitionKey?`): a `null` return means "no resolvable partition for this message", in which case the Document-Tier Batch-Lifecycle Behavior opens no batch and bare-passes-through to `next()`. The resolver is only ever invoked for registered participants, so the prior null-inbound NRE (an in-process command's `null` inbound message reaching an unguarded resolver) is eliminated by construction. `DocumentTierBatchLifecycleBehavior<TMessage>` is rewritten to be registry-gated: a registry miss is a bare pass-through; a registry hit resolves the partition key, derives the registration's container via `CosmosContainerFactory`, and opens the batch on it.
- The Cosmos DI registration no longer accepts eager `Container` instances. The eager two-`Container`-instance `WithCosmosDocumentReliability` overload is REMOVED in favor of deriving handles from the app-owned `CosmosClient`; a per-registration `Func<IServiceProvider, Container>` factory overload is kept for applications that resolve their containers from the service provider themselves. The single-container DI holders (`DocumentContainer` / `LeaseContainer`) are superseded by the registry + factory and removed.

### Fixed

- Non-participant dispatch no longer throws from the Cosmos outbox, regardless of registration order (#238, #239, ADR-0008). `WithCosmosDocumentReliability<T>` globally replaces the outbound `IRouteBrokeredMessages`, but only PARTICIPANT command types open a document-tier batch (which sets the surface handle); previously a NON-registered command whose handler Send/Published routed straight into `CosmosBrokeredMessageOutbox`, which threw `InvalidOperationException` on the null handle — contradicting "a command type without a registration bypasses the document tier entirely". Routing is now gated by a closed-by-construction `HandleGatedOutboxRouter` decorator: when the surface handle is null (every non-participant dispatch, and every dispatch after a participant's batch scope closes) routing delegates to a directly-constructed default broker router — a plain `BrokeredMessageRouter` over the always-`AddMessageBrokers`-registered `IMessagingInfrastructureProvider`, resolved lazily inside the registration factory at dispatch time — so a non-participant command dispatches straight to the broker exactly as if Cosmos were not installed; only a participant's mid-batch dispatch (handle set) routes through the Cosmos outbox — unchanged. Because the inner-default arm is constructed directly and never depends on `IBrokeredMessageOutbox`, the wiring is registration-order-independent: it behaves identically whether `AddChatterCqrs` (which runs the Cosmos pipeline callback) or `AddMessageBrokers` runs first, and whether `RouteMessagesToOutbox` is on or off. (This replaces the prior capture-the-core-default-descriptor approach, which was broken on both ends: the pipeline callback runs before `AddMessageBrokers` registers the default router, so the captured descriptor was null and threw; and under `RouteMessagesToOutbox` the rebuilt inner resolved the already-replaced Cosmos outbox and still threw on the null handle.) The factory `Replace` is idempotent-in-effect across multiple `WithCosmosDocumentReliability<T>` calls (exactly one router descriptor, never double-wrapped). The mixed configuration "`RouteMessagesToOutbox=true` + Cosmos provider + a separate non-Cosmos outbox" is UNSUPPORTED. The `CosmosBrokeredMessageOutbox` null-handle throw is retained as a hard wiring-error guard the decorator now ensures non-participants never reach.
- Multi-message outbox drain (#219): each outbox document in a `SendToOutbox` call with two or more messages now stamps its own freshly-derived partition-key node (minted per document from a detached `JsonElement`). Previously, shared `JsonNode` instances resolved once in `SendToOutbox` were re-stamped across documents; on the second message the already-parented node threw, the batch never executed, and the message redelivered forever. Cross-document node re-parenting is now structurally impossible — the `JsonElement` value type carries no parent reference, and each `ToJsonObject` call mints a fresh `JsonNode` at stamp time.

## [0.1.0] - 2026-06-14

### Added

- Initial document-tier (Cosmos DB) reliability provider **skeleton** (#218): the package and DI surface, the document-tier reliability surface (the doc-tier atomic-write handle — sibling of `IPersistanceTransaction` — carrying the bound container, the open `TransactionalBatch`, the resolved partition-key value, and the container's partition-key path), the app-registered partition-key resolver, and the Document-Tier Batch-Lifecycle Behavior **shell** registered as the outermost pipeline behavior. The behavior opens a `TransactionalBatch` on the resolved partition and executes it once after the handler — guarded so an empty batch (zero staged ops) never calls the Cosmos transport. The change-feed lease container is registered for the future relay. Outbox enqueue, inbox dedup marker, the change-feed relay, and the Cosmos emulator suite are **not** implemented in this release — they arrive in #219 (outbox), #220 (inbox), #222 (relay), and #223 (emulator suite).
