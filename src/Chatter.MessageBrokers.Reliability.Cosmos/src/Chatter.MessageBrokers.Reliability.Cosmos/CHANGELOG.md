## [0.4.2] - 2026-08-24

### Fixed

- Corrected the NuGet package `<Description>`, which made four claims the library does not support. The package is no longer scoped as document-tier — it is described as shipping three independently registrable primitives: the Document Tier, the Standalone Inbox Gate, and the Standalone Outbox Relay. Removed the false claim that Chatter exclusively owns the reserved `inbox:`/`outbox:` item-id namespace; the Reserved Item-Id Namespace is now stated directionally — a prohibition on the Document Tier's public staging surface, an obligation on a Standalone Outbox Relay's monitored container. Removed the banned "database/container/lease" alias for the Change-Feed Source Identity, and dropped `ChangeFeedProcessor` cardinality entirely as an internal detail. The Outbox Body Resolver is now attributed to the Standalone Outbox Relay only, and only when one is configured — the Document-Tier Outbox Relay always reconstructs the message verbatim. The description was also materially shortened (356 → 196 words), with the implementation detail that duplicated the README and the module glossary removed. Package metadata only — no behavior change, nothing to do on upgrade.

## [0.4.1] - 2026-08-22

### Fixed

- Corrected the NuGet package `<Description>`, which described standalone inbox marker behavior the library does not have. The description now also notes the gate's concurrency posture: it deduplicates redeliveries but does not serialize concurrent delivery, so two concurrent deliveries of the same message id both run the handler, and handlers must be idempotent and safe under concurrent execution. Package metadata only — no behavior change, nothing to do on upgrade.

## [0.4.0] - 2026-06-30

### Added

- Standalone, lease-less Cosmos inbox-dedup gate (#253, ADR-0009): `WithCosmosInbox(this CommandPipelineBuilder, Action<CosmosInboxOptions>)` registers `CosmosBrokeredMessageInbox : IBrokeredMessageInbox, IInboxDeduplicator` and adds the existing `InboxBehavior<T>` — and NOTHING else (no lease container, no relay host, no outbox, no router replacement) — for a stateless consumer (e.g. a message ACL hop) that has no Cosmos aggregate, no transactional outbox, and no lease container. Unlike the document tier (which dedups inside the aggregate's `TransactionalBatch`), the gate performs an anti-TOCTOU TWO-PHASE WRITE-AHEAD claim (ADR-0009, amended D1): phase 1 `CreateItemStream`s a PENDING `CosmosInboxMarker` (`_chatterType="inbox"`, id `inbox:{encoded(MessageId)}`, the raw `MessageId`, `Completed=false`, an optional TTL) on a single-segment `/idempotencyKey`-partitioned container BEFORE the handler; on a fresh 201 the handler runs, then phase 2 `PatchItemStream`s the marker to `Completed=true` AFTER it returns — so a redelivery confirms a duplicate on COMPLETION, not mere existence. This closes the abandoned-marker permanent-loss defect the prior single-phase confirm-on-existence had: a marker persisted then ABANDONED (the process hard-killed between the 201 and handler completion) would otherwise be mistaken for a completed one and its handler NEVER run — and best-effort compensation cannot close that window because its `catch` fires only on a handler exception, never on a SIGKILL between the create and completion. A create-409 is still closed-by-construction (no read-then-add) and, per CONFIRM-NOT-INFER (ADR-0009 D1), never trusted as a bare duplicate — the application owns the container and could author a colliding `inbox:`-prefixed id through a non-staging path — so `ReceiveViaInbox` point-reads the conflicting document (checking `_chatterType="inbox"` AND `MessageId` equal to the inbound id BEFORE inspecting completion) and resolves it THREE ways: a genuine COMPLETED marker for this id is a confirmed duplicate → SKIP; a genuine but PENDING/abandoned marker for this id is TAKEN OVER → the handler runs, then the claim completes (eliminating the loss); a non-marker / different-id / non-success read, or a not-yet-visible 404 whose bounded budget (`CosmosInboxOptions.ReadBackMaxAttempts`/`ReadBackInterval`) is exhausted, REDELIVERS (throws) rather than silently skipping. FAIL-LOUD on a missing id (ADR-0009 D2): a null/whitespace inbound `MessageId` throws `InvalidOperationException` before any write, matching the document tier and the in-memory inbox rather than the EF relational inbox's run-with-no-dedup stance — reachable behind a raw Azure Service Bus producer, which passes `MessageId` through with no fallback. The claim is write-ahead, so a handler failure (fresh claim or take-over) rethrows the ORIGINAL exception for redelivery and LEAVES the write-ahead PENDING marker in place — never deleting it — for the take-over path to adopt and re-run, while a phase-2 completion-write FAILURE THROWS (the message redelivers rather than acking with a still-pending marker — never swallowed); take-over of an abandoned pending marker re-runs the handler and non-batched handler side effects that already ran re-run on redelivery (AT-LEAST-ONCE), so handlers behind this inbox MUST be idempotent — the same side-effect-timing contract the document tier documents (ADR-0007). The shared marker state is MONOTONIC (absent -> pending -> completed; a TTL purge via `MarkerTimeToLive` is the only removal), so the gate never moves completed -> absent and a marker another concurrent same-id delivery already completed can never be reverted. The two-phase shape costs one extra completion write (one `PatchItemStream` per fresh or taken-over delivery). `CosmosInboxOptions` carries the required `Database`/`Container`, an optional `PartitionKeyPath` (defaults to `["/idempotencyKey"]`; v1 supports only a single segment, a multi-segment path throws at registration), an optional `MarkerTimeToLive` (seconds; null/non-positive emits no TTL, so markers persist indefinitely by default), and the confirm read-back budget. `HasBeenReceived` on `CosmosBrokeredMessageInbox` always throws `NotSupportedException` — a read-then-add would reintroduce the eliminated TOCTOU, matching the document tier's `CosmosInboxDeduplicator`. The standalone outbox relay (`AddCosmosOutboxRelay`) and this inbox are orthogonal and fully supported together; the document tier (`WithCosmosDocumentReliability`) and this inbox are UNSUPPORTED together in one pipeline (ADR-0009 D3, documented rather than registration-guarded, since no current consumer hits the combination).
- Clarified the standalone-inbox handler contract as idempotent AND concurrency-safe (#253, ADR-0009 D1 sub-note): because the lease-less take-over cannot distinguish an ABANDONED pending marker from a LIVE in-flight one, two genuinely-concurrent in-flight deliveries of the same `MessageId` both TAKE OVER and run the handler CONCURRENTLY. Accepted posture: this inbox DEDUPS REDELIVERIES and is NOT a distributed lock — it does not serialize concurrent delivery; mutual exclusion for concurrent delivery is the transport's message-lock/session (e.g. Azure Service Bus PeekLock or a session). The prior "handlers must be idempotent" wording is sequential-retry-safe but weaker than concurrency-safe, so the contract is strengthened to idempotent AND safe under concurrent execution of the same id. Docs/XML-doc clarification only — NO behavior or wire-shape change.
- Optional dedup-window TTL on `CosmosInboxMarker`: the marker's `ToJsonObject` gained an optional time-to-live parameter so a caller (currently the standalone inbox) can stamp a positive `/ttl` and have Cosmos self-purge the marker after the window; omitted or non-positive emits no TTL, byte-identical to the prior unconditional-no-TTL shape, so the #220 document-tier inbox marker (which never TTLs its co-resident marker) is unaffected.

### Fixed

- Standalone-inbox gate-corruption class under concurrent same-id delivery (#253, ADR-0009 D1 monotonic-marker sub-note). The interim two-phase design best-effort compensation-DELETED the write-ahead marker on a handler failure; because `marker.Id` is deterministic from the message id, that delete could remove a marker ANOTHER concurrent same-id delivery had already patched to `Completed=true` — reverting completed -> absent and defeating once-only (a redelivery would re-claim and re-run a handler the gate already recorded as done). The compensation-delete is REMOVED: a handler failure (fresh claim or take-over) now simply rethrows the original exception and LEAVES the pending marker for the existing take-over path to adopt and re-run. The shared marker state is thereby MONOTONIC — it only ever moves absent -> pending -> completed, and a TTL purge (`MarkerTimeToLive`) is the only removal — so the gate never moves completed -> absent and the corruption class is closed BY CONSTRUCTION. This REMOVES machinery: it is NOT the rejected liveness lease (no lease container, no relay, no owner token, no TTL heartbeat) and does NOT change the accepted P1 concurrent-execution posture (two genuinely-concurrent in-flight same-id deliveries still both run the handler). Consequence: a poison/permanently-failing message with no `MarkerTimeToLive` leaves a persistent pending marker that each redelivery re-takes-over and re-runs (correct at-least-once; the transport eventually dead-letters it), and `MarkerTimeToLive` bounds that marker accumulation. Behavior corrected within the same unreleased feature — no wire-shape or version change.

## [0.3.0] - 2026-06-27

### Documentation

- Documented the cross-tier inbox handler-side-effect contract (#220/#241, ADR-0007). Because the Document-Tier Batch-Lifecycle Behavior stamps the `inbox:` marker, runs `next()`, and only THEN executes the single `TransactionalBatch`, a confirmed-duplicate marker-409 surfaces AFTER the handler has run. Consequence on a redelivered duplicate: writes staged on the framework-owned batch (the aggregate write + co-resident outbox doc) roll back atomically and never re-commit (EXACTLY-ONCE), but handler side effects performed OUTSIDE the batch (external HTTP, non-Cosmos writes) have already executed and re-execute on every redelivery (AT-LEAST-ONCE) — so handlers with non-batched side effects MUST be idempotent. This contrasts with the relational tier (`BrokeredMessageInbox.ReceiveViaInbox`), which reads `HasBeenReceived` first and SKIPS the handler entirely on a known duplicate, so its non-batched side effects do not re-run. This is the deliberate cost of the no-pre-read / TOCTOU-free design (a pre-read would reintroduce the eliminated TOCTOU); it records existing intent and is a documentation-only clarification (README, XML-doc, ADR-0007) with NO behavior or wire-shape change.

### Added

- Drain-time outbox body resolution seam for the change-feed relay (ADR-0007): the new public `IOutboxBodyResolver` with `Task<OutboundBrokeredMessage?> ResolveAsync(OutboxDrainContext, CancellationToken)` lets the relay RESOLVE the brokered-message body from CURRENT store state at drain time instead of reconstructing it verbatim from the persisted outbox document. The public readonly struct `OutboxDrainContext { string MessageId; PartitionKey PartitionKey; IReadOnlyList<string> PartitionKeyPath; JsonElement Document; }` carries the drained document's identity, resolved partition key, the container's partition-key path, and the raw document. The relay invokes the bound resolver once per ADMITTED pending-outbox document. The host's pre-scope gate is the pure `CosmosOutboxDocument.IsPendingOutbox` identity guard ONLY (it runs NO caller code and never throws); the optional `AdditionalPendingFilter` is composed at a SINGLE admission site — evaluated EXACTLY ONCE inside the relay, never re-evaluated by the host gate — so a non-idempotent or throwing caller filter cannot be double-evaluated and wedge the change feed. A document that is not a pending outbox document (a domain write, an inbox marker, a malformed item, the relay's own delivered/TTL event) is skipped BEFORE the per-document scope is opened or the resolver factory is invoked, so it never reaches the seam. A document that passes `IsPendingOutbox` but is then narrowed out by the caller's `AdditionalPendingFilter` opens a scope and invokes the resolver factory before the relay rejects it on the filter (one wasted scope; the resolver is never asked to resolve; nothing is published or stamped; the scope is disposed). For an admitted document a NON-NULL `OutboundBrokeredMessage` return is published and the document is then stamped `delivered`; a NULL return publishes nothing yet STILL stamps the document `delivered` so it self-purges (a document that resolves to nothing is purged rather than left `pending` to re-trigger every change-feed pass and pin the lease); a THROW stamps nothing and PROPAGATES out of the change-feed handler so the SDK does not checkpoint and the document re-surfaces next pass (at-least-once). When NO resolver is bound the relay uses the unchanged verbatim Reconstruct path (the existing default) — so a THIN trigger document carrying only the marker fields (no `MessageBody`/`MessageContentType`/`MessageContext`) REQUIRES a resolver, since the verbatim path throws "no content type" on it. The seam is purely additive: the existing pipeline-integrated `WithCosmosDocumentReliability` drain is unchanged and remains the default.
- Standalone change-feed outbox relay registration `AddCosmosOutboxRelay(this IServiceCollection, Action<CosmosOutboxRelayOptions>)` (namespace `Microsoft.Extensions.DependencyInjection`): a self-contained relay registered as its OWN `IHostedService`, INDEPENDENT of `AddChatterCqrs`/`WithCosmosDocumentReliability` and the command-pipeline `DocumentReliabilityRegistry`, for applications that want a change-feed Outbox Relay without participating in the command pipeline (or that want to drain a container the pipeline never registered). It is REPEATABLE — call once per monitored container to run multiple standalone relays side by side. `CosmosOutboxRelayOptions` carries `MonitoredContainerFactory` and `LeaseContainerFactory` (`Func<IServiceProvider, Container>`), `PartitionKeyPath` (recovers each document's partition key for the delivered/TTL patch), an optional `BodyResolverFactory` (`Func<IServiceProvider, IOutboxBodyResolver>`; when null the relay uses the verbatim Reconstruct path), and optional declared `MonitoredSourceIdentity`/`LeaseSourceIdentity` processor dedup keys (as on the advanced pipeline overload). The standalone relay drains the same co-resident pending outbox documents and publishes/stamps with the same at-least-once delivery and TTL-enabled-container prerequisite as the pipeline-integrated relay. DI-lifetime note: the host's pre-scope gate is the pure `IsPendingOutbox` identity guard ONLY (it runs NO caller code and never throws); the optional `AdditionalPendingFilter` is composed at a SINGLE admission site, evaluated EXACTLY ONCE inside the relay (the host gate never re-evaluates it), so a non-idempotent or throwing caller filter cannot be double-evaluated and wedge the change feed. The host opens a fresh `IServiceScope` and resolves the `IOutboxBodyResolver` from that scope (disposed after each document) for any document that passes `IsPendingOutbox`, so a resolver MAY depend on / capture scoped services (e.g. a scoped `DbContext`) in its constructor — no manual per-document scope inside `ResolveAsync` is required. A change-feed document that is NOT a pending outbox document (a domain write, an inbox marker, a malformed item, the relay's own delivered/TTL event) is cheaply skipped with NO scope opened, NO factory call, and NO user DI touched, so it cannot run user code or wedge the change feed. A document that passes `IsPendingOutbox` but is narrowed out by the caller's `AdditionalPendingFilter` opens a scope and invokes the factory before the relay rejects it on the filter (one wasted scope; the resolver is never asked to resolve; nothing is published or stamped; the scope is disposed). The raw `BodyResolverFactory` is the ADVANCED escape hatch and carries an explicit contract: because resolution happens inside the per-admitted-document scope, the factory MUST resolve a FRESH resolver from the supplied provider on every call and MUST NOT cache or capture the resolver (or its scoped dependencies) across documents.
- Safe-by-default convenience registrations for the standalone outbox relay so the common case never touches the raw `BodyResolverFactory` escape hatch: the generic `AddCosmosOutboxRelay<TResolver>(this IServiceCollection, Action<CosmosOutboxRelayOptions>)` (recommended) registers `TResolver` `Scoped` (via `TryAdd`, preserving any existing registration) and AUTO-WIRES `BodyResolverFactory` to resolve it from the host-owned per-admitted-document scope — a fresh instance per admitted (pending outbox) document, so the resolver may depend on scoped services; and the keyed `AddCosmosOutboxRelay<TResolver>(this IServiceCollection, object serviceKey, Action<CosmosOutboxRelayOptions>)` registers `TResolver` as a keyed-scoped `IOutboxBodyResolver` under `serviceKey` and binds THIS relay to that keyed resolver, for applications running MULTIPLE monitored containers each needing its own resolver (distinct keys never collide). Both overloads OWN the `BodyResolverFactory` wiring: if `configure` ALSO sets `BodyResolverFactory`, the overload throws `ArgumentException` rather than silently overriding the caller's delegate — either let the typed/keyed overload wire the resolver, or use the raw `AddCosmosOutboxRelay(configure)` escape hatch and set `BodyResolverFactory` yourself, never both.
- Fail-fast uniqueness guard against the silent standalone-relay consumer-group collision class: two standalone `AddCosmosOutboxRelay` registrations over the SAME monitored+lease containers (the same change-feed source identity) differing ONLY in their `AdditionalPendingFilter`/`BodyResolverFactory` would derive the SAME processor name and lease — one Cosmos consumer group whose lease ranges the SDK load-balances across both relays, so a pending outbox document checkpointed by the relay whose filter/resolver REJECTS it is never drained by the relay that would admit it and the document wedges. Because a lease cannot be keyed on a `Func` delegate, the distinction must come from the caller's source identity. The guard is enforced at TWO by-construction points sharing one accumulator: for DECLARED identities (both `MonitoredSourceIdentity` and `LeaseSourceIdentity` set) the derived processor name is checked at `AddCosmosOutboxRelay` REGISTRATION (a duplicate declared pair throws `InvalidOperationException` then); for GROUND-TRUTH-defaulted identities (both null, resolvable only after the provider is built and the containers are resolved) the resolved processor name is checked at host START (a second host resolving to the same ground-truth identity throws `InvalidOperationException` from `StartAsync`, naming the colliding processor name). Declared relays skip the start-time check (already registration-guarded). Distinct standalone relays over the same containers MUST declare distinct `MonitoredSourceIdentity`/`LeaseSourceIdentity` values. The `#187` single-relay default is unaffected — one relay never collides with itself.
- Promoted the relay's pending-document predicate and made its delivery stamping configurable behind hardened, construction-validated invariants: `CosmosOutboxDocument.IsPendingOutbox(JsonElement)` is now a PUBLIC static helper (the default pending predicate — `_chatterType="outbox"` AND `status="pending"`), reusable and composable. The relay ALWAYS applies this id-guard; `CosmosOutboxRelayOptions.AdditionalPendingFilter` (`Func<JsonElement, bool>?`, default null) is an ADDITIONAL predicate that runs (logical AND) only on documents that already passed the always-applied gate, so it can only further NARROW admission and CANNOT replace or weaken the #222 id-guard. The stamp knobs remain configurable with the existing values as defaults (`StatusPatchPath` `"/status"`, `DeliveredStatusValue` `"delivered"`, `DeliveredTtlSeconds` `86400`) but are now VALIDATED at `AddCosmosOutboxRelay` registration (throwing `ArgumentException` then, not at drain time): `DeliveredStatusValue` must differ from `pending`; `DeliveredTtlSeconds` must be `> 0` (`0`/`-1`/negatives rejected — a delivered document must be scheduled for self-purge); `StatusPatchPath` must be anchored to the gate's status field (`"/"` + that field) so a delivered stamp always moves the document out of pending. The delivered stamp's TTL patch path is NO LONGER a knob — it is HARD-WIRED to the Cosmos reserved `/ttl` property (the only field Cosmos self-purges on), so a delivered stamp that does not schedule self-purge is unrepresentable; `DeliveredTtlSeconds` remains the configurable positive retention. Purely additive — the existing relay behavior remains the validated default.
- Document-tier change-feed outbox relay (#222, ADR-0007): the persisted co-resident outbox documents are now drained and published. A hosted `IHostedService` runs one Cosmos `ChangeFeedProcessor` per DISTINCT `(Database, ContainerName, LeaseName)` triple from the `DocumentReliabilityRegistry` — NOT one per command type, since many command types may share one container (ADR-0008) — with a STABLE per-triple `processorName` (a constant prefix + the triple) so every app instance sharing a lease cooperates on the same logical processor, and a UNIQUE per-host `instanceName` (`{prefix}:{MachineName}:{Guid}`) so co-located instances do not collide on a lease. Change feed v3 delivers ALL container changes (domain docs, inbox markers, outbox docs, and the relay's own delivery-stamp updates), so the relay filters IN CODE to exactly `_chatterType="outbox" && status="pending"`: a domain document, an inbox marker (`_chatterType="inbox"`), an already-`delivered` outbox document (the relay's OWN delivery-stamp event — publish-once by construction), and a malformed outbox document with a missing/non-string/empty status are all skipped. A selected document is reconstructed into an `OutboundBrokeredMessage` exactly as the relational `OutboxProcessor` does (`MessageId` verbatim, `Destination`, `MessageBody`, `MessageContentType`, `MessageContext` materialized through `ChatterJson.Options`, content-type falling back to the persisted `MessageContext` when the document content-type is empty, infrastructure type read from the `MessageContext`, body bytes via an `IBodyConverterFactory` converter) and published via `IMessagingInfrastructureProvider.GetDispatcher(infra).Dispatch(message, null)` — the SAME no-reliability-re-entry path the relational relay uses (NOT `IBrokeredMessageDispatcher`, which can route back through the outbox and recurse). On publish SUCCESS the relay advances the document to `status="delivered"` and stamps a positive per-document `ttl` (`/status` and `/ttl`) in a SINGLE `PatchItemAsync` (not `ReplaceItem`) keyed on the document `id` read off the change-feed item and the partition key recovered from the same item at the container's declared partition-key path, so the patch lands in the document's own logical partition. Cosmos then self-purges the delivered document once its TTL elapses — this REQUIRES the application's container to have TTL enabled (`defaultTtl` set, e.g. `-1`), a documented application prerequisite, NOT automatic. The relay is AT-LEAST-ONCE: publish and the delivered/TTL patch are two separate writes, so a publish that succeeds and then a patch that fails leaves the document `pending` and it is re-published on the next change-feed pass — downstream consumers MUST dedup, and the #220 document-tier inbox marker is the in-framework mechanism. A publish that THROWS issues NO patch and PROPAGATES out of the change-feed handler so the SDK does NOT checkpoint the batch (the document re-surfaces next pass) rather than advancing the lease past an unpublished document. The relay host is registered ONCE idempotently across N `WithCosmosDocumentReliability<T>` calls (guarded on the same `Any(...)` once pattern as the outermost behavior); it resolves the registry, `CosmosContainerFactory`, `IMessagingInfrastructureProvider`, and `IBodyConverterFactory` from DI. The Cosmos provider still does NOT implement `IPollableOutboxStore` — dispatch is this change-feed relay, not a polling query (ADR-0007).
- Enforced reserved id-namespace for the `inbox:`/`outbox:` item-id prefix (#220 hardening, ADR-0007): the prefix is now a Chatter-reserved id-namespace ENFORCED at stage time (parity with the trusted `_chatterType` reserved field), not a naming convention. The public document-tier atomic-write surface rejects an app-authored reserved-prefix id by construction — the only public create/upsert path is the peek-guarded `StageCreateItemStream`, whose guard keys on the PERSISTED `item.id` peeked from the payload bytes the SDK reads, so a reserved-prefix persisted id cannot be staged by any public create/upsert by construction; `StageReplaceItem<T>`/`StagePatchItem` guard their explicit op-key `id` (which IS the persisted key). Each calls `CosmosItemId.GuardNotReserved` BEFORE staging, so a rejected stage leaves the batch and `StagedOperationCount` unperturbed. The framework's own reserved-id writes (the outbox doc, the inbox marker) flow through an internal guard-bypassing `ICosmosReservedWriteHandle` facet that is the sole sanctioned reserved-id writer. This guard is DEFENSE-IN-DEPTH on the public staging surface — it is NOT the soundness basis for the marker-409 → confirmed-duplicate decision. The app owns the container and can author a reserved-prefix id through a non-staging path the staging guard cannot close, so soundness comes from CONFIRMING the conflicting doc at execute time (see the `### Fixed` entry for the marker-409 confirmation), not from the reserved namespace.
- Document-tier inbox idempotent dedup (#220, ADR-0006/0007): a redelivered message with the same identity is handled exactly once. The `DocumentTierBatchLifecycleBehavior` now stamps a co-resident `CosmosInboxMarker` (`_chatterType="inbox"`, id `inbox:{encoded(MessageId)}` via the shared `CosmosItemId` encoder, the raw `MessageId` verbatim, a `ReceivedAtUtc` ISO-8601 instant; NO status field and NO TTL) into the framework-owned `TransactionalBatch` as op index 0 — BEFORE the handler runs — for a participant command whose inbound message carries a usable identity, in the aggregate's partition so it rides the SAME batch as the aggregate + outbox writes and commits atomically with the business write (no TOCTOU; dedup is closed-by-construction via the create-conflict, NOT a read-then-add). At batch-execute time the response inspection decides ack-vs-redeliver: a 409 Conflict on the MARKER op (index 0) is a CANDIDATE duplicate that is then CONFIRMED by point-reading the conflicting doc — it is acked without re-handling (no throw, no redeliver) ONLY when that doc is a genuine Chatter inbox marker (its `_chatterType` equals `inbox` AND its `MessageId` equals the inbound message id), the all-or-nothing batch having failed so nothing committed; a marker-409 whose conflicting doc is NOT a confirmed marker (an app-authored reserved-prefix collision), a NOT-FOUND read, or any other non-success read redelivers instead of being swallowed. An aggregate ETag/412, a 409 on a NON-marker op, a marker 424 failed-dependency, no per-op results, or any other non-success still throws `CosmosBatchExecutionException` so the transport redelivers/retries (conflating the marker 409 with an aggregate 412 would be silent message loss, so only a CONFIRMED marker-op 409 is swallowed). A participant command MUST carry a non-empty `MessageId`: a participant that resolves a partition but has a null/whitespace `MessageId` cannot be deduped by identity, so the once-only guarantee cannot be honored — the behavior rejects it loudly with `InvalidOperationException` BEFORE the batch is opened (nothing staged, the handler never runs, nothing acked), matching the in-memory tier which throws. The marker's `type="inbox"` discriminator keeps markers out of the #222 change-feed relay (which drains `type="outbox"`) by construction. The fresh-node partition-key stamping primitive is extracted into a shared `CosmosPartitionKeyStamping` helper used by both the outbox document and the inbox marker (each passing its own reserved-root-field collision-guard set; no duplication); the outbox wire shape and stamping behavior are unchanged. `CosmosInboxDeduplicator` realizes the tier-neutral `IInboxDeduplicator` contract TYPE for parity/discoverability but is intentionally NOT DI-registered — the document tier never resolves `IBrokeredMessageInbox`/`IInboxDeduplicator` (a cast-facet of the single resolved store the document tier does not register), so registering it would violate core's resolves-to-null cast-at-consumption invariant; its `HasBeenReceived` throws `NotSupportedException` because a read-then-add would reintroduce the TOCTOU this design eliminates. An app-configurable dedup-window TTL on markers is a deferred design point.
- Per-command document-tier participation registry and multi-container model (#238, ADR-0008): document-tier reliability is now opt-in PER COMMAND TYPE via a positive allowlist. `WithCosmosDocumentReliability<TCommand>(database, container, lease, resolver, partitionKeyPath...)` adds one registration per participating command type to a singleton `DocumentReliabilityRegistry`; participation IS having a registration, so a command type without one bypasses the document tier entirely (no resolver call, no batch). Multiple single-partition containers are supported — many command types may map to one container, but exactly one registration exists per command type (a duplicate registration for the same command type throws). Container handles are DERIVED (never provisioned) from the app-registered `CosmosClient` singleton via `client.GetContainer(database, container)` by the new singleton `CosmosContainerFactory`, cached thread-safely per `(database, container)`; the application owns the `CosmosClient` lifecycle and the existence of the database/container/lease (a documented prerequisite — the provider registers no client). ADR-0007's single-aggregate/single-partition hard constraint is unaffected; the registry adds container selection, not cross-partition atomicity.
- Document-tier outbox enqueue (#219): `CosmosBrokeredMessageOutbox` realizes `IBrokeredMessageOutbox.SendToOutbox` by resolving the active doc-tier atomic-write handle from the reliability surface and contributing the Chatter-owned outbox document's `CreateItemStream` op to the framework-owned `TransactionalBatch` (it never executes the batch — the Document-Tier Batch-Lifecycle Behavior owns the single commit point). The outbox is container-agnostic — it stages onto whatever container the behavior opened the batch on, so it supports the multi-container registry above with no change. The outbox document (`CosmosOutboxDocument`) carries the `_chatterType="outbox"` discriminator, an `outbox:{encoded(MessageId)}` id via the shared Cosmos-id-safe encoder (`CosmosItemId`, reused by #220 for inbox markers), the raw `MessageId` verbatim, the `MessageContext` serialized with `ChatterJson.Options` (EF parity), the message body/destination/content-type, and `status="pending"`; the resolved partition-key value is stamped at the container's actual partition-key path (supporting a hierarchical path), not a fixed field. Registered as `IBrokeredMessageOutbox` with the outbox router in DI.
- Closed-by-construction staging contract on `ICosmosAtomicWriteHandle`: the framework-owned `TransactionalBatch` is no longer publicly reachable for op-adds. All staging goes through intent-revealing methods (`StageCreateItemStream`, `StageReplaceItem<T>`, `StagePatchItem`), each of which calls the corresponding SDK batch op AND increments `StagedOperationCount` in one indivisible action. The ack-on-uncommitted class — stage an op via the raw batch without calling a count method → empty-batch guard reads 0 → skips `ExecuteAsync` → acks with nothing committed — is impossible by construction. `StagedOperationCount` is read-only for the behavior's empty-batch guard only; callers may not manipulate it independently. `StageCreateItemStream` is the Chatter-owned wire-shape path (outbox, #220 inbox marker) and the only public create/upsert path. The `CosmosBatchExecutionException.StatusCode` response-inspection seam is unchanged — #220 can still distinguish a confirmed-duplicate inbox-marker 409. Closes the first of the two deferred P1 skeleton findings.
- Removed the typed `StageCreateItem<T>`/`StageUpsertItem<T>` from the public document-tier atomic-write surface pre-release: their reserved-namespace guard keyed on an explicit `id` parameter the Cosmos SDK ignores — the SDK derives the persisted physical id by serializing `item` and reading `item.id`, so the guarded parameter could diverge from what Cosmos persists and a reserved-prefix doc could be staged unguarded. The sole surviving public create/upsert path is the peek-guarded `StageCreateItemStream`, whose guard keys on the persisted `item.id`.
- Batch-response inspection in the Document-Tier Batch-Lifecycle Behavior: after the single `ExecuteAsync`, a non-success `TransactionalBatchResponse` throws `CosmosBatchExecutionException` so the message is not acked when the writes did not commit (a forced aggregate ETag/412 surfaces here). The inspection is structured as a clean seam so #220 can later distinguish a confirmed-duplicate inbox-marker 409. The empty-batch guard (skip `ExecuteAsync` when no op was staged) is preserved. Closes the second deferred P1 skeleton finding.

### Changed

- A document-tier participant with a resolved partition but a null/whitespace `MessageId` now FAILS LOUD (#220/#241, ADR-0007). Previously such a message stamped no inbox marker and proceeded — running the handler and committing the aggregate + outbox before acking — so a redelivery of the same identity-less message was undetectable (a silent once-only loss). The behavior now throws `InvalidOperationException` BEFORE opening the batch, so nothing is staged, the handler never runs, and nothing is acked. A participant without a `MessageId` is a protocol/config error, matching the in-memory tier which throws.
- The `ResolvePartitionKey` delegate is now Try/nullable (`PartitionKey?`): a `null` return means "no resolvable partition for this message", in which case the Document-Tier Batch-Lifecycle Behavior opens no batch and bare-passes-through to `next()`. The resolver is only ever invoked for registered participants, so the prior null-inbound NRE (an in-process command's `null` inbound message reaching an unguarded resolver) is eliminated by construction. `DocumentTierBatchLifecycleBehavior<TMessage>` is rewritten to be registry-gated: a registry miss is a bare pass-through; a registry hit resolves the partition key, derives the registration's container via `CosmosContainerFactory`, and opens the batch on it.
- The Cosmos DI registration no longer accepts eager `Container` instances. The eager two-`Container`-instance `WithCosmosDocumentReliability` overload is REMOVED in favor of deriving handles from the app-owned `CosmosClient`; a per-registration `Func<IServiceProvider, Container>` factory overload is kept for applications that resolve their containers from the service provider themselves. The single-container DI holders (`DocumentContainer` / `LeaseContainer`) are superseded by the registry + factory and removed.

### Fixed

- Silent first-delivery loss on an app-authored reserved-prefix collision (#220/#241, ADR-0007). A marker-op 409 at batch-execute is no longer treated as a duplicate by inference: the Document-Tier Batch-Lifecycle Behavior now CONFIRMS the duplicate by point-reading the conflicting document and acks it as a duplicate ONLY when that doc is a genuine Chatter inbox marker (its `_chatterType` equals `inbox` AND its `MessageId` equals the inbound message id). Because the application owns the container (it registers the `CosmosClient` the container is derived from, and the atomic-write handle exposes the raw `Container`), an app could author a doc with an `inbox:{encoded(MessageId)}` id through a non-staging path no staging guard can close; its create would 409 the framework's marker create, and inferring "duplicate" from that bare 409 silently lost the colliding message's first delivery. With confirmation, an app-authored `inbox:`-prefixed collision is detected and redelivered, not silently dropped; a NOT-FOUND read (a TTL/delete race) or any other non-success read is non-confirmable and likewise redelivers. The point-read is cold-path-only (runs solely on the 409 branch) and is NOT a TOCTOU — the atomic create already failed, so the read only disambiguates why and gates no subsequent write. No wire-shape change.
- Non-participant dispatch no longer throws from the Cosmos outbox, regardless of registration order (#238, #239, ADR-0008). `WithCosmosDocumentReliability<T>` globally replaces the outbound `IRouteBrokeredMessages`, but only PARTICIPANT command types open a document-tier batch (which sets the surface handle); previously a NON-registered command whose handler Send/Published routed straight into `CosmosBrokeredMessageOutbox`, which threw `InvalidOperationException` on the null handle — contradicting "a command type without a registration bypasses the document tier entirely". Routing is now gated by a closed-by-construction `HandleGatedOutboxRouter` decorator: when the surface handle is null (every non-participant dispatch, and every dispatch after a participant's batch scope closes) routing delegates to a directly-constructed default broker router — a plain `BrokeredMessageRouter` over the always-`AddMessageBrokers`-registered `IMessagingInfrastructureProvider`, resolved lazily inside the registration factory at dispatch time — so a non-participant command dispatches straight to the broker exactly as if Cosmos were not installed; only a participant's mid-batch dispatch (handle set) routes through the Cosmos outbox — unchanged. Because the inner-default arm is constructed directly and never depends on `IBrokeredMessageOutbox`, the wiring is registration-order-independent: it behaves identically whether `AddChatterCqrs` (which runs the Cosmos pipeline callback) or `AddMessageBrokers` runs first, and whether `RouteMessagesToOutbox` is on or off. (This replaces the prior capture-the-core-default-descriptor approach, which was broken on both ends: the pipeline callback runs before `AddMessageBrokers` registers the default router, so the captured descriptor was null and threw; and under `RouteMessagesToOutbox` the rebuilt inner resolved the already-replaced Cosmos outbox and still threw on the null handle.) The factory `Replace` is idempotent-in-effect across multiple `WithCosmosDocumentReliability<T>` calls (exactly one router descriptor, never double-wrapped). The mixed configuration "`RouteMessagesToOutbox=true` + Cosmos provider + a separate non-Cosmos outbox" is UNSUPPORTED. The `CosmosBrokeredMessageOutbox` null-handle throw is retained as a hard wiring-error guard the decorator now ensures non-participants never reach.
- Multi-message outbox drain (#219): each outbox document in a `SendToOutbox` call with two or more messages now stamps its own freshly-derived partition-key node (minted per document from a detached `JsonElement`). Previously, shared `JsonNode` instances resolved once in `SendToOutbox` were re-stamped across documents; on the second message the already-parented node threw, the batch never executed, and the message redelivered forever. Cross-document node re-parenting is now structurally impossible — the `JsonElement` value type carries no parent reference, and each `ToJsonObject` call mints a fresh `JsonNode` at stamp time.
