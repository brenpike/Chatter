# Chatter.MessageBrokers.AzureServiceBus — Characterization Findings

This document is a pure observation log produced during behavior-pinning (characterization) testing of `Chatter.MessageBrokers.AzureServiceBus`. Every row records **current behavior as-is** — not desired or corrected behavior. The only production-source change made was adding `[assembly: InternalsVisibleTo("Chatter.MessageBrokers.AzureServiceBus.Tests")]` (mirroring the `Chatter.CQRS` / `Chatter.MessageBrokers` precedent); no behavior was altered. Tests that pin these behaviors live under `src/Chatter.MessageBrokers.AzureServiceBus/tests/`. Each finding is flagged here for human review and prioritization; no code fix is prescribed.

| # | Unit | Pinned behavior | Why suspicious | Pinning test | Suggested follow-up |
|---|------|-----------------|----------------|--------------|---------------------|
| 1 | `ServiceBusOptionsBuilder.Build()` | Throws the bare base `System.Exception` (message `"A connection string is required."`) when no connection string is supplied inline or via config | A bare `System.Exception` cannot be caught selectively by callers; sibling validation elsewhere uses `ArgumentException`/specific types | `Options/UsingServiceBusOptionsBuilder/WhenBuilding.cs::MustThrowBareExceptionWhenNoConnectionStringInlineOrConfig`, `MustThrowExactlyBaseExceptionTypeForMissingConnectionString` | Throw a specific exception type (e.g. `ArgumentException` or a custom `MissingConnectionStringException`) so callers can handle it distinctly |
| 2 | `ServiceBusOptions.RetryPolicy` (config binding) | The `internal` `RetryPolicy` property never binds via `section.Get<ServiceBusOptions>()` (the config binder skips internal setters), so `PostConfiguration` ALWAYS takes its first branch and `Policy` is a fresh `RetryExponential` (`RetryPolicy.Default`) regardless of config — even an all-zero `RetryPolicy` section does NOT yield `NoRetry` | The `all-zero -> NoRetry` and `populated -> mapped RetryExponential` branches of `PostConfiguration` are dead code via config; retry configuration through `appsettings` is silently ignored | `Options/UsingServiceBusOptionsBuilder/WhenBuilding.cs::MustLeavePolicyAsRetryExponentialWhenRetryPolicySectionAllZero`, `MustLeavePolicyAsRetryExponentialWhenRetryPolicySectionPopulated`, `MustLeavePolicyAsRetryExponentialWhenSectionAbsent` | Make `RetryPolicy` a public-settable property (or bind it explicitly), or document that retry policy is configurable only via the `WithNoRetry()` / `WithExponentialDelay()` fluent setters |
| 3 | `ServiceBusOptionsBuilder.PostConfiguration` all-zero branch | When (hypothetically) reached, an all-zero `RetryPolicyConfiguation` maps to `RetryPolicy.NoRetry`, silently disabling all retries | Zero-valued retry config silently disabling retries is a footgun; combined with finding #2 it is currently unreachable from config | (dead via config binding — pinned only indirectly through the all-zero test in finding #2, which confirms NoRetry is NOT produced) | If the binding is fixed (finding #2), require an explicit opt-in for no-retry rather than inferring it from all-zero values |
| 4 | `NullTokenProvider.GetTokenAsync` | Returns a hardcoded dummy `SecurityToken` with `TokenValue == "token"`, `Audience == "audience"`, and an `ExpiresAtUtc` derived from `DateTime.Now` (non-deterministic, local time not UTC) | A real token provider must produce valid tokens; this no-op uses a local-time, non-deterministic expiry and constant dummy values — only safe because it is gated out whenever the connection string carries SAS | `UsingNullTokenProvider/WhenGettingToken.cs::MustReturnTokenWithHardcodedTokenValue`, `MustReturnTokenWithHardcodedAudience` (expiry intentionally not pinned) | Document that `NullTokenProvider` is a sentinel no-op; if an expiry is meaningful, use `DateTime.UtcNow` and a deterministic offset |
| 5 | `ServiceBusRetryExceptionPredicatesProvider` / `ServiceBusCircuitBreakerExceptionPredicatesProvider` | The two providers' `GetExceptionPredicates()` bodies are byte-for-byte identical (same four `IsTransient`-gated predicates) | Duplicated logic across two types invites drift if one is updated and the other is not | `Receiving/Retry/UsingServiceBusRetryExceptionPredicatesProvider/WhenProvidingPredicates.cs::MustProvideExactlyFourPredicates` (+ siblings), `Receiving/CircuitBreaker/UsingServiceBusCircuitBreakerExceptionPredicatesProvider/WhenProvidingPredicates.cs::MustProvideExactlyFourPredicates` (+ siblings) | Extract the shared predicate set into a single helper consumed by both providers |
| 6 | `ServiceBusRetryExceptionPredicatesProvider` / `ServiceBusCircuitBreakerExceptionPredicatesProvider` (non-transient coverage gap) | The "no match when `IsTransient == false`" path could only be pinned for `ServiceBusException` (which exposes a `bool isTransient` ctor). `ServiceBusCommunicationException`, `ServerBusyException`, and `ServiceBusTimeoutException` hardcode `IsTransient == true` in the v5.2.0 SDK with no public ctor/setter to construct a non-transient instance, so their non-transient rejection branch is not constructible in a test | The `&& exception.IsTransient` clause is untestable (and effectively a no-op) for three of the four predicates given the SDK's hardcoded transience | `Receiving/Retry/.../WhenProvidingPredicates.cs::MustNotMatchNonTransientServiceBusException` (only `ServiceBusException` is pinnable; the other three pin only the transient-match path) | None actionable in product code; documented as an SDK constraint — revisit if the SDK adds non-transient construction for these subclasses |
| 7 | `OutboundBrokeredMessageExtensions.AsAzureServiceBusMessage` | Setting a `GroupId` (mapped to the SDK `Message.SessionId`) with no `PartitionKey` supplied maps `SessionId` from the `GroupId` and leaves `PartitionKey` unassigned -- no throw. Setting a `GroupId` together with a matching, non-empty `PartitionKey` maps both. Only a `GroupId` set alongside a *different*, non-empty `PartitionKey` throws, and it throws the SDK's `ArgumentOutOfRangeException` (`"PartitionKey:{value} cannot be set to a different value than SessionId:{SessionId}."`) from `set_PartitionKey`, not `InvalidOperationException` | Root cause of production issue #262: prior to the fix, any caller that set only a `GroupId` without an explicit `PartitionKey` got a hard SDK exception at send time. A residual gap remains: an explicit, genuinely mismatched `PartitionKey` still surfaces the raw SDK `ArgumentOutOfRangeException` rather than a validated, domain-specific error | `Sending/UsingOutboundBrokeredMessageExtensions/WhenMappingToAzureServiceBusMessage.cs::MustMapSessionIdFromGroupIdWhenNoPartitionKey`, `MustMapSessionIdFromGroupIdWhenPartitionKeyMatches`, `MustThrowWhenGroupIdSetWithDifferentPartitionKey` | RESOLVED in v1.4.1 (issue #262): `AsAzureServiceBusMessage` now only assigns `PartitionKey` on the SDK message when a partition key was actually supplied via `WithPartitionKey`, letting the mapped `SessionId` stand in for it when absent. A genuine mismatch -- a `GroupId` set alongside a different, non-empty `PartitionKey` -- still throws, but as the SDK's actual `ArgumentOutOfRangeException`, the type this document previously and incorrectly recorded as `InvalidOperationException` |
