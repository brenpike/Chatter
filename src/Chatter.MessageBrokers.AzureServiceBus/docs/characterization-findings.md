# Chatter.MessageBrokers.AzureServiceBus — Characterization Findings

This document is a pure observation log produced during behavior-pinning (characterization) testing of `Chatter.MessageBrokers.AzureServiceBus`. Every row records **behavior as-is** — not desired behavior — and is kept current as the code changes. The only production-source change made during the audit itself was adding `[assembly: InternalsVisibleTo("Chatter.MessageBrokers.AzureServiceBus.Tests")]` (mirroring the `Chatter.CQRS` / `Chatter.MessageBrokers` precedent); no behavior was altered. Tests that pin these behaviors live under `src/Chatter.MessageBrokers.AzureServiceBus/tests/`. Each finding was flagged here for human review and prioritization.

A finding that has since been addressed keeps its row: the *Pinned behavior* column is rewritten to describe what the code does now, the original observation is retained in *Why suspicious*, and the *Suggested follow-up* column carries the disposition together with the version or commit that landed it. A finding whose subject no longer exists at all is removed rather than rewritten, and no row may cite a test or type that is absent from the tree. Row numbers are stable and are never reused: finding **4** (`NullTokenProvider.GetTokenAsync`) was removed outright — neither the type nor its cited pinning test survived the `42b761e` migration to `Azure.Messaging.ServiceBus` — and rows 5-7 deliberately keep their original numbers so existing references still resolve.

| # | Unit | Pinned behavior | Why suspicious | Pinning test | Suggested follow-up |
|---|------|-----------------|----------------|--------------|---------------------|
| 1 | `ServiceBusOptionsBuilder.Build()` | Throws the bare base `System.Exception` (message `"A connection string is required."`) when no connection string is supplied inline or via config | A bare `System.Exception` cannot be caught selectively by callers; sibling validation elsewhere uses `ArgumentException`/specific types | `Options/UsingServiceBusOptionsBuilder/WhenBuilding.cs::MustThrowBareExceptionWhenNoConnectionStringInlineOrConfig`, `MustThrowExactlyBaseExceptionTypeForMissingConnectionString` | Throw a specific exception type (e.g. `ArgumentException` or a custom `MissingConnectionStringException`) so callers can handle it distinctly |
| 2 | `ServiceBusOptions.RetryPolicy` (config binding) | A populated `Chatter:Infrastructure:AzureServiceBus:RetryPolicy` section binds and reaches `PostConfiguration`, which turns it into matching `ServiceBusRetryOptions`. An absent section leaves `RetryOptions` unset, an empty section falls back to the SDK defaults, and a `RetryOptions` key in configuration is ignored in favour of the `RetryPolicy`-derived options | ORIGINAL FINDING, since fixed: the `internal` `RetryPolicy` property never bound, because `Build()` replaced the whole instance via `section.Get<ServiceBusOptions>()` and the configuration binder skips non-public setters. `PostConfiguration` always took its first branch, every other branch was dead code, and retry tuning supplied through `appsettings` was silently discarded | `Options/UsingServiceBusOptionsBuilder/WhenBuilding.cs::MustApplyConfiguredRetryPolicyWhenSectionPopulated`, `MustLeaveRetryOptionsUnsetWhenSectionAbsent`, `MustFallBackToSdkDefaultRetryOptionsWhenRetryPolicySectionEmpty`, `MustIgnoreConfiguredRetryOptionsWhenRetryPolicyConfigured` | RESOLVED in v2.2.0 (issue #313, epic #296): `Build()` now binds INTO the default-initialized instance with `BindNonPublicProperties = true` rather than replacing it, so the internal property genuinely binds and keys the section omits keep their defaults |
| 3 | `ServiceBusOptionsBuilder.PostConfiguration` (no-retry inference) | An all-zero `RetryPolicyConfiguration` section no longer disables retry: each parameter falls back to the SDK default unless a value greater than zero was configured, and retry is switched off from configuration ONLY through the explicit `RetryPolicy:NoRetry` boolean. `DeltaBackoffInSeconds` is still accepted and still ignored — the SDK retry model has no per-attempt delta-backoff knob | ORIGINAL FINDING, since fixed: an all-zero `RetryPolicyConfiguration` mapped to `RetryPolicy.NoRetry`, silently disabling all retries. Zero-valued retry configuration disabling retry is a footgun, and it was unreachable from configuration only because of finding #2 | `Options/UsingServiceBusOptionsBuilder/WhenBuilding.cs::MustFallBackToSdkDefaultRetryOptionsWhenRetryPolicyAllZeroWithoutNoRetryOptIn`, `MustDisableRetryWhenRetryPolicyNoRetryOptInConfigured`, `MustPreferFluentNoRetryOverConfiguredRetryPolicy` | RESOLVED in v2.2.0 (issue #313, epic #296): an explicit `RetryPolicy:NoRetry` opt-in replaced the inference, and the inference is gone by construction — no combination of configured numbers can derive `MaxRetries = 0` |
| 5 | `ServiceBusRetryExceptionPredicatesProvider` / `ServiceBusCircuitBreakerExceptionPredicatesProvider` | The two providers' `GetExceptionPredicates()` bodies are byte-for-byte identical (the same four `ServiceBusException` predicates — one gated on `IsTransient`, three on a `ServiceBusFailureReason`) | Duplicated logic across two types invites drift if one is updated and the other is not | `Receiving/Retry/UsingServiceBusRetryExceptionPredicatesProvider/WhenProvidingPredicates.cs::MustProvideExactlyFourPredicates` (+ siblings), `Receiving/CircuitBreaker/UsingServiceBusCircuitBreakerExceptionPredicatesProvider/WhenProvidingPredicates.cs::MustProvideExactlyFourPredicates` (+ siblings) | Extract the shared predicate set into a single helper consumed by both providers |
| 6 | `ServiceBusRetryExceptionPredicatesProvider` / `ServiceBusCircuitBreakerExceptionPredicatesProvider` (non-transient coverage) | The "no match when the exception is not transient" path is pinnable directly: a `ServiceBusException` carrying `ServiceBusFailureReason.GeneralError` matches none of the four predicates. Only the first predicate gates on `IsTransient`; the other three key on a specific `ServiceBusFailureReason` | ORIGINAL FINDING, since dissolved: under the v5.2.0 `Microsoft.Azure.ServiceBus` SDK, `ServiceBusCommunicationException`, `ServerBusyException`, and `ServiceBusTimeoutException` hardcoded `IsTransient == true` with no public constructor or setter for a non-transient instance, so their rejection branch could not be constructed in a test | `Receiving/Retry/UsingServiceBusRetryExceptionPredicatesProvider/WhenProvidingPredicates.cs::MustNotMatchNonTransientServiceBusException`, `Receiving/CircuitBreaker/UsingServiceBusCircuitBreakerExceptionPredicatesProvider/WhenProvidingPredicates.cs::MustNotMatchNonTransientServiceBusException` | RESOLVED by the `42b761e` migration to `Azure.Messaging.ServiceBus` 7.20.2: the v5 exception hierarchy collapsed into a single `ServiceBusException` carrying a `ServiceBusFailureReason`, so the three uninstantiable subclasses no longer exist and the coverage gap is gone |
| 7 | `OutboundBrokeredMessageExtensions.AsAzureServiceBusMessage` | Setting a `GroupId` (mapped to `ServiceBusMessage.SessionId` in `Azure.Messaging.ServiceBus` 7.20.2) with no `PartitionKey` supplied maps `SessionId` from the `GroupId` and leaves `PartitionKey` unassigned -- no throw. Setting a `GroupId` together with a matching, non-empty `PartitionKey` maps both. Only a `GroupId` set alongside a *different*, non-empty `PartitionKey` throws, and it throws the SDK's `ArgumentOutOfRangeException` (`"PartitionKey:{value} cannot be set to a different value than SessionId:{SessionId}."`) from `set_PartitionKey`, not `InvalidOperationException` | Root cause of production issue #262: prior to the fix, any caller that set only a `GroupId` without an explicit `PartitionKey` got a hard SDK exception at send time. A residual gap remains: an explicit, genuinely mismatched `PartitionKey` still surfaces the raw SDK `ArgumentOutOfRangeException` rather than a validated, domain-specific error | `Sending/UsingOutboundBrokeredMessageExtensions/WhenMappingToAzureServiceBusMessage.cs::MustMapSessionIdFromGroupIdWhenNoPartitionKey`, `MustMapSessionIdFromGroupIdWhenPartitionKeyMatches`, `MustThrowWhenGroupIdSetWithDifferentPartitionKey` | RESOLVED in v1.4.1 (issue #262): `AsAzureServiceBusMessage` now only assigns `PartitionKey` on the SDK message when a partition key was actually supplied via `WithPartitionKey`, letting the mapped `SessionId` stand in for it when absent. A genuine mismatch -- a `GroupId` set alongside a different, non-empty `PartitionKey` -- still throws, but as the SDK's actual `ArgumentOutOfRangeException`, the type this document previously and incorrectly recorded as `InvalidOperationException` |
