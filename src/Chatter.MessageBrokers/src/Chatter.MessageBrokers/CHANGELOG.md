## [0.27.0] - 2026-09-09

### Added

- **Two new `ReliabilityOptions` settings bound the shipped in-memory Inbox now that it is process-lifetime (see Fixed, below): `InMemoryInboxDeduplicationWindowInMinutes` (fluent `WithInMemoryInboxDeduplicationWindow(int)`, config key `Chatter:MessageBrokers:Reliability:InMemoryInboxDeduplicationWindowInMinutes`, default `60`) and `InMemoryInboxMaxEntries` (fluent `WithInMemoryInboxMaxEntries(int)`, config key `Chatter:MessageBrokers:Reliability:InMemoryInboxMaxEntries`, default `200000`).** After a receipt completes, a redelivery of the same message id is skipped for the Deduplication Window. **That window is mandatory and must be at least one minute: a configured value below `1` is refused while the options are being built**, pinned by `MustRefuseAConfiguredInMemoryInboxDeduplicationWindowOfZero`, `MustRefuseAConfiguredNegativeInMemoryInboxDeduplicationWindow` and `MustRefuseANestedInMemoryInboxDeduplicationWindowAndPublishNothingWhenTheParentSectionCarriesIt`; `1` itself is accepted, pinned by `MustAcceptTheSmallestInMemoryInboxDeduplicationWindowTheSettingCanExpress`. It is deliberately not read as "disabled" the way a non-positive `MinutesToLiveInMemory` is — that setting governs cleanup of outbox rows already processed and is unchanged by this release, whereas the window is the inbox's ONLY reclamation rule, so a window that could be switched off would leave entries, and a hung handler's reservation in particular, that nothing was able to remove. The entry cap is a memory safety valve rather than the deduplication guarantee: under memory pressure it evicts completed-but-unexpired receipts to bound memory, which truncates the advertised window, so a redelivery inside it can be handled again once its receipt has been evicted — an eviction of that kind logs a warning exactly once per store, pinned by `MustWarnExactlyOnceAcrossRepeatedCapEvictions`, and reclaims already-expired entries before it evicts any unexpired one, pinned by `MustReclaimExpiredEntriesBeforeEvictingUnexpiredOnesAndNotWarn`. A configured cap below `1` is refused at build time, pinned by `MustRefuseAConfiguredInMemoryInboxMaxEntriesOfZero` and `MustRefuseAConfiguredNegativeInMemoryInboxMaxEntries`; `1` itself is accepted, pinned by `MustAcceptTheSmallestInMemoryInboxMaxEntriesTheInboxCanHold`. An in-flight reservation — a receipt whose handler has not yet returned — is LEASED by that same Deduplication Window rather than held indefinitely, so the setting states one rule for both states: an id is remembered for the window, and a reservation is honoured for the window. Inside the window a reservation is never expired and never evicted, whatever pressure the store is under, pinned by `MustNeverReclaimAnInFlightReservationInsideTheWindow` and `MustNeverEvictAnInFlightReservationAtTheCap`, and the store grows past its configured cap without throwing or blocking while every entry holds such a reservation, pinned by `MustGrowPastTheCapWithoutThrowingWhenEveryEntryIsInFlight`. Once the window has elapsed the reservation is abandoned and becomes reclaimable on exactly the terms an expired receipt is, so a handler that has not returned holds its message id for the window and no longer: the redelivery is handled again, pinned by `MustHandleARedeliveryOfAnAbandonedInFlightReservationOnceTheWindowHasElapsed`; `HasBeenReceived` reports `false` for it, pinned by `MustReportHasBeenReceivedFalseForAnAbandonedInFlightReservation`; the routine sweep reclaims it, pinned by `MustReclaimAnAbandonedInFlightReservationOnTheNextSweep`; and enforcing the cap reclaims it instead of evicting an unexpired receipt, pinned by `MustReclaimAnAbandonedInFlightReservationRatherThanEvictAnUnexpiredReceiptAtTheCap`. Because the window is mandatory and positive, there is no configuration under which a reservation outlives it, pinned across the ends of the configurable range by `MustNeverHoldAnInFlightReservationBeyondTheWindowUnderEveryConfigurableWindow` and `MustHandleARedeliveryOnceTheWindowHasElapsedUnderEveryConfigurableWindow`, and the store's growth past its cap while every entry is in flight is therefore bounded in time rather than merely tolerated, pinned by `MustReturnToItsCapOnceTheWindowElapsesForTheEntriesThatGrewPastIt`. **The lease does not distinguish a dead handler from a slow one.** A merely slow but perfectly live handler is pre-empted on exactly the same terms once its lease elapses: a second handler for that message id then runs concurrently with the first, and the first one's completion is silently discarded when it eventually arrives, because the conditional update it makes no longer matches the reservation it took. **Migration:** a handler that can run longer than the Deduplication Window must be idempotent, and the window should be sized above the slowest handler expected to run behind the inbox. What a concurrent delivery does is unchanged: one that meets a reservation the window still honours is skipped immediately, without waiting for that reservation's owner and without taking the delivery over from it (#300, #327, #328, #441).

### Fixed

- **The shipped in-memory Outbox and Inbox were registered per-scope while their whole state lived in a per-instance dictionary, so the drain and the deduplication described in the entries below never actually ran.** `InMemoryBrokeredMessageOutbox` and `InMemoryBrokeredMessageInbox` keep their entire state in a single per-instance `ConcurrentDictionary`, but every consumer of a reliability store opens a fresh scope per operation — `BrokeredMessageOutboxProcessor` opens one scope per poll, and the received-message dispatcher opens one scope per delivery. A row sent to the Outbox in one scope was invisible to the poll resolved in a later scope, so the poller always found an empty Outbox to drain; a message id received in one scope was invisible to the dispatcher resolved for the next delivery's scope, so the Inbox deduplicated nothing across redeliveries. Both shipped defaults now carry the internal `IProcessLifetimeStore` marker, and `AddMessageBrokers` promotes any default carrying it to a process-lifetime registration, so the same instance — and the same dictionary — is resolved from every scope for the lifetime of the process; a custom store an application registers itself keeps whatever lifetime it was registered with. Pinned by `InboxDefault_ResolvesSameInstanceAcrossScopes`, `InboxDefault_SkipsADuplicateReceivedInASecondScope`, `CustomScopedInbox_KeepsItsOwnLifetime`, `OutboxDefault_ResolvesSameInstanceAcrossScopes` and `OutboxDefault_RowSentInOneScopeIsDrainedByTheProcessorResolvedInAnother` (#300, #327, #328, #441).
- **The default in-memory Outbox never dispatched anything.** `OutboxProcessor` obtains the Unit of Work by casting the resolved Outbox (Reliability-Store Facet Resolution), and `InMemoryBrokeredMessageOutbox` implemented no facet satisfying that cast, so the cast threw `InvalidCastException` on every poll. `OutboxProcessor` wraps its polling pass in a catch-and-log, so that failure never surfaced as anything beyond one swallowed log line, and the shipped default Outbox was a permanent no-op out of the box. `InMemoryBrokeredMessageOutbox` now also implements `IUnitOfWork`: it has nothing of its own to enlist, so its `ExecuteAsync` runs the supplied operation as-is and lets that operation's own failure travel out unchanged, rather than wrapping it in a transaction the in-memory store cannot honor. Pinned by `WhenDrainingTheDefaultInMemoryOutbox`, `WhenExecutingUnitOfWork` and `WhenResolvingReliabilityStores`. This facet is what makes a drain CORRECT once one runs; it is the entry above that makes a drain REACHABLE at all, since until that fix the Outbox this facet was added to was a fresh, empty instance in every polling scope — neither half was observable in production before both landed (#300, #327, #328, #441).
- **A dispatch that fails is no longer recorded as processed.** `OutboxProcessor` stamped a message's processed date BEFORE publishing it, so a publish failure still marked the message processed — the surrounding catch-and-log swallowed the failure, and a message that never reached the broker was never retried and never seen again. The drain now publishes first and stamps the processed date only once the publish has returned, so a failed publish leaves the row retryable on the next poll instead of silently losing the message. Pinned by `WhenDrainingTheDefaultInMemoryOutbox` (#300, #327, #328).
- **The in-memory Inbox no longer throws `InvalidOperationException` when one message id is received concurrently.** `InMemoryBrokeredMessageInbox` checked whether an id was already present, ran the message receiver, and only then tried to add the id — so two concurrent receipts of the same id both passed the check, both ran the receiver, and the loser's `TryAdd` failed and raised `InvalidOperationException` ("Unable to retrieve brokered message...") instead of being deduplicated. Pinned by `WhenReceivingConcurrently`. The reservation this fix takes is what makes the deduplication CORRECT once a redelivery reaches the same instance; it is the root-cause entry above that makes a redelivery reach the same instance at all, since until that fix a redelivery arrived in a fresh scope and found an empty Inbox — neither half was observable in production before both landed (#300, #327, #328, #441).
- **A redelivery whose expired entry a concurrent sweep reclaimed is no longer mistaken for a duplicate and dropped.** The reserve path re-reserves an expired entry with a value-conditional `ConcurrentDictionary.TryUpdate`, and `TryUpdate` reports `false` in two different situations: when the comparison value no longer matches, and when the key is absent altogether. A sweep — elected by another receipt, or run by cap enforcement — that removed the expired entry between this delivery's read of it and its update therefore failed that update with no competing reservation in existence anywhere, so the delivery traced "was already received", returned without invoking the receiver, and the message was acked as handled and silently lost. It was reachable in ordinary steady state, right after a window elapsed under concurrent load, which is precisely when expired entries exist and the sweep is due. The reserve path now makes one further add attempt when that update fails: an add that succeeds means the entry had been swept and this delivery holds a fresh reservation, and an add that fails means a genuine concurrent duplicate. The budget stays bounded at two add attempts, so a receipt still cannot spin against the sweep. Pinned by `MustHandleARedeliveryWhoseExpiredEntryASweepReclaimsWhileItIsBeingReReserved` and `MustNotReportASweptEntryAsAnAlreadyReceivedDuplicate`, which drive that interleaving through an internal seam the store exposes only to a test rather than through timing (#300, #327, #328, #441).

### Changed

- **Polling drains are now genuinely at-least-once. A mark or commit failure AFTER a successful publish, and concurrent multi-instance relational polling, can now DUPLICATE a delivery that the previous pre-dispatch claim used to suppress.** The Fixed entry above trades a silent, unrecoverable loss for a possible duplicate: a message is now published, and only then claimed processed, so a failure between those two steps — recording the processed date, or committing that record — redelivers the message on the next poll rather than losing it, and the same window opens when more than one instance polls the same relational store concurrently. **Migration:** a handler behind a polling Outbox that is not already naturally idempotent should enable the Inbox, which is exactly the mechanism this context provides for once-only handling in the face of at-least-once delivery. Pinned by `WhenDrainingTheDefaultInMemoryOutbox` (#300, #327, #328).
- **The in-memory Inbox now RESERVES a message id before invoking the message receiver, and releases the reservation if the receiver throws.** Previously the id was added to the Inbox only after the receiver returned, so a concurrent duplicate delivery of the same id was invisible to `HasBeenReceived` for the receiver's entire duration and could run alongside it. The reservation is now taken up front: `HasBeenReceived` reports an IN-FLIGHT delivery as already received, so a concurrent duplicate now SKIPS rather than double-executing or throwing, and a receiver that itself throws releases its reservation so a genuinely failed delivery can still be retried. Pinned by `WhenReceivingConcurrently` (#300, #327, #328).
- **`InMemoryBrokeredMessageInbox` (public) now requires a `ReliabilityOptions` argument at construction. This is a breaking change to its constructor signature.** Bounding the Inbox with the deduplication window and entry cap added above requires reading both settings when the store is constructed, so `new InMemoryBrokeredMessageInbox(logger)` becomes `new InMemoryBrokeredMessageInbox(logger, reliabilityOptions)`. **Migration:** a consumer hand-constructing this type must add the new argument at every call site; a consumer resolving `IBrokeredMessageInbox` from the container — which is how `AddMessageBrokers` wires the shipped default — is unaffected, since the container supplies the new parameter itself. That argument must be a `ReliabilityOptions` produced by `ReliabilityOptionsBuilder`: every property on `ReliabilityOptions` has an internal setter and the documented defaults are the builder's, so a hand-constructed `new ReliabilityOptions()` carries a zero Deduplication Window and a zero entry cap. The constructor now REFUSES such an instance with `ArgumentOutOfRangeException` rather than returning an Inbox that deduplicates nothing, pinned by `MustThrowArgumentOutOfRangeExceptionWhenDeduplicationWindowIsNotPositive`, `MustThrowArgumentOutOfRangeExceptionWhenMaxEntriesIsNotPositive` and `MustThrowArgumentOutOfRangeExceptionWhenOptionsAreDefaultConstructed`. SemVer's `0.x` allowance permits a breaking constructor change of this kind in a MINOR rather than a MAJOR; see below (#300, #327, #328, #441).
- **`HasBeenReceived` now reports `false` once a completed receipt's Deduplication Window elapses, where it previously reported `true` for as long as the process ran.** A redelivery of a message id arriving after the window has elapsed is handled again rather than skipped forever. Pinned by `MustReportHasBeenReceivedTrueInsideTheWindowAndFalseAfterIt` and `MustHandleARedeliveryAgainOnceTheWindowHasElapsed`. The previous "handled once, forever" behaviour is NOT available under any configuration: the window is mandatory and at least one minute, so every retained id is eventually released. **Migration:** a handler that relied on being run exactly once for the lifetime of the process needs a durable inbox — the EF-backed `IBrokeredMessageInbox` in the sibling reliability package — rather than the in-memory one (#300, #327, #328, #441).
- **`SendToOutbox`'s `InvalidOperationException` on a repeated `MessageId` is now reachable in practice, because the shipped Outbox's dictionary now outlives the scope a message was sent in.** Previously every scope resolved its own empty dictionary, so a repeated `MessageId` sent from two different scopes never collided and this exception could only be observed within a single scope. It is deliberately kept loud rather than made idempotent or swallowed, exactly as before this release. `MinutesToLiveInMemory` is unchanged in meaning by this release, and now operates across polls rather than within a single, always-empty one, since the rows it expires live in the same process-lifetime dictionary the drain reads (#300, #327, #328, #441).
- **Why this is a MINOR rather than a MAJOR.** `InMemoryBrokeredMessageInbox`'s constructor gained a required parameter, which is a breaking change to a public type's public surface. Under SemVer's `0.x` allowance this package takes it as a MINOR rather than a MAJOR, exactly as the constructor and lifetime changes in prior 0.x releases have. The internal `IProcessLifetimeStore` marker and the registration extension that acts on it are NOT new public surface — both stay internal, and the fix they support is otherwise observable only as the shipped stores now working as documented (#300, #327, #328, #441).

## [0.26.0] - 2026-09-09

### Added

- **`ConfiguredValueRefusedException` (public, `Chatter.MessageBrokers.Exceptions`)** is the single named failure this package raises when an options builder refuses a configured value. It carries `OptionName` (the refused property, qualified by its options type — `ReliabilityOptions.OutboxProcessingIntervalInMilliseconds`), `RefusedValue`, `RequiredBound` and `ConfigurationPath` (the section the refusing builder actually resolved), and its `Message` contains all four — pinned by `MustNameTheRefusedPropertyValueBoundAndResolvedSectionPathWhenAConfiguredValueIsRefused` on both `ReliabilityOptionsBuilder` and `CircuitBreakerOptionsBuilder`. The path named is the one the builder RESOLVED rather than the documented section constant: a builder retargeted onto a custom section name reports that custom path, pinned by `MustNameTheResolvedCustomSectionPathWhenAConfiguredValueIsRefusedThroughACustomSectionName`. A nested builder composed by a parent has no section of its own, so `ConfigurationPath` is `null` there rather than fabricated, and the message omits the path clause — the option name still identifies the property in every case (#423).

### Changed

- **Seven configured values are now refused while the options are being built. A configuration that previously started the host and misbehaved later can now stop it from starting at all.** Each refusal raises `ConfiguredValueRefusedException` (above). The newly-refused keys, each with its migration path:
  - **`Chatter:MessageBrokers:TransactionMode`** must name or number a member `TransactionMode` defines. The configuration binder is loud only for a mode it cannot PARSE, so a numeric literal converted cleanly to an undefined member of this byte-backed enum and reached the `TransactionContext` the receiver builds. *Migration:* use a defined member — every numeric value the enum defines is still accepted, pinned by `MustAcceptEveryNumericTransactionModeTheEnumDefines`; the refusal is pinned by `MustRefuseANumericTransactionModeTheEnumDoesNotDefine`.
  - **`Chatter:MessageBrokers:Reliability:OutboxProcessingIntervalInMilliseconds`** must be at least `0` when `EnableOutboxPollingProcessor` is on — the processor is the value's only reader and is registered only then, so a host with the poller off starts whatever the interval says, pinned by `MustAcceptAnOutOfRangeOutboxProcessingIntervalWhenTheOutboxPollingProcessorIsDisabled`. `BrokeredMessageOutboxProcessor` awaits `Task.Delay(interval)` with no `try` of its own, so anything below `-1` faulted the whole background service, and `-1` is `Timeout.Infinite`, which an ENABLED poller would wait on for good. *Migration:* state a non-negative interval; to stop polling, leave `EnableOutboxPollingProcessor` off rather than encoding "never" as `-1`. Pinned by `MustRefuseAConfiguredOutboxProcessingIntervalOfNegativeFive` and `MustAgreeWithTheOutboxPollingSinkAboutAConfiguredProcessingInterval`, which asks `Task.Delay` itself what it accepts.
  - **`Chatter:MessageBrokers:Reliability:MinutesToLiveInMemory`** refuses only a `NaN` and a positive `Infinity`; every finite value is accepted whatever its magnitude and whatever its sign. The `double` converter takes `"NaN"` and `"Infinity"` straight off a configuration section, and a `NaN` slips through the expiry scan's own `ttl <= 0` disable branch — every comparison against a `NaN` is false — to expire every message the instant it is processed. *Migration:* state any finite number of minutes; a non-positive one leaves expiry cleanup disabled. Pinned by `MustAgreeWithTheExpiryScanAboutAConfiguredMinutesToLiveInMemory`, `MustRefuseAConfiguredNaNMinutesToLiveInMemoryTheExpiryScanDoesNotDisableItselfFor` and `MustRefuseAConfiguredInfiniteMinutesToLiveInMemoryTheExpiryScanRunsWithoutFaulting`, each of which drives the real expiry scan.
  - **`Chatter:MessageBrokers:Recovery:MaxRetryAttempts`** must be at least `1`. `RetryStrategy` starts at attempt 1 and gives up once `attempts >= MaxRetryAttempts`, so every budget at or below `1` buys exactly one attempt: a `0` or a negative stated a budget the sink cannot express and disabled retry without saying so. *Migration:* state `1` where the previous value bought that single attempt, or the budget actually wanted. Pinned by `MustRefuseAConfiguredMaxRetryAttemptsBelowTheSmallestBudgetTheRetryStrategyCanExpress` and `MustAcceptTheSmallestMaxRetryAttemptsTheRetryStrategyCanExpress`, both of which derive the bound by running the real `RetryStrategy` and counting the attempts it allows rather than restating its accounting.
  - **`Chatter:MessageBrokers:Recovery:CircuitBreaker:ConcurrentHalfOpenAttempts`** must be at least `1`. The breaker turns this count into `new SemaphoreSlim(n, n)` and awaits it before every half-open trial: a negative threw out of the breaker's own constructor, and a `0` is a perfectly legal semaphore that admits nothing, so the host started and the first trial then blocked for good. *Migration:* state `1` or more. Pinned by `MustRefuseAConfiguredConcurrentHalfOpenAttemptsOfZero`, `MustRefuseAConfiguredNegativeConcurrentHalfOpenAttempts` and `MustAcceptTheSmallestConcurrentHalfOpenAttemptsTheSemaphoreAdmits`, each of which drives a real semaphore to establish the bound.
  - **`Chatter:MessageBrokers:Recovery:CircuitBreaker:OpenToHalfOpenWaitTimeInSeconds`** must be a number of seconds `Task.Delay` can wait — `0` through `4294967`, since the breaker hands this value to `Task.Delay` as a `TimeSpan`. *Migration:* state a non-negative wait inside that range. Pinned by `MustAgreeWithTaskDelayAboutAConfiguredOpenToHalfOpenWaitTime`, which asks `Task.Delay` itself rather than restating its accepted range.
  - **`Chatter:MessageBrokers:Recovery:CircuitBreaker:SecondsOpenBeforeCriticalFailureNotification`** must be a number of seconds `Timer.Change` can schedule — the same `0` through `4294967` range, since the breaker arms its critical-failure notification by handing this value, as a `TimeSpan`, to `Timer.Change`. *Migration:* state a non-negative number of seconds inside that range. Pinned by `MustAgreeWithTimerChangeAboutAConfiguredTimeOpenBeforeCriticalEvent`, which asks a real timer.

  A refused value that belongs to a NESTED builder and arrives through a parent's section publishes nothing, which is why validation is its own phase between resolving the graph and publishing it: pinned by `MustRefuseANestedCircuitBreakerValueAndPublishNothingWhenTheParentSectionCarriesIt` and `MustRefuseANestedReliabilityValueAndPublishNothingWhenTheParentSectionCarriesIt` on `MessageBrokerOptionsBuilder`, and `MustRefuseANestedCircuitBreakerValueAndPublishNothingWhenThisSectionCarriesIt` on `RecoveryOptionsBuilder`. `AddMessageBrokers` builds the options graph as it runs, so a host configured this way now fails there instead of starting.

  **Still accepted, and deliberately so.** An `OutboxProcessingIntervalInMilliseconds` of `0` — `Task.Delay` completes it immediately, so how aggressively the outbox is polled stays the operator's call. A non-positive `MinutesToLiveInMemory` — that IS the outbox's documented "expiry cleanup disabled" branch. An `OpenToHalfOpenWaitTimeInSeconds` of `0` — load-bearing since 0.24.0: a zero wait is always already elapsed, so an open circuit never refuses and the first call after opening goes straight to a trial, pinned by `MustAcceptAConfiguredOpenToHalfOpenWaitTimeOfZero`. And `NumberOfFailuresBeforeOpen` and `NumberOfHalfOpenSuccessesToClose` are NOT validated at any value: the state store counts them as `++count >= threshold`, so no value faults the sink and a non-positive threshold means "trip, or close, on the first", which is intent an operator is entitled to state — pinned by `MustAcceptAConfiguredCountThresholdOfZero` against a later sweep that would refuse every non-positive number on sight. `ReceiverOptions.MaxConcurrentCalls` is also unchanged by this release; it still surfaces from the receiver that initializes with it.

  **Why this is a MINOR rather than a MAJOR.** These refusals withdraw an accept this package DOCUMENTED. `src/README.md` shipped a section headed "No option value is semantically checked at build time", which stated that a right-typed but nonsensical value "is not checked at all" and named two of the exact cases now refused — a non-sensible outbox poll interval and a `ConcurrentHalfOpenAttempts` below `1`. Two tests existed for the sole purpose of recording those accepts, `MustAcceptAConfiguredOutboxProcessingIntervalOfNegativeFive` and `MustAcceptAConfiguredConcurrentHalfOpenAttemptsOfZero`; both were inverted in place into the refusal pins above rather than deleted, so the deferral record became the pin. Breaking a documented consumer expectation is a MAJOR trigger; under SemVer's `0.x` allowance this package takes it as a MINOR, which is why every newly-refused key is named with its migration path above (#423).
- **`RecoveryOptionsBuilder.UseExponentialDelayRecovery(int)` now tunes the delay strategy to the SAME clamped attempt budget it writes into the options.** The method clamps its argument to this package's exponential ceiling of 15 attempts, but it recorded the RAW argument for the strategy, so `UseExponentialDelayRecovery(30)` produced a `RecoveryOptions.MaxRetryAttempts` of `15` alongside a resolved `IRetryDelayStrategy` tuned to a 30-attempt schedule — a per-attempt delay ceiling far above the one the clamped budget implies. The ceiling is now applied once, into a local assigned to both the options field and the strategy argument. An argument at or below `15` resolves exactly the strategy it always did; only a caller passing more than `15` sees a change. Pinned by `MustTuneTheResolvedExponentialDelayStrategyToTheClampedMaxRetryAttempts`, which resolves the strategy out of the built provider and compares its delay cap against reference `ExponentialDelayRetry` instances built from the clamped budget and from the raw argument — both caps are longer than any test could wait for, so the pin compares the resolved cap rather than timing a delay (#423).

### Fixed

- **A large `MinutesToLiveInMemory` no longer stops the in-memory outbox dispatching anything.** `InMemoryBrokeredMessageOutbox` computed each message's expiry instant as `ProcessedFromOutboxAtUtc.AddMinutes(ttl)`, which throws an `ArgumentOutOfRangeException` once the ttl outruns what a `DateTime` can hold. `OutboxProcessor` calls `UpdateProcessedDate` inside its unit of work BEFORE it dispatches, and catches every exception around the whole block, so such a ttl stamped each message processed, logged one line and left it never dispatched — and, being stamped, never retried either. The scan now compares ELAPSED minutes against the ttl instead of computing an expiry instant, so it cannot overflow at any magnitude and a ttl no elapsed time can reach simply never expires anything. Pinned by `MustRetainProcessedMessageWithoutFaultingWhenMinutesToLiveOutrunsTheDateRange` (#423).

## [0.25.0] - 2026-09-08

### Changed

- **Nested options are no longer registered with the `IServiceCollection` until the whole options graph is finalized.** `MessageBrokerOptionsBuilder.AddReliabilityOptions(...)`, `AddRecoveryOptions(...)` and `RecoveryOptionsBuilder.WithCircuitBreaker(...)` used to `Build()` the sub-builder as the fluent call ran and register its result there and then, so the container carried a `ReliabilityOptions`, `RecoveryOptions` or `CircuitBreakerOptions` registration before the parent builder had bound its own configuration section over the graph. Each of the four options builders in this package — `MessageBrokerOptionsBuilder`, `ReliabilityOptionsBuilder`, `RecoveryOptionsBuilder` and `CircuitBreakerOptionsBuilder` — now separates composition from publication behind an internal `Resolve()`, which produces the finalized options without touching the container. The registration site that follows `Resolve()` is a named internal `Publish(TOptions)` on the three CHILD builders — `ReliabilityOptionsBuilder`, `RecoveryOptionsBuilder` and `CircuitBreakerOptionsBuilder` — where `Build()` is `Resolve()` followed by `Publish()`. `MessageBrokerOptionsBuilder` has NO `Publish` method: it is the outermost builder, so its internal `Build()` resolves the graph, binds its own section over it, and only then performs the parent's registrations inline — calling each child's `Publish` with the nested instance reachable from that finalized graph rather than with the sub-builder's own return value. The child builders' `Build()` methods are public, so a composition-time callback that calls one directly (`AddRecoveryOptions(r => r.Build())`) publishes an unbound instance from the child, outside the parent's finalized-graph publish. Pinned by `MustNotRegisterAnyServiceWhenResolved` on each of the four builders, and by `MustNotRegisterNestedOptionsBeforeBuildWhenFluentNestedOptionsUsed` and `MustNotRegisterCircuitBreakerOptionsBeforeBuildWhenWithCircuitBreakerUsed`. `Resolve()` is internal on all four builders and `Publish(TOptions)` is internal on the three child builders; no existing public signature, type or accessibility changed — the publishing entry points (`ReliabilityOptionsBuilder.Build()`, `RecoveryOptionsBuilder.Build()`, `CircuitBreakerOptionsBuilder.Build()` and every `FromConfig` overload) stay public, and `MessageBrokerOptionsBuilder.Build()` stays internal as it already was (#423).
- **A fluent call on any of this package's four options builders now records a value and registers nothing — every registration a builder performs happens in its publish step.** `RecoveryOptionsBuilder.UseNoDelayRecovery()`, `UseExponentialDelayRecovery(int)`, `UseConstantDelayRecovery(int)` and `UseRouteToErrorQueueRecoveryAction()` were the last fluent methods still writing to the container as they were called, each performing its `IRetryDelayStrategy` or `IMaxReceivesExceededAction` `Replace` on the spot. They now record which delay strategy was asked for (with its argument) and whether the route-to-error-queue action was asked for, and `Publish` performs the identical registrations — pinned by `MustResolveNoDelayRetryWhenUseNoDelayRecoveryComposedThroughTheParentBuild`, `MustResolveExponentialDelayRetryWhenUseExponentialDelayRecoveryComposedThroughTheParentBuild`, `MustResolveConstantDelayRetryWhenUseConstantDelayRecoveryComposedThroughTheParentBuild` and `MustResolveErrorQueueDispatcherWhenUseRouteToErrorQueueRecoveryActionComposedThroughTheParentBuild`, which each configure through the parent builder and resolve the strategy or action back out of the built provider. The guarantee is guarded across each builder's DECLARED PUBLIC INSTANCE METHODS rather than method by method: `MustLeaveTheContainerEmptyForEveryFluentMethodOnMessageBrokerOptionsBuilder`, `MustLeaveTheContainerEmptyForEveryFluentMethodOnReliabilityOptionsBuilder`, `MustLeaveTheContainerEmptyForEveryFluentMethodOnRecoveryOptionsBuilder` and `MustLeaveTheContainerEmptyForEveryFluentMethodOnCircuitBreakerOptionsBuilder` enumerate their builder type's public instance methods by reflection (`BindingFlags.Public | BindingFlags.Instance`), exclude only the publish path (`Build`, `Resolve`, `Publish`, `FromConfig`) and members declared by `object`, invoke each one over a fresh `ServiceCollection` and assert it stays empty. That exclusion list is a positive allowlist matched BY NAME, so an INSTANCE METHOD added later to one of the four builder types is swept from the day it is written unless it is called `Build`, `Resolve`, `Publish` or `FromConfig` — a future member carrying one of those four names is exempt whatever it does. A parameter shape the sweep cannot synthesise fails the test naming that method instead of silently skipping it. What the sweep proves of a method it does reach is bounded by how it calls one: every argument is synthesised at its default — an empty array, a zero-valued struct, a NO-OP `Action<TBuilder>` — so it establishes that the method registers nothing when invoked that way, not that no argument value and no callback-configured state can drive it to register. An EXTENSION METHOD is not: reflection binds against the builder type, and an extension method is a static declared on another type, so the sweep cannot see one. `MessageBrokerOptionsBuilderExtensions.UseGuidMessageIdGenerator()`, `UseCombGuidMessageIdGenerator()` and `UseHashedBodyGuidMessageIdGenerator()`, and `ChatterMessageBrokerExtensions.AddReceiver<TMessage>(...)`, read like fluent calls at the call site but register through the public `MessageBrokerOptionsBuilder.Services` as they run, and are outside this guarantee — tracked in #438. This is a statement about the declared instance methods of the four builders named above and nothing else (#423).
- **The configured retry delay strategy is published with `Replace`, so it still wins over the shipped presence-gated default.** `AddChatterMessageBrokers` registers `NoDelayRetry` as the `IRetryDelayStrategy` only when none is registered already; `Publish` registers the configured strategy with `Replace` (remove-all then add), which is unconditional, so the configured strategy is the sole surviving registration regardless of the order in which the two run. What carries the guarantee is that `Publish`'s `Replace` fires at all, and that the shipped default stays presence-gated rather than becoming an unconditional registration of its own — both pinned by `MustResolveConfiguredRetryDelayStrategyNotThePresenceGatedDefault`. The recorded delay strategy is a single choice rather than an accumulation, so the last fluent call still wins, pinned by `MustResolveTheLastRequestedRetryDelayStrategyAcrossTwoAddRecoveryOptionsCalls` (#423).

### Fixed

- **Configuring the same nested options twice no longer discards the first call's configuration.** `AddReliabilityOptions(...)`, `AddRecoveryOptions(...)` and `WithCircuitBreaker(...)` each constructed a FRESH sub-builder on every call and overwrote the one already retained, so a second call started from the sub-builder's own defaults and only that call's settings reached the finalized options. Each setter now configures the ONE sub-builder it retains — each retained field has exactly one assignment site — so two calls compose instead of the later one displacing the earlier. Pinned by `MustKeepBothReliabilitySettingsAcrossTwoAddReliabilityOptionsCalls`, which routes outbox routing through the first `AddReliabilityOptions` call and the outbox polling processor through the second, then asserts the finalized `ReliabilityOptions` carries both. The exception predicates configured through these setters were additive before this change and remain so — `RetryExceptionEvaluator` and `CircuitBreakerExceptionEvaluator` each consume every registered provider — pinned by `MustKeepBothRetryPredicateSetsWhenAddRecoveryOptionsUsedTwice`, `MustKeepBothRetryPredicateSetsAcrossTwoAddRecoveryOptionsCalls` and `MustKeepBothCircuitBreakerPredicateSetsAcrossTwoWithCircuitBreakerCalls` (#423).

## [0.24.0] - 2026-09-08

### Changed

- **`ICircuitBreakerStateStore` now issues one atomic admission and adjudicates every transition itself, instead of exposing separate state reads and transition calls.** The new `AdmitAsync(TimeSpan openToHalfOpenWaitTime, CancellationToken cancellationToken)` returns a `CircuitBreakerAdmission` — a decision the store made, not state the caller observed, so it cannot go stale across an await. `CircuitBreakerAdmission` (public, readonly struct) carries a `CircuitBreakerVerdict` (public enum: `Refused`, `Execute`, `Trial`; `Refused` is its default value, so an admission that was never issued denies rather than admits), the `CircuitBreakerState`, the half-open `Episode` the admission belongs to, and `LastException`. When the store finds an open circuit's cooling period elapsed, the transition to `HalfOpen` and the `Trial` admission that enters it happen inside the same call, under the same lock — no caller can observe the store between deciding cooling is over and admitting the trial. The admission is also the token an outcome is reported against: the four former transition calls are replaced by two reports, `Task<bool> RecordSuccessAsync(CircuitBreakerAdmission admission, int successesToClose, CancellationToken cancellationToken)` and `Task<bool> RecordFailureAsync(CircuitBreakerAdmission admission, Exception ex, int failuresToOpen, CancellationToken cancellationToken)`, neither of which is callable without presenting an admission. The admission AUTHORIZES a report rather than authenticating its bearer: it carries no proof of issuance, and what the store re-checks is the verdict and the episode it names. An external implementor of `ICircuitBreakerStateStore` must:
  - **delete** `OpenAsync(Exception)`, `CloseAsync()`, `IncrementFailureCounterAsync(Exception)` and `IncrementSuccessCounterAsync()`; there is no replacement call for a caller that invoked them, because reporting an outcome is now the only way the circuit moves;
  - **track an episode counter**, incrementing it on every transition — into open, into closed, and into half-open;
  - **implement `AdmitAsync`** to decide the verdict from current state under the store's own synchronization, performing the open-to-half-open transition as part of that same decision when the wait has elapsed. `CircuitBreaker` runs the action only for `Execute` or `Trial` and refuses every other verdict, so a store that returns a value outside the enum refuses rather than executing — pinned by `MustRefuseAnAdmissionCarryingAVerdictOutsideTheContract`;
  - **implement the two reports** so that re-checking the admission and performing the transition it warrants happen inside the *same* acquisition of that synchronization. Each must re-check the admission's verdict and its episode against the store's current episode, and record nothing at all when either fails — not the counter, and not the last exception. `RecordSuccessAsync` accepts only a `Trial` verdict and closes at `successesToClose`; `RecordFailureAsync` accepts `Execute` or `Trial`, re-opens immediately on a `Trial` (the trial is the probe, so one failure is the whole evidence) and otherwise counts toward `failuresToOpen`;
  - **accept a `CancellationToken` on all three async members** — `AdmitAsync(TimeSpan openToHalfOpenWaitTime, CancellationToken cancellationToken)`, `RecordSuccessAsync(CircuitBreakerAdmission admission, int successesToClose, CancellationToken cancellationToken)` and `RecordFailureAsync(CircuitBreakerAdmission admission, Exception ex, int failuresToOpen, CancellationToken cancellationToken)`. `CircuitBreaker` hands the token of the call being adjudicated to all three, pinned by `MustPassItsOwnTokenToEveryStoreCall`, so a store whose adjudication is real I/O can carry that cancellation into it. The shipped in-memory store's bodies are synchronous under one lock, so it honours the token by throwing *before* it takes that lock and recording nothing — pinned by `MustRefuseToAdmitWithoutTouchingStateWhenTheTokenIsAlreadyCancelled`, `MustRecordNothingWhenASuccessIsReportedWithAnAlreadyCancelledToken` and `MustRecordNothingWhenAFailureIsReportedWithAnAlreadyCancelledToken`;
  - **measure the cooling interval from a MONOTONIC source, never from the wall clock.** `LastStateChangedDateUtc` is a diagnostic that no decision reads; an implementation that decides `openToHalfOpenWaitTime` has elapsed by subtracting it from `DateTime.UtcNow` admits a trial early after a forward clock correction and holds the circuit open past the configured wait after a backward one. See the Fixed entry below;
  - **return `true` from a report only when that report itself transitioned the circuit** — pinned by `MustReportOnlyTheCallThatTransitionedTheCircuit`, with a `default(CircuitBreakerAdmission)` — whose `Refused` verdict is what denies it, since its `Episode` of `0` matches a fresh store's — changing nothing pinned by `MustChangeNothingForAnOutcomeReportedAgainstAnAdmissionThatWasNeverIssued`. `CircuitBreaker` drives its critical-failure timer from that answer alone and never re-reads the store (#432, #298).
- **With `OpenToHalfOpenWaitTimeInSeconds` set to `0`, an open circuit never refuses.** A zero wait is always already elapsed, so the first call after opening is admitted straight to a trial instead of being refused once more. The builder's default is `15` seconds (`CircuitBreakerOptionsBuilder`'s default, unchanged by this release), so production behaviour at the default configuration is unaffected; this only changes callers who configured an explicit `0`-second wait (#432, #298).
- **The cooling wait is now ordered after the admission decision rather than before the transition.** `CircuitBreaker.ExecuteAsync` used to delay for the cooling period and only then ask the store to transition; it now asks the store to adjudicate first — the store performs the elapsed-cooling transition inside `AdmitAsync` — and paces a resulting refusal with the same delay afterward. Total wall-clock time to the first trial is unchanged; only the ordering of the wait relative to the transition decision moved (#432, #298).

### Removed

- **`ICircuitBreakerStateStore.TryHalfOpenAsync()`** is removed. `AdmitAsync(TimeSpan)` supersedes it: it decides the same open-to-half-open transition, atomically, as part of the single admission decision every caller now takes. An external implementor of `ICircuitBreakerStateStore` must delete this member (#432, #298).
- **`ICircuitBreakerStateStore.OpenAsync(Exception)`, `CloseAsync()`, `IncrementFailureCounterAsync(Exception)` and `IncrementSuccessCounterAsync()`** are removed, along with their implementations on `InMemoryCircuitBreakerStateStore`. The contract now exposes no transition command of any kind — its absence is pinned by `MustNotExposeATransitionCommand`, which asserts none of the four names is declared on either the interface or the shipped store. `RecordSuccessAsync` and `RecordFailureAsync` replace all four: a caller reports the outcome of the call it was admitted to, and the store decides which transition that outcome warrants. An external implementor must delete all four members and implement the two reports described in the Changed entry above. A caller that invoked any of the four directly has no replacement call to migrate to; arranging a specific circuit state in a test now means driving the store through its own adjudication — admit, then report a failure — rather than commanding it (#432, #298).

### Fixed

- **The circuit breaker's cooling period is no longer measured from the wall clock.** `InMemoryCircuitBreakerStateStore` decided whether an open circuit had finished cooling by subtracting `LastStateChangedDateUtc` from `DateTime.UtcNow`, and `DateTime.UtcNow` is not monotonic: an NTP correction, a VM migration or an operator moving the system clock shifted it. A clock correction FORWARD made the configured wait look already elapsed and admitted a trial early; a correction BACKWARD held the circuit open past that wait, potentially far past it. The elapsed interval is now measured from a monotonic source, so no decision the store makes reads the wall clock — pinned by `MustNotAdmitATrialEarlyWhenTheWallClockStampMovesBackward` and `MustStillAdmitATrialWhenTheWallClockStampMovesForward`, which move the store's own wall-clock stamp (the equivalent of moving the clock the other way) and assert the verdict does not follow it. `LastStateChangedDateUtc` keeps its wall-clock meaning and is still stamped at every transition, pinned by `MustUpdateLastStateChangedDateWhenAnAdmissionEntersHalfOpen` and `MustUpdateLastStateChangedDateWhenASuccessReportClosesTheCircuit` (#432, #298).
- **A cancellation arriving while the store is adjudicating no longer runs the action anyway.** `CircuitBreaker.ExecuteAsync` checked the caller's token once, before asking for an admission, and never again before invoking the action — and the store contract carried no token at all, so a cancellation landing during adjudication was invisible to both. All three store members now take the caller's `CancellationToken`, and `ExecuteAsync` re-checks it across the admission await, pinned by `MustNotRunTheActionWhenCancellationArrivesWhileTheStoreIsAdjudicating`. That re-check reads the TOKEN, not the circuit's state: the admission's verdict and episode still select the branch and authorize every report, so it does not reintroduce the stale state read the entries below removed (#432, #298).
- **`CircuitBreaker.ExecuteAsync` no longer selects its branch from state it observed before an `await`.** It previously read `IsOpen`, then `State`, then `State`/`LastException` again across separate lock acquisitions and an intervening `await`, so another caller could change the store's state in between and the branch taken no longer matched the store's current state. It now takes exactly one decision — the admission `AdmitAsync` issues — and branches on that, so the branch can never be invalidated by a concurrent caller. This is reachable in production: `ICircuitBreaker` and `ICircuitBreakerStateStore` are registered `Scoped`, and `BrokeredMessageReceiver` shares one recovery strategy across up to `MaxConcurrentCalls` concurrent workers (#432, #298).
- **A half-open trial's success can no longer land in a later episode's counter.** The removed `IncrementSuccessCounterAsync()` took no episode, so a success arriving after the circuit had re-opened and reset still incremented the counter toward closing a half-open episode it was never part of. `RecordSuccessAsync` now takes the admission the trial was issued and discards the success once that admission's episode has ended, pinned by `MustDiscardASuccessWhoseEpisodeHasEnded` (#432, #298).
- **A half-open trial's success can no longer CLOSE a circuit that has since tripped.** Previously the breaker incremented the success counter, compared the returned count against the threshold itself, and then issued `CloseAsync()` — an unconditional command that consulted nothing — so counting the success and closing the circuit were two decisions taken with the store's lock released in between. The store now re-checks the admission's episode and performs the close inside one acquisition of that lock, and a success reported against an ended episode leaves the circuit exactly where it is, pinned by `MustNotCloseTheCircuitForASuccessReportedAgainstAnEndedEpisode` (#432, #298).
- **A half-open trial's failure can no longer RE-OPEN a circuit that has since closed.** The trial path previously called `OpenAsync(ex)` directly, an unconditional command carrying no notion of which half-open episode the failed trial belonged to. A failure is now reported against the admission that authorized the trial, and one whose episode has ended leaves the circuit closed, pinned by `MustNotOpenTheCircuitForAFailureReportedAgainstAnEndedEpisode` (#432, #298).
- **A failure the store discards no longer overwrites `LastException`.** The removed `IncrementFailureCounterAsync(Exception)` recorded the exception unconditionally as part of the increment, with no notion of which episode the failure belonged to. The store now records the exception only for a report it accepts, so the exception a rejected report carried leaves `LastException` untouched, pinned by `MustNotRecordTheLastExceptionForAFailureReportedAgainstAnEndedEpisode` (#432, #298).

## [0.22.0] - 2026-09-07

### Changed

- **The default retry-exception predicates and the default circuit-breaker-trip-exception predicates are now answered by two separate types.** Previously one type implemented both `IRetryExceptionPredicatesProvider` and `ICircuitBreakerExceptionPredicatesProvider` and was registered as both, so what to retry and what should trip the circuit could not diverge. `DefaultRetryExceptionPredicatesProvider` and `DefaultCircuitBreakerExceptionPredicatesProvider` (both `internal`) now decide each question independently — each yields exactly one predicate, matching a transient `BrokeredMessageReceiverException` (#317, #298).

- **`DefaultExceptionsPredicateProvider`** (public) is removed. An application that referenced it directly, or registered it itself, must remove that reference; the framework registers its two internal replacements automatically. See the Security entry below for the migration path for callers who relied on its message-text matching (#317, #298).

### Security

- **Exception message TEXT no longer influences whether a receive fault is retried or trips the circuit breaker.** The removed `DefaultExceptionsPredicateProvider` classified an exception as transient in part by substring-matching its message against eight strings (`retry`, `timeout`, `time out`, `rerun`, `internal server error`, `waiting`, `wait until`, `service unavailable`). A handler exception routinely echoes message-body content, so a crafted — or merely unlucky — message could be classified transient, retried to the trip threshold, and open the shared per-receiver circuit breaker that gates that receiver's message receive, its delivery-count probe, dispatch, and all four settlement paths (ack, nack, deadletter, and the error-queue forward). Since 0.21.0 an open circuit refuses rather than executes, and a refusal itself spends retry budget, so tripping it on one message denies service to every other message on the receiver rather than merely delaying them. Both shipped default predicate sets — the retry set and the circuit-breaker-trip set — now decide by exception TYPE only. No shipped transport loses coverage: Azure Service Bus, SQL Service Broker, and RabbitMQ each already classify their own SDK faults by exception type, in their own modules, unchanged. An application using only the core package, or a custom `IMessagingInfrastructureReceiver`, whose faults were retried only because their message text happened to match one of those eight strings, must register an explicit type-based predicate instead: `.RetryWhen<TException>()` for retry, `.IsTrippedBy<TException>()` for the circuit-breaker trip decision (#317, #298).

## [0.21.0] - 2026-09-06

### Changed

- **An open `CircuitBreaker` no longer executes the action.** It refuses instead, throwing `CircuitBreakerOpenException` without invoking the action. Calling code that relied on the action still running while the circuit was open must handle the refusal. A refused attempt also now consumes retry budget, so work behind a persistently open circuit surfaces `MaxRetryAttemptsExceededException` rather than retrying indefinitely (#316, #318, #320, #298).
- **`IRetryDelayStrategy` implementors must accept a `CancellationToken`.** The tokenful `ExecuteAsync` overloads are now the abstract contract members; the tokenless forms remain as default-interface shims, so callers of the interface are unaffected (#316, #298).
- **`ICircuitBreakerStateStore` gains `Task<bool> TryHalfOpenAsync()`.** An implementation must compare-and-swap `Open` to `HalfOpen` under its own synchronization, mutating nothing and returning `false` from any other state (#316, #298).

### Fixed

- An open `CircuitBreaker` previously still executed the action on every call: the documented fast-fail `throw` sat after a `try` that always returned or rethrew, so it was unreachable. The open path is now its own branch that refuses without running the action (#316, #298).
- A caller waking from either the open-circuit cooling wait or the half-open admission wait no longer forces a recovered circuit back to half-open, nor discards accumulated half-open successes. Such a caller no longer announces the half-open transition either: the information-level message is emitted only when the state store grants the transition, so a refusal no longer records a phantom state change in operational logs (#316, #298).
- The open-circuit cooling wait ignored the caller's cancellation token; cancelling during that wait now throws `OperationCanceledException` and leaves the circuit open rather than moving it to half-open (#316, #298).
- A half-open trial's failure path opened the circuit for any exception, including a caller-requested shutdown cancellation, without consulting the trip predicate. It now shares the same trip decision as the closed path: a non-tripping exception no longer reopens the circuit, and a caller's own cancellation never does either (#316, #298).
- The half-open slot is now released correctly after a failed trial, so the next trial is admitted rather than left waiting (#316, #298).
- `RetryStrategy`'s retry loop no longer spins unbounded when the circuit breaker refuses every attempt: a refusal now consumes retry budget like any other failure, so a persistently open circuit reaches `MaxRetryAttemptsExceededException` (#318, #320, #298).

## [0.19.0] - 2026-09-03

### Added

- `IOptions<MessageBrokerOptions>`, `IOptionsSnapshot<MessageBrokerOptions>` and `IOptionsMonitor<MessageBrokerOptions>` now resolve the instance `MessageBrokerOptionsBuilder.Build()` finished, rather than one the container built for itself. This is an ADDED capability, not a defect fix: this builder never registered a `Configure<MessageBrokerOptions>`, so there was no second instance to remove — what the facets resolved instead was a framework-created, all-default `MessageBrokerOptions` whose `TransactionMode` was `None` and whose `Reliability` and `Recovery` were both `null`, so an application reading `.Recovery.MaxRetryAttempts` off a facet got a `NullReferenceException` rather than a wrong number, and not one configured key landed. The monitor facet is for resolution only: configuration is bound once at build time, so the options never reload, the change registration is inert, and — there being no named options in this package — every name, including none, resolves the same built instance (#296).

### Changed

- **`MessageBrokerOptions`, `ReliabilityOptions`, `RecoveryOptions`, and `CircuitBreakerOptions` now bind their configuration section INTO the fluent-defaulted instance (`BindNonPublicProperties = true`) instead of REPLACING it via `Get<T>()`.** Every bindable property on these types is `internal set`, and `ConfigurationBinder.Get<T>()` defaults to `BindNonPublicProperties = false`, so a populated configuration section previously bound nothing and every configured value was silently discarded. Replacing the instance also skipped the fluent defaults applied elsewhere in the builder, so the result was worse than not configuring anything at all. Unspecified keys now keep their builder defaults; specified keys are honoured (#296, #311, #312).

- `AddMessageBrokers` now actually reads the `Chatter:MessageBrokers` configuration section. Previously the documented DI entry point never passed a section to the builder, so `appsettings` configuration was inert no matter how it was written (#296, #311, #312).
- `RecoveryOptions.CircuitBreakerOptions` is now aliased to the documented `CircuitBreaker` configuration key via `[ConfigurationKeyName]`, so the same documented key is honoured regardless of entry point (#296, #312).
- The instance `MessageBrokerOptionsBuilder.FromConfig(string)` no longer discards accumulated fluent state or registers a shadow second set of options singletons (#296, #311).
- **A consumer's own `services.Configure<MessageBrokerOptions>(...)`, `Configure<ReliabilityOptions>(...)`, `Configure<RecoveryOptions>(...)` or `Configure<CircuitBreakerOptions>(...)` is no longer consulted.** The options facets for these four types are now bound directly to the instance the builder finished and never go through the container's options factory, which is exactly what makes that instance authoritative; a post-configure of them consequently stops applying. No known consumer does this, but it is a public behaviour change: configure these options through the fluent builder or the `Chatter:MessageBrokers` section instead (#296).

### Fixed

- **`IOptions<CircuitBreakerOptions>`, `IOptions<RecoveryOptions>` and `IOptions<ReliabilityOptions>` (and their snapshot and monitor forms) resolved a SECOND options instance that had never seen the builder's fluent defaults.** Each of those three builders registered a `Configure<T>(section)` alongside the singleton it had just built, so the container's own options factory constructed its own object from the configuration section alone. A facet reader therefore saw `ConcurrentHalfOpenAttempts` as `0` where the built instance held `1`, `MaxRetryAttempts` as `0` with a null `CircuitBreakerOptions` where the built instance held `5` and a populated one, and `OutboxProcessingIntervalInMilliseconds` as `0` where the built instance held `5000`. All three builders now register the built instance for both the concrete type and the three facets, so every SINGLE-INSTANCE resolution — the concrete type and all three facets — returns it. The facet registrations REPLACE rather than append, so a second `Build()` on the same service collection cannot leave an earlier instance reachable through a facet; the concrete registration APPENDS, so an earlier instance does remain reachable through `IEnumerable<T>`, which is harmless because each one is the finished product of its own `Build()` rather than a half-built object. Nothing inside this package injected those facets — `BrokeredMessageOutboxProcessor`, `RetryStrategy`, `RetryWithCircuitBreakerStrategy` and `CircuitBreaker` all inject the concrete options types, which were always correctly seeded — so the divergent values were reachable only by an application that resolved a facet itself (#296).

Upgrader note: any consumer that already had a populated `Chatter:MessageBrokers` section (including its `CircuitBreaker`, `Reliability`, and `Recovery` subsections) has been running on type defaults regardless of what was configured. On upgrade, that configuration starts taking effect — review `MaxRetryAttempts`, the circuit-breaker thresholds, and especially `TransactionMode` before upgrading. Two failure shapes are worth separating before you upgrade. A value of the wrong TYPE — a non-numeric count, a non-boolean flag, a `TransactionMode` naming no member of the enum — cannot be converted, so `ConfigurationBinder` throws an `InvalidOperationException` out of `Build()` naming the full configuration key path; that is the binder's own failure and it is the one case that names the key you wrote. A value of the right type but a nonsensical VALUE is not checked at all: it still surfaces from the component that reads it, or silently misbehaves there. Build-time validation over the second class is tracked in issue #423 (#296, #311, #312, #313).

## [0.16.0] - 2026-08-30

### Changed

- **BREAKING:** `IMessagingInfrastructureReceiver.AckMessageAsync`, `NackMessageAsync`, and `DeadletterMessageAsync` now return `Task<SettlementResult>` instead of `Task<bool>`. `SettlementResult` (backed by the new `SettlementOutcome` enum: `Settled`, `NotRequired`, `Failed`) distinguishes "there was nothing to settle" (e.g. Azure Service Bus `ReceiveAndDelete`, RabbitMQ at-most-once) from "settlement was attempted and did not happen" — a distinction the former `bool` collapsed into a single `false`. A custom `IMessagingInfrastructureReceiver` implementation must migrate its three settlement members to return `SettlementResult.Settled()`, `SettlementResult.NotRequired(reason)`, or `SettlementResult.Failed(reason)` in place of `true`/`false`. Receive-failure retention (the diagnostics an application observes on a failed receive) now keys on the `Failed` outcome rather than a bare `false`, so `BrokerDiagnostics.ErrorTypes.SettlementFailed` (`"settlement_failed"`) now appears as `error.type` on a receive metric for a settlement the infrastructure reported as failed without throwing, in addition to the pre-existing exception-carrying case (#283).
- **BREAKING:** `IMessagingInfrastructureReceiver` gains a defaulted `bool WritesToErrorQueue => false` member: whether the infrastructure writes a failed delivery to the Error Queue itself, so the core must not run its own error-recovery action (`ErrorQueueDispatcher` → `IForwardMessages`) for that delivery and duplicate the write. A settlement is now eligible for the core's error-recovery action only when it is BOTH settled AND `WritesToErrorQueue` is `false` — previously an infrastructure that owned the Error Queue write could only suppress the core's duplicate by misreporting its own settlement as `false`. A custom implementation that owns its own Error Queue write must now override `WritesToErrorQueue` to report `true` instead of misreporting its settlement outcome (#283).
- Bundled dependency uplift to Chatter.CQRS 0.10.0 (an in-repo `ProjectReference`, so the pack-time package dependency moves with it); no behavioral change to Chatter.MessageBrokers itself beyond the additions above.

## [0.15.0] - 2026-08-29

### Added

- Optional, opt-in OpenTelemetry-compatible tracing and metrics built entirely on the BCL (`System.Diagnostics.ActivitySource` and `System.Diagnostics.Metrics.Meter`) with no `OpenTelemetry.*` package dependency. The `ActivitySource` and the `Meter` are both named `Chatter.MessageBrokers`; an application opts in BY NAME with `.AddSource("Chatter.*")` / `.AddMeter("Chatter.*")` on its own provider. The scope names are the opt-in contract — the `ActivitySource` and `Meter` instances themselves are not public surface. When nothing subscribes to the source or the meter there is no cost and no change to what goes on the wire (#274).
- Broker-boundary instrumentation: a send span per dispatch call and a receive span per delivery, a `messaging.client.operation.duration` histogram in seconds, and `messaging.client.sent.messages` / `messaging.client.consumed.messages` counters. Instrumentation never materializes a lazily-supplied publish batch — a caller's sequence is enumerated once, by the router, at the same moment and with the same side effects whether diagnostics are on or off. The batch count is therefore observed DURING that enumeration and carried on the send span at stop, and `messaging.client.sent.messages` reports the messages actually yielded, so a dispatch that fails mid-enumeration records a partial count rather than a whole batch (#274).
- Receive metrics carry `error.type` for a delivery the worker's error ladder SETTLED — a poisoned message, an exhausted delivery, a nack — not only for a failure that escaped the worker, so an application subscribed to the meter and to no `ActivitySource` does not see a failed receive reported as a successful operation (#274).
- A delivery carrying no usable `traceparent` starts a fresh root span with any ambient activity attached as a link, matching how a delivery that does carry one treats ambient context. A headerless delivery is no longer a child of whatever unrelated host activity happened to be current when the receive loop started, and the ambient activity that suppression sets aside is restored once the receive span stops, so it is intact for the rest of that delivery's flow whether the span was sampled in or out (#274).
- The send span and the send metrics carry `messaging.destination.name` for the `Send`/`Publish` overloads that omit an explicit destination and let each message's `BrokeredMessageAttribute` resolve one. The destination is observed during the single enumeration the router already performs — never resolved eagerly — and is reported only when every message of the dispatch call resolved to the SAME destination; a batch spanning several destinations reports none, because the attribute holds one value (#274).
- Receive metrics carry `error.type` when message handling succeeded but the settlement then failed — an acknowledgement, negative acknowledgement, deadletter or failed-recovery action that Recovery could not complete. Such a failure is swallowed into a `false` return by design and so never leaves the processing worker, which means it would otherwise have been reported as a successful receive while the message stayed unsettled and eligible for redelivery (#274).
- W3C trace-context propagation (`traceparent` / `tracestate`) across the brokered message boundary, carried on the message context so it survives the outbox and replay. Scope is deliberately partial: trace context flows for Azure Service Bus, RabbitMQ, the EntityFramework outbox, and the Cosmos outbox. It does not flow across the SQL Service Broker `DefaultType` receive path, nor for SQL Change Feed messages, which originate from a SQL trigger with no producer to stamp them. Both gaps are pre-existing limitations that affect all headers alike and are not introduced by tracing (#274).

### Changed

- The outbound dispatch sequence is now documented as single-pass on both seams it crosses (`IRouteBrokeredMessages.Route` and `IMessagingInfrastructureDispatcher.Dispatch`): the sequence is lazy and its iterator carries per-yield side effects — message id generation, message body conversion, W3C trace-context propagation — plus the send span's batch count, so an implementation must enumerate it exactly once and must not walk it with `Count()`/`Any()`/`ToList()` in addition to the real enumeration. This documents a contract the pipeline already relied on; no behavior change (#274).
- Bundled dependency uplift to Chatter.CQRS 0.9.0 (an in-repo `ProjectReference`, so the pack-time package dependency moves with it); no behavioral change to Chatter.MessageBrokers itself beyond the additions above.

## [0.13.1] - 2026-06-09

### Fixed

- `BrokeredMessageReceiver` startup now owns the infrastructure receiver privately through `InitializeAsync` (outside the teardown gate) and publishes it only via an atomic, non-blocking go-live/surrender handoff taken under the teardown gate, so teardown can no longer reach a still-initializing receiver. This structural change dissolves the entire "await / field-assignment outside the gate during the `Starting` window" defect class — subsuming the earlier per-window guards (the indivisible disposal-claim-with-receiver and the half-built-state guards below) — while keeping init off the gate, so a hung `InitializeAsync` cannot block teardown.
- `BrokeredMessageReceiver` teardown disposition (stop vs. dispose) is now decided exactly once, monotonically, entirely under the teardown gate, and is never reset. A premature pre-start `Dispose()` on a DI-singleton receiver still takes the `NotStarted` restartable no-op without recording a disposition, so it can no longer leak `Dispose` strength into a later genuine `StopReceiver()` (which would have disposed infrastructure that should only be stopped). Because the disposition is recorded once under the gate and never reset, strongest-wins holds by construction across the receiver's life — a `Dispose` racing or following a `Stop` still disposes infrastructure — and there is no longer a lock-free outside-the-gate strength mutation or a per-epoch reset to race against.
- `BrokeredMessageReceiver` teardown admission is now a single `SemaphoreSlim`-serialized critical section (replacing the earlier lock-free single-flight flag) layered atop the retained lifecycle+strength state machine (`NotStarted` → `Starting` → `Live` → `TornDown`). By construction this makes impossible: (a) stranded-admission hangs — losers serialize on the gate and re-observe terminal state; (b) startup/teardown orphaned primitives and double-Stop — loop-primitive construction and go-live run under the same gate teardown takes, so teardown sees either the pre-construction infra-only state or the full set, never a half-built one; (c) disposal-disposition races — the teardown disposition is recorded once under the same teardown gate and never reset (subsuming the former separate escalation step and per-epoch reset), so a teardown loser can neither erase a recorded `Dispose` request via a concurrent reset nor observe a stale disposition that would leave infrastructure merely stopped instead of disposed; deadlock-safe with no `SynchronizationContext` capture; (d) disposal-claim-over-null-receiver leak — the one-shot infrastructure disposal claim is now produced indivisibly with the non-null receiver via a single primitive, so a `Dispose`-strength teardown racing the `Starting` window before the infrastructure receiver is assigned can no longer latch the disposal claim over a null receiver and leak the infrastructure receiver that the abandoned go-live path subsequently disposes. Preserved: idempotency, strength monotonicity (a `Dispose` racing a `Stop` still disposes infrastructure), startup-window partial teardown, and the original non-OCE receive-loop-fault TOCTOU fix that caused a net8.0-specific flaky shutdown (`WhenReceiveLoopFaults`).
- `BrokeredMessageReceiver` teardown is now non-throwing and terminal, aligned to the canonical .NET `DisposeAsync`/`DisposeAsyncCore` pattern. Infrastructure-teardown faults raised during `DisposeAsync`, `Dispose`, or `StopReceiver` are swallowed-and-logged (per the guideline that disposal must not throw) and teardown still reaches a clean terminal state — replacing the prior fault-resettable retry machinery: a faulted quiesce or transient teardown fault no longer leaves teardown retryable, and synchronous `Dispose` no longer defers latching `disposed` on a fault. Net behavior: teardown is serialized and race-free across startup, strength, and epoch, and now also terminal and non-throwing rather than retryable.
- `BrokeredMessageReceiver.DisposeAsync` now follows the canonical `DisposeAsyncCore` template, delegating teardown through the shared core so async disposal, synchronous `Dispose`, and `StopReceiver` share one terminal, non-throwing teardown path.
- A throwing `InitializeAsync` during startup now disposes the partially-initialized infrastructure receiver instead of leaking it; startup remains startup-fatal and the original exception propagates.
