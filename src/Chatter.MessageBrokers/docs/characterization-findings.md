# Chatter.MessageBrokers — Characterization Findings

This document is a pure observation log produced during behavior-pinning (characterization) testing of `Chatter.MessageBrokers`. Every row records **current behavior as-is** — not desired or corrected behavior. No production source was modified. Tests that pin these behaviors live under `src/Chatter.MessageBrokers/tests/`. Each finding is flagged here for human review and prioritization; no code fix is prescribed.

| # | Unit | Pinned behavior | Why suspicious | Pinning test | Suggested follow-up |
|---|------|-----------------|----------------|--------------|---------------------|
| 1 | `BrokeredMessageAttributeProvider.GetBrokeredMessageDescription<T>()` | Throws `NullReferenceException` for undecorated types | Every sibling getter (`GetMessageName`, `GetReceiverName`, `GetErrorQueueName`, `GetInfrastructureType`) uses null-conditional `?.` and returns `null`; `GetBrokeredMessageDescription` dereferences the null attribute directly (missing `?.`) | `UsingBrokeredMessageAttributeProvider/WhenGettingAttributeDetails.cs::MustThrowWhenGettingDescriptionForUndecoratedType` | Add null-conditional `?.` to align with the other getters and return `null` instead of throwing |
| 2 | `BrokeredMessageAttribute` | Constructor arg `receivingPath` populates a property named `ReceiverName`; no `ReceivingPath` property exists; `sendingPath` maps to `SendingPath` | Asymmetric naming: `receivingPath` → `ReceiverName` breaks the parameter-to-property naming convention established by `sendingPath` → `SendingPath` | `UsingBrokeredMessageAttribute/WhenConstructing.cs::MustMapReceivingPathArgToReceiverNameProperty` | Consider adding a `ReceivingPath` alias property or renaming `ReceiverName` to `ReceivingPath` for symmetry; if `ReceiverName` is public API it is a breaking change — review carefully |
| 3 | `BrokeredMessageAttribute` | `infrastructureType` parameter defaults to `""` (empty string); `errorQueueName`, `messageDescription`, and `deadletterQueueName` default to `null` | Inconsistent sentinel across optional parameters in the same type; callers must distinguish `null` vs `""` for infrastructure type | `UsingBrokeredMessageAttribute/WhenConstructing.cs::MustDefaultInfrastructureTypeToEmptyStringWhenNotSupplied` | Align to a single sentinel (`null` preferred); audit all call sites that check `string.IsNullOrEmpty` vs `!= null` for infra type |
| 4 | `RoutingSlip.RouteToNextStep()` | Mutates `Route` in place (removes head, appends to `Visited`); `Route` setter is `internal`; collection drains destructively across calls; returns `null` once exhausted | Single-pass / stateful design makes the slip non-replayable; callers cannot inspect the original route after traversal | `UsingRoutingSlip/WhenRoutingToNextStep.cs::MustRemoveHeadFromRouteInPlace`, `MustAccumulateVisitedInOrderAcrossRepeatedCallsToExhaustion`, `MustReturnNullOnceRouteIsExhausted` | Document the single-pass contract explicitly in XML-doc; consider a snapshot/clone API if replayability is needed |
| 5 | `ExponentialDelayRetry` (delay formula) | Formula `(int)(0.5 * (2^a - 1)) * 1000` truncates the `0.5` factor before multiplying by `1000`, yielding attempt 1 → 0 ms, attempt 2 → 1 000 ms; actual schedule (1 s, 3 s, 7 s, 15 s…) diverges from XML-doc remarks which claim 2 s, 4 s… | Doc/behavior divergence and lost sub-second precision due to integer truncation order | `Recovery/Retry/UsingExponentialDelayRetry/WhenComputingDelay.cs::MustComputeZeroMillisecondsForAttemptOneDueToTruncation`, `MustComputeOneSecondForAttemptTwo` | Fix truncation order (`(int)(0.5 * (2^a - 1) * 1000)`) or update XML-doc to match actual schedule; rerun tests after either change |
| 6 | `ExponentialDelayRetry` (overflow) | At attempt 31 the computed term overflows `Int32` to a negative value; only the `_maxDelayInMilliseconds` cap in `ExecuteAsync` prevents propagating a negative delay, not the computed term itself | A missing clamp on the raw computed value allows negative intermediate results; cap in the wrong layer | `Recovery/Retry/UsingExponentialDelayRetry/WhenComputingDelay.cs::MustOverflowToNegativeForLargeAttempt` | Clamp the computed term to `[0, int.MaxValue]` before applying the ms cap, or switch to `long` arithmetic and clamp to the configured max |
| 7 | `RetryStrategy.ExecuteAsync` | `catch (CircuitBreakerOpenException) {}` is an empty block — no increment, no delay, no evaluation; if the action keeps throwing `CircuitBreakerOpenException` the `while(true)` loop never terminates (busy-spin / infinite loop) | Silent swallow + unconditional loop creates a hang under a persistently open circuit breaker | `Recovery/Retry/UsingRetryStrategy/WhenExecuting.cs::MustSwallowCircuitBreakerOpenExceptionAndRetryWithoutDelay` | Add an attempt counter or rethrow after a max-attempt guard inside the `CircuitBreakerOpenException` catch block |
| 8 | `CircuitBreaker.ExecuteAsync` | The `throw new CircuitBreakerOpenException(...)` statement after a `try/finally` whose `try` block unconditionally returns or throws is unreachable code | Dead code reduces readability and can mask future refactoring mistakes | (documented observation — not directly assertable in a pinning test) | Remove the unreachable `throw` or restructure the control flow so the throw is reachable when intended |
| 9 | `RetryWithCircuitBreakerStrategy` | No null-argument guards: constructor assigns `_options`, `_circuitBreaker`, and `_retry` without null checks | `RetryStrategy` and `CircuitBreaker` both guard their constructor arguments; inconsistent defensive-construction contract | `Recovery/UsingRetryWithCircuitBreakerStrategy/WhenExecuting.cs::MustNotThrowWhenConstructedWithNullOptions` | Add `ArgumentNullException` guards for all three constructor parameters to match sibling types |
| 10 | `CircuitBreakerState` enum | Ordinal order is `Closed(0)`, `HalfOpen(1)`, `Open(2)` (non-severity, non-alphabetical); state checks use named helpers or `!= HalfOpen` comparisons rather than ordinal ordering | Non-intuitive ordering invites misuse if anyone adds an ordinal comparison in future maintenance | `Recovery/CircuitBreaker/UsingInMemoryCircuitBreakerStateStore/WhenManagingState.cs::MustDefaultToClosedState` | Add an XML-doc warning that ordinal values carry no severity meaning; consider reordering to `Closed(0)`, `Open(1)`, `HalfOpen(2)` (breaking if serialized) — evaluate impact first |
| 11 | `RetryExceptionEvaluator` / `CircuitBreakerExceptionEvaluator` | Use `predicatesProviders?.SelectMany(pp => pp?.GetExceptionPredicates())`; a provider that returns a `null` predicate *collection* (not a null provider) would NRE on enumeration; the null-collection-from-provider path was NOT pinned | Latent NRE for a non-null provider returning null collection; safe paths (null provider list; null predicate element) are pinned | `Recovery/Retry/UsingRetryExceptionEvaluator/WhenEvaluating.cs` (and circuit-breaker evaluator tests) | Add a `.Where(c => c != null)` after `GetExceptionPredicates()` call, or document the contract that providers must not return null collections |
| 12 | `InboundBrokeredMessage` ctor | Sets `BodyConverter = bodyConverter ?? new JsonBodyConverter()` then immediately reads `bodyConverter.ContentType` off the original (still-null) parameter → `NullReferenceException`; the null-coalescing fallback is dead/unreachable for that access | Null-coalescing assignment followed by null-dereference on the original param makes the guard useless | `Receiving/UsingInboundBrokeredMessage/WhenConstructing.cs::MustThrowNullReferenceWhenBodyConverterIsNull` | Change `bodyConverter.ContentType` to `BodyConverter.ContentType` (use the already-assigned field) so the fallback is actually reachable |
| 13 | `OutboundBrokeredMessage.RefreshTimeToLive()` | Guard `ttl.Duration().TotalMilliseconds > 0` uses absolute value, so an already-expired (negative) TTL passes the check and the raw negative TTL is stored; the `else` branch (clamp to `TimeSpan.Zero`) only fires when expiry is exactly now | Expired TTLs should likely be clamped to zero, not stored as negative; absolute-value guard masks the expiry condition | `Sending/UsingOutboundBrokeredMessage/...::MustSetNegativeTimeToLiveWhenExpiryHasPassed` | Replace `ttl.Duration().TotalMilliseconds > 0` with `ttl.TotalMilliseconds > 0` so negative TTLs fall into the clamp-to-zero branch |
| 14 | `FailureContext.ToString()` | Constructor accepts a null `failure` argument (no guard), but `ToString()` dereferences `Failure.Message` and `Failure.StackTrace` → NRE; `failureDescription` is validated but `failure` is not | Asymmetric null handling in the same constructor: one param guarded, the other not | `Context/UsingFailureContext/WhenConstructing.cs::MustThrowNullReferenceFromToStringWhenFailureIsNull` | Add an `ArgumentNullException` guard for `failure` in the constructor, or add a null check inside `ToString()` |
| 15 | `MaxReceiveAttemptsExceededException` | Declares no custom constructors, message, or properties; produces the framework default message "Exception of type '…MaxReceiveAttemptsExceededException' was thrown."; carries no attempt count, threshold, message id, or inner exception | Minimal diagnostic value; operators cannot distinguish this exception or determine context from logs alone | `Receiving/UsingMaxReceiveAttemptsExceededException/WhenConstructing.cs::MustUseDefaultExceptionMessageNamingDerivedType` | Add a constructor accepting attempt count, threshold, and optionally message id; set a meaningful default message string |
| 16 | `InMemoryBrokeredMessageOutbox` | With the default `ReliabilityOptions.MinutesToLiveInMemory == 0`, expiry cleanup is fully skipped → processed messages are retained indefinitely; re-adding the same id still throws `InvalidOperationException` | Unbounded in-memory growth on the default (unconfigured) option value; zero is likely intended as "no cleanup" but is undocumented and potentially a footgun | `Reliability/Outbox/UsingInMemoryBrokeredMessageOutbox/WhenManagingOutbox.cs::MustRetainProcessedMessageWhenMinutesToLiveIsZero` | Document that `MinutesToLiveInMemory = 0` disables cleanup; consider a non-zero default, or a sentinel constant (`NoExpiry`), and add a max-size guard |
| 17 | `BrokeredMessageDispatcher.Dispatch` (lazy projection) | Per-message body conversion, id generation, and destination resolution live inside a `yield return` projection; these only execute when the router enumerates the sequence; a router that does not enumerate silently skips all conversion and id-stamping | Silent data loss for non-enumerating routers; no error or log | `Sending/UsingBrokeredMessageDispatcher/WhenSending.cs::MustNotBuildOutboundMessageWhenRouterDoesNotEnumerate` | Materialize the outbound sequence before passing to the router (e.g. `.ToList()`), or document and enforce that all routers must enumerate the sequence |
| 18 | `BrokeredMessageDispatcher.Dispatch` (infra-type sentinel) | A missing `MessageContext.InfrastructureType` cast `(string)infraType` yields `null` passed to `Route`; `BrokeredMessageRouter.Route` defaults `infrastructureType` to `""` — layers disagree on the no-infra sentinel | `null` vs `""` sentinel disagreement between dispatcher and router for the same concept | `Sending/UsingBrokeredMessageDispatcher/WhenSending.cs::MustPassNullInfrastructureTypeWhenNoneInMessageContext` | Standardize the no-infra sentinel to `null` throughout, or to `""`, and add a null-coalescing conversion at the dispatcher→router boundary |
| 19 | `BrokeredMessageRouter.Route(single)` | The empty-destination `ArgumentNullException` guard is only reachable via the internal JSON constructor; the public `OutboundBrokeredMessage` constructor already rejects whitespace destinations — so the guard is dead via the public API | Dead guard reduces test coverage signal and may mislead maintainers | `Routing/UsingBrokeredMessageRouter/WhenRouting.cs::MustThrowWhenSingleMessageHasNoDestination` | Remove the dead guard if the public constructor is the sole entry point, or expose a path that can reach it; add a comment explaining why it is reachable only via internal construction |
| 20 | `OutboxBrokeredMessageRouter` | `Route(batch, …, infrastructureType)` discards the `infrastructureType` argument (outbox `SendToOutbox` has no such parameter); `Route(single)` calls the single outbox overload directly — infra-type routing intent is silently lost via the outbox path | Callers providing an infra type get silent no-op routing rather than an error or fallback | `Reliability/Outbox/UsingOutboxBrokeredMessageRouter/WhenRouting.cs::MustIgnoreInfrastructureTypeWhenWritingBatchToOutbox`, `MustWriteSingleMessageToOutboxViaSingleOverload` | Log a warning or throw when `infrastructureType` is non-empty and being discarded; or document explicitly that the outbox router ignores infra type by design |
| 21 | `ReplyRouter` | Null `ReplyToRoutingContext` returns `Task.CompletedTask` with no routing and no log; production code contains `//TODO: log` | Silent no-op on missing reply context; the in-code TODO acknowledges the logging gap | `Routing/UsingReplyRouter/WhenRouting.cs::MustReturnCompletedTaskWhenDestinationRouterContextIsNull` | Implement the TODO: log a warning when `ReplyToRoutingContext` is null so operators can detect misconfigured reply routing |
