# Chatter.MessageBrokers.SqlServiceBroker — Characterization Findings

This document is a pure observation log produced during behavior-pinning (characterization) testing of `Chatter.MessageBrokers.SqlServiceBroker`. Every row records **current behavior as-is** — not desired or corrected behavior. No production source was modified. Tests that pin these behaviors live under `src/Chatter.MessageBrokers.SqlServiceBroker/tests/`. Each finding is flagged here for human review and prioritization; no code fix is prescribed.

| # | Unit | Pinned behavior | Why suspicious | Pinning test | Suggested follow-up |
|---|------|-----------------|----------------|--------------|---------------------|
| 1 | `SqlServiceBrokerOptionsBuilder` fluent setters (`WithConnectionString`, `WithMessageBodyType`, `WithJsonBodyType`) | Throw `NullReferenceException` when called before `AddSqlServiceBrokerOptions` initializes `_sqlServiceBrokerOptions` | All three setters dereference `_sqlServiceBrokerOptions` without a null check; the field is `null` until one of the `AddSqlServiceBrokerOptions` overloads is called, making call order silently load-bearing | `Configuration/UsingSqlServiceBrokerOptionsBuilder/WhenBuilding.cs::MustThrowNullReferenceExceptionWhenWithConnectionStringCalledBeforeAddOptions`, `MustThrowNullReferenceExceptionWhenWithMessageBodyTypeCalledBeforeAddOptions`, `MustThrowNullReferenceExceptionWhenWithJsonBodyTypeCalledBeforeAddOptions` | Add a null check (or initialize `_sqlServiceBrokerOptions` eagerly) in each fluent setter to give a meaningful `InvalidOperationException` instead of an opaque `NullReferenceException` |
| 2 | `SqlServiceBrokerOptions` constructor vs. builder connection-string overload | `ConversationLifetimeInSeconds` defaults to `int.MaxValue` via the parameterized constructor, but the property initializer and the builder's `AddSqlServiceBrokerOptions(string)` overload both default it to `0` — three code paths, two different values | Divergent defaults for the same property depending on how the options object is created; callers using the constructor directly get a dramatically different conversation lifetime than callers using the builder | `Configuration/UsingSqlServiceBrokerOptionsBuilder/WhenBuilding.cs::MustDefaultCtorConversationLifetimeToIntMaxValue`, `MustDefaultBuilderOverloadConversationLifetimeToZero`, `MustHaveDivergentCtorAndBuilderConversationLifetimeDefaults` | Reconcile the three defaults to a single value; document the chosen default in XML-doc on the property; audit any callers that rely on the `int.MaxValue` path |
| 3 | `BeginDialogConversationCommand.Create()` | Mutates `_initiatorServiceName` (bracket-wrap) and `_targetServiceName` (bracket-strip) in place on every call — non-idempotent across repeated `Create()` calls; additionally, the initiator is bracket-wrapped while the target is bracket-stripped (asymmetric identifier handling) | Instance field mutation inside a build method means a second call to `Create()` will double-bracket the initiator and double-strip the target; asymmetric escaping risks SQL object-name mismatches for callers that pass pre-bracketed service names | `Scripts/UsingBeginDialogConversationCommand/WhenCreatingCommand.cs::MustBracketWrapInitiatorServiceName`, `MustNotDoubleBracketInitiatorThatAlreadyStartsWithBracket`, `MustStripBracketsFromTargetServiceNameParameterValue` | Make `Create()` work on local copies rather than mutating instance fields; document and align the bracket convention (wrap vs. strip) consistently for both service names |
| 4 | `ReceiveMessageFromQueueCommand.Create()` | Interpolates `{_queueName}` raw into the `FROM` clause of the SQL statement with no bracket-escaping and no parameterization | Queue names containing spaces, special characters, or SQL keywords will produce malformed or silently incorrect SQL; the surface is injection-adjacent for caller-supplied names | `Scripts/UsingReceiveMessageFromQueueCommand/WhenCreatingCommand.cs::MustInterpolateQueueNameRawWithoutBracketEscaping`, `MustEmitExactBaseQueryForDefaultHandleAndDefaultTimeout` | Bracket-escape `_queueName` (e.g. `[{_queueName}]` after stripping any existing brackets) when interpolating into the `FROM` clause; document the name constraints if parameterization is not feasible for DDL-style identifiers |
| 5 | `EndDialogConversationCommand.Create()` | The error-clause branch returns early, making `WITH CLEANUP` unreachable when an error clause is emitted even if `enableCleanup` is `true`; additionally, a non-zero `errorCode` paired with a blank `errorDescription` silently drops the entire error clause (guard requires both to be present) | Two silent suppressions in the same command builder: a caller enabling cleanup alongside an error will not get cleanup, and a caller setting only an error code (without a description) gets no error clause and no diagnostic | `Scripts/UsingEndDialogConversationCommand/WhenCreatingCommand.cs::MustNotEmitCleanupWhenErrorClauseEmittedEvenIfCleanupEnabled`, `MustSkipErrorClauseWhenErrorCodeSetButDescriptionBlank`, `MustNotAddErrorCodeParameterWhenDescriptionBlank` | Consider either documenting the mutual-exclusion of error and cleanup as a Service Broker constraint, or restructuring control flow to emit cleanup after the error clause; add a guard or log for the blank-description case |
| 6 | `JsonUnicodeBodyConverter` | Hard-codes `Encoding.Unicode` (UTF-16 LE) and `ContentType` of `"application/json; charset=utf-16"`, diverging from the sibling `JsonBodyConverter` which uses UTF-8; UTF-8 bytes fed through this converter's `Stringify` method produce garbled output, not the original string | Any message body produced by the UTF-8 converter (or any standard HTTP JSON client) will be silently corrupted when decoded by this converter; the content-type advertisement (`utf-16`) diverges from the HTTP/JSON ecosystem default | `UsingJsonUnicodeBodyConverter/WhenConverting.cs::MustGetBytesUsingUtf16Encode`, `MustGarbleWhenUtf8BytesDecodedAsUnicode`, `MustExposeApplicationJsonUtf16ContentType` | Document explicitly that this converter is intended only for SQL Service Broker endpoints that negotiate `utf-16` bodies; add a compatibility note warning against mixing with the UTF-8 converter or standard JSON clients |
| 7 | `SqlRetryExceptionPredicatesProvider` and `SqlCircuitBreakerExceptionPredicatesProvider` — `SqlException`-positive predicate branches | The branches matching `e is SqlException` are NOT pinnable without a live SQL connection; `SqlException` is sealed with no public constructor and cannot be constructed in unit tests or mocked by Moq, so only the non-`SqlException` and null branches are covered by the characterization tests; additionally, the two provider implementations are byte-for-byte identical (only namespace and implemented interface differ) | Characterization boundary: the transient-error and error-number branches are untestable in isolation — this is an observation of coverage limits, not a behavior divergence; the duplicated implementation is a maintenance surface for future divergence | `Receiving/Retry/UsingSqlRetryExceptionPredicatesProvider/WhenGettingExceptionPredicates.cs::MustReturnFalseFromEveryPredicateForNonSqlException`, `MustReturnFalseFromEveryPredicateForNull`; `Receiving/CircuitBreaker/UsingSqlCircuitBreakerExceptionPredicatesProvider/WhenGettingExceptionPredicates.cs::MustReturnFalseFromEveryPredicateForNonSqlException`, `MustReturnFalseFromEveryPredicateForNull` | Consider a shared base or helper for the common predicate logic to eliminate the duplicated implementation; evaluate whether an integration test harness is feasible for the `SqlException`-positive paths |
| 8 | `ReceivedMessage` constructor | Assigns all constructor arguments verbatim to getter-only properties with no null or argument validation; a null `Body`, null `ServiceName`, null `ServiceContractName`, or null `MessageTypeName` is stored as-is | Every sibling message type in the broader Chatter stack performs at least some argument validation; the absence of any guard here makes downstream NREs non-local and hard to diagnose | `Receiving/UsingReceivedMessage/WhenConstructing.cs::MustStoreNullBodyAsIs`, `MustStoreNullStringsAsIs` | Add `ArgumentNullException` guards for fields whose null value would cause a downstream NRE; at minimum document which fields are nullable by design |
| 9 | `SqlExceptionHelper.IsErrorNumberTransient` — error number `-2` and error number `20` | Error `-2` (DBNETLIB timeout) is treated as NON-transient because the `case -2:` branch is commented out in production; error `20` is listed in the transient set | Error `-2` is a well-known network-timeout error code for SQL Server and is typically considered transient; treating it as non-transient means a timeout-induced disconnect will not trigger the configured retry policy; error `20` appearing in the transient list is unusual and may warrant a comment explaining the rationale | `Receiving/UsingSqlExceptionHelper/WhenCheckingErrorNumberTransience.cs::MustReturnFalseForMinusTwoBecauseItsCaseIsCommentedOut`, `MustReturnTrueForDocumentedTransientErrorNumber` (InlineData(20)), `MustReturnFalseForNonTransientErrorNumber` | Review the intent behind the commented-out `-2` case and either restore it with a guard or add a source comment explaining why it is intentionally excluded; verify that error `20` belongs in the transient set |
